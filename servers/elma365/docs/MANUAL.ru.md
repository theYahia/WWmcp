# Руководство пользователя elma365-mcp

Пакет `@theyahia/elma365-mcp`, версия 2.0.0, 20 инструментов. Node.js 18 и выше.
Публичный API ELMA365, точка входа `https://<домен>.elma365.ru/pub/v1/`.

## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ к low-code платформе ELMA365: разделы и приложения, элементы
приложений (записи), BPM-задачи и их завершение по исходам, запуск и наблюдение
бизнес-процессов, пользователи, лента комментариев. Задача, которую это снимает, —
переключение между чатом и веб-интерфейсом BPM: «какие задачи прилетели на меня и ещё не
закрыты», «согласуй заявку 8f3… с исходом „Утверждено“», «запусти процесс приёма
сотрудника», «заведи запись в реестре договоров».

Кому это нужно: сотруднику, у которого рабочий день состоит из BPM-задач; руководителю,
который согласовывает; интегратору, который разбирается в чужом контуре ELMA365 — какие
есть разделы, приложения и коды полей.

Отдельная особенность платформы: **имена всего в ELMA365 настраиваются заказчиком.**
Ни namespace, ни коды приложений, ни коды полей заранее неизвестны. Поэтому три
инструмента обнаружения (`list_namespaces`, `list_apps`, `get_app_schema`) — не
вспомогательные, а первый шаг любого сценария.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "elma365": {
      "command": "npx",
      "args": ["-y", "@theyahia/elma365-mcp"],
      "env": {
        "ELMA365_DOMAIN": "mycompany",
        "ELMA365_TOKEN": "ваш_токен"
      }
    }
  }
}
```

Клиент читает конфигурацию при старте — после правки его нужно перезапустить.

### Claude Code

```
claude mcp add elma365 -e ELMA365_DOMAIN=mycompany -e ELMA365_TOKEN=ваш_токен -- npx -y @theyahia/elma365-mcp
```

### Cursor / Windsurf / VS Code (Copilot)

Cursor и Windsurf принимают тот же блок `mcpServers` в `.cursor/mcp.json` или
`.windsurf/mcp.json`. У VS Code файл `.vscode/mcp.json`, и корневой ключ там — `servers`,
а не `mcpServers`; поля `command`, `args`, `env` те же. Файл рабочей области обычно
попадает в систему контроля версий — `ELMA365_TOKEN` в нём хранить не следует.

### Режим Streamable HTTP

```bash
ELMA365_DOMAIN=mycompany ELMA365_TOKEN=токен npx @theyahia/elma365-mcp --http --port 3000
```

Порт задаётся **аргументом командной строки `--port`** (по умолчанию 3000), а не
переменной окружения. Эндпоинты: `POST /mcp` и `GET /health`; всё остальное — `404`.
`/health` возвращает `status`, `server`, `version` и блок `config` с двумя признаками:
`domainConfigured` и `tokenConfigured` — так проверяют, что переменные дошли до процесса,
не делая запросов к ELMA365.

Защита от DNS-rebinding: принимаются только запросы с `Host`, равным `localhost`,
`127.0.0.1` или `[::1]` (с портом и без). Прочие получают `403` с подсказкой настроить
`ELMA365_ALLOWED_HOSTS`. Аутентификации у `/mcp` нет — доступ к порту равносилен доступу
к контуру ELMA365 в объёме прав токена, поэтому порт в недоверенной сети не публикуют.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `ELMA365_DOMAIN` | да (или `ELMA365_BASE_URL`) | Поддомен облака (`mycompany` → `mycompany.elma365.ru`) либо полный хост (`mycompany.elma365.ru`) |
| `ELMA365_TOKEN` | да | Токен API, уходит заголовком `Authorization: Bearer …` |
| `ELMA365_BASE_URL` | нет | Полный базовый адрес для локальной установки, например `https://elma365.mycorp.com/pub/v1`. **Имеет приоритет** над `ELMA365_DOMAIN` |
| `ELMA365_TIMEOUT` | нет | Таймаут запроса в миллисекундах, по умолчанию 10 000 |
| `ELMA365_ALLOWED_HOSTS` | нет | Дополнительные допустимые `Host` через запятую (HTTP-режим) |

Домен распознаётся по наличию точки: значение без точки считается поддоменом облака и
достраивается до `<значение>.elma365.ru`; значение с точкой берётся как готовый хост.
Отсутствие переменных обнаруживается при первом вызове инструмента, а не при старте.

## 3. Где взять токен доступа

Токен создаётся в интерфейсе ELMA365: **Администрирование → Токены → «+ Токен»**. Раздел
доступен группе «Администраторы». Значение показывается **только в момент создания** —
потом его нельзя посмотреть, только выпустить новый.

Три следствия, которые определяют работу сервера:

1. **Токен привязан к пользователю.** Все действия выполняются от его имени: созданные
   элементы, комментарии и завершённые задачи будут числиться за ним.
2. **Права токена — это права пользователя.** Видно ровно то, что видит этот сотрудник.
   Инструмент, на который прав нет, не исчезнет из списка — он вернёт отказ от API.
   Ограничивать область работы агента следует правами пользователя в ELMA365, а не
   формулировкой запросов.
3. **Список задач привязан к тому же пользователю.** `get_tasks` с видом `income`
   возвращает задачи, пришедшие владельцу токена, а не тому, кто разговаривает с агентом.

**Домен.** Возьмите поддомен из адреса своего контура: у `https://mycompany.elma365.ru`
это `mycompany`. Для локальной установки задайте `ELMA365_BASE_URL` целиком, вместе с
хвостом `/pub/v1` — тогда `ELMA365_DOMAIN` не используется.

## 4. Инструменты по задачам

Списочные инструменты работают по схеме `from` (смещение, по умолчанию 0) и `size`
(количество, 1–10 000, по умолчанию 50). Ответы возвращаются форматированным JSON — как
их отдал ELMA365, без переупаковки. Типовой конверт списка выглядит как
`{success, error, result: {result: [...], total}}`.

### 4.1 Обнаружение структуры — начинать отсюда

**`list_namespaces`** — разделы системы. Параметров нет.

**`list_apps`** — приложения внутри раздела. Обязателен `namespace`.

**`get_app_schema`** — схема приложения: коды и типы полей. Обязательны `namespace` и
`code`. Это единственный способ узнать, как называются поля, которые дальше пойдут в
`data` при создании и изменении элементов.

Пропускать этот шаг нельзя: коды придумывает тот, кто настраивал контур. Приложение
«Договоры» в одном контуре может иметь код `contracts`, в другом — `dogovor`, и
угаданное имя даст `404`, а не пустой список.

### 4.2 Элементы приложений

**`get_app_items`** — список записей. Обязательны `namespace` и `code`; необязательны
`from`, `size`, `active` (только не удалённые), `filter` — объект «код поля: значение», и
`sortExpressions` — массив правил `{field, ascending}` (`ascending` по умолчанию `true`).

**`get_app_item`** — одна запись. Обязательны `namespace`, `code` и `id` (UUID).

**`create_item`** — создание. Обязательны `namespace`, `code` и `data` — объект полей по
их кодам. Необязательны `statusGroupId` и `withEventForceCreate` (принудительно вызвать
событие создания). Поля уходят в ELMA365 вложенными в `context` — сервер оборачивает их
сам.

**`update_app_item`** — изменение. Обязательны `namespace`, `code`, `id` и `data`
(изменяемые поля). Помечен как разрушающий: перезаписывает значения полей.

**`set_app_item_status`** — смена статуса. Обязательны `namespace`, `code`, `id` и
`status` — **код** статуса, а не название. Тоже помечен как разрушающий.

### 4.3 BPM-задачи

**`get_tasks`** — список. Необязательный `kind` выбирает выборку:

| `kind` | Что возвращает |
|---|---|
| `all` (по умолчанию) | Все задачи |
| `income` | Входящие — пришедшие владельцу токена |
| `outcome` | Исходящие — поставленные им |
| `participate` | Задачи, в которых он участвует |

Прочее: `from`, `size`, `closed` (включать завершённые), `filter` — объект полей задачи.

**`get_task`** — одна задача по `id`.

**`get_task_exits`** — доступные **исходы** задачи по `id`. Исход — это вариант
завершения, заданный схемой процесса («Утверждено», «Отклонено», «На доработку»).
Вызывается **перед** завершением: идентификатор исхода нельзя ни угадать, ни составить.

**`complete_task`** — завершение. Обязательны `id`, `exitId` (из `get_task_exits`) и
`instanceId` — идентификатор экземпляра процесса, которому принадлежит задача.
Необязательный `context` передаёт значения полей формы завершения.

**`reassign_task`** — переназначение. Обязательны `id` и `userId` нового исполнителя
(искать через `get_users`).

### 4.4 Бизнес-процессы

**`list_processes`** — шаблоны процессов раздела. Обязателен `namespace`.

**`start_process`** — запуск. Обязательны `namespace` и `code` шаблона; необязательный
`context` передаёт входные параметры процесса.

**`get_process_instances`** — запущенные экземпляры по шаблону. Обязательны `namespace` и
`code`; необязательны `from`, `size`, `active` (только активные) и `filter`.

### 4.5 Пользователи

**`get_users`** — список; `from`, `size` и `filter` — объект вида `{"email": "…"}`.

**`get_user_by_id`** — пользователь по `id`. **Отдельного эндпоинта у ELMA365 нет**:
инструмент запрашивает список с фильтром по идентификатору и возвращает первый элемент.
Если разобрать конверт не удалось, возвращается полный ответ — данные не теряются.

### 4.6 Комментарии

Комментарии в ELMA365 — это лента объекта (feed), а не отдельная сущность приложения.

**`get_comments`** — сообщения ленты элемента. Обязательны `namespace`, `code`, `itemId`;
необязательны `from` и `size`.

**`add_comment`** — новое сообщение. Обязательны `namespace`, `code`, `itemId` и `text`.

## 5. Готовые сценарии

**1. «Какие задачи на мне и ещё не закрыты?»**
`get_tasks` (`kind: "income"`, `closed: false`). Возвращаются задачи владельца токена —
это важно понимать при общей установке на отдел.

**2. «Согласуй заявку: завершить задачу с исходом „Утверждено“.»**
`get_tasks` (найти задачу и её `id`) → `get_task` (взять `instanceId` экземпляра
процесса) → `get_task_exits` (`id`, найти идентификатор нужного исхода) →
`complete_task` (`id`, `exitId`, `instanceId`, при необходимости `context` с полями
формы). Порядок обязателен: идентификатор исхода без `get_task_exits` не получить.

**3. «Что вообще есть в системе?»**
`list_namespaces` → `list_apps` по интересующему разделу → `get_app_schema` по
приложению. Три вызова дают карту контура: разделы, приложения, коды и типы полей.

**4. «Заведи запись в реестре договоров.»**
`get_app_schema` (`namespace`, `code` — узнать коды полей) → `create_item`
(`namespace`, `code`, `data` с кодами полей из схемы). Ответ содержит созданный элемент;
идентификатор берут из него для последующих действий.

**5. «Найди все заявки в статусе „новая“ за последние…»**
`get_app_items` (`namespace`, `code`, `filter: {"status": "new"}`,
`sortExpressions: [{"field": "createdAt", "ascending": false}]`, `size: 50`). Коды полей
и коды статусов — из `get_app_schema`, не по названиям на экране.

**6. «Запусти процесс приёма сотрудника.»**
`list_processes` (`namespace`, найти код шаблона) → `start_process` (`namespace`, `code`,
`context` с входными параметрами) → `get_process_instances` (`namespace`, `code`,
`active: true`) для проверки, что экземпляр появился.

**7. «Переназначь задачу на Петрова.»**
`get_users` (`filter: {"email": "petrov@…"}`, взять `id`) → `reassign_task` (`id` задачи,
`userId`).

**8. «Покажи переписку по элементу и добавь комментарий.»**
`get_comments` (`namespace`, `code`, `itemId`) → `add_comment` (те же три параметра плюс
`text`).

**9. «Смени статус элемента на „в работе“.»**
`get_app_schema` (найти код нужного статуса) → `set_app_item_status` (`namespace`,
`code`, `id`, `status` — код). Название статуса из интерфейса API не примет.

## 6. Ограничения и подводные камни

### 6.1 Ничего нельзя угадать: namespace, коды приложений и полей

Это главное свойство работы с ELMA365. Платформа low-code, и вся номенклатура задаётся
при внедрении. Ошибка в коде даёт `404` — не пустой список и не подсказку. Отсюда
жёсткое правило: сначала `list_namespaces` → `list_apps` → `get_app_schema`, потом
чтение и запись.

То же относится к статусам: `set_app_item_status` принимает **код** статуса, а `filter`
сравнивает значения полей по их кодам.

### 6.2 Изменяющие вызовы повторяются автоматически — учитывайте это

Клиент ELMA365 в этом сервере собственный, и он повторяет **любой** запрос при `429`,
`5xx` и таймауте: до трёх попыток, задержка `1000 × 2^(попытка−1)` мс, но не дольше
8 секунд; повтор после таймаута идёт без задержки. Различия между чтением и записью, как
и ключа идемпотентности, здесь нет.

Практическое следствие: если `create_item`, `start_process` или `add_comment` завершились
таймаутом, запрос уже мог быть выполнен на стороне ELMA365 и повторён сервером. Прежде
чем повторять вручную, проверьте `get_app_items` или `get_process_instances` — иначе
рискуете получить дубль записи или второй запущенный процесс.

Таймаут по умолчанию — 10 секунд, настраивается `ELMA365_TIMEOUT`. Для тяжёлых выборок
(`size` в тысячах) его имеет смысл поднять, а не полагаться на повторы.

### 6.3 Ответ отдаётся целиком, без выжимки

Инструменты возвращают форматированный JSON ответа ELMA365 как есть. Ни сокращения
полей, ни обрезки объёма: `get_app_items` с `size: 10000` вернёт десять тысяч записей со
всеми полями. Для обзорных задач берите `size` в десятках и сужайте `filter`.

Верхняя граница `size` — 10 000, это ограничение самой платформы для списочных
эндпоинтов. `from` ограничен миллионом.

### 6.4 Завершение задачи требует трёх идентификаторов

`complete_task` не работает по одному идентификатору задачи. Нужны:

- `id` — сама задача;
- `exitId` — исход, только из `get_task_exits`;
- `instanceId` — экземпляр процесса, к которому относится задача; берётся из `get_task`
  или из списка задач.

Это не избыточность: одна и та же задача в разных экземплярах процесса завершается
разными исходами, и платформа требует указать оба контекста.

### 6.5 Задачи считаются от владельца токена

`kind: "income"` и `outcome` определяются пользователем, которому выдан токен. Если
сервер подключён на весь отдел с одним токеном, «мои задачи» будут задачами владельца
токена, а не спрашивающего. Для персональной работы каждому нужен свой токен и своё
подключение.

### 6.6 Комментарии живут в ленте, а не в приложении

Инструменты комментариев обращаются к ленте объекта
(`feed/<namespace>/<code>/<itemId>/message`). Отдельной коллекции комментариев у элемента
приложения в API нет. Практически это значит, что комментарий адресуется тем же тройным
ключом, что и сам элемент: раздел, приложение, идентификатор записи.

### 6.7 Что помечено как разрушающее

Разрушающими объявлены `update_app_item` и `set_app_item_status` — они перезаписывают
данные существующей записи. `create_item`, `complete_task`, `reassign_task`,
`start_process` и `add_comment` помечены как пишущие, но не разрушающие. Инструментов
удаления в сервере нет вовсе.

Подтверждения перед действием сервер не запрашивает: аннотации — подсказка клиенту MCP,
а не барьер. Настоящий барьер — права пользователя, которому выдан токен.

## 7. Частые ошибки

Ошибка возвращается модели результатом с признаком `isError: true` и текстом
`Ошибка ELMA365: <сообщение>`. Сообщения HTTP-уровня выглядят как
`ELMA365 HTTP <код>: <статус> — <тело ответа>`; тело API прикладывается целиком, поэтому
описание причины обычно есть прямо в тексте.

| Что видно | Что это значит | Что делать |
|---|---|---|
| `ELMA365_DOMAIN не задан. Укажите домен (например: mycompany)` | Домен не дошёл до процесса; проявляется при первом вызове инструмента | Задать `ELMA365_DOMAIN` (поддомен без `https://`) либо `ELMA365_BASE_URL` целиком |
| `ELMA365_TOKEN не задан. Укажите Bearer-токен ELMA365 API` | Нет токена | Создать: Администрирование → Токены → «+ Токен»; значение видно только при создании |
| `ELMA365 HTTP 401` | Токен не принят: опечатка, отозван, выдан в другом контуре | Выпустить новый токен; сверить домен |
| `ELMA365 HTTP 403` | Токен верен, но у пользователя нет прав на объект или операцию | Выдать права пользователю, которому принадлежит токен |
| `ELMA365 HTTP 404` | Не найден `namespace`, код приложения, код процесса или идентификатор элемента | `list_namespaces` → `list_apps` → `get_app_schema`; коды нельзя угадывать |
| `ELMA365 HTTP 400` с текстом про поле | Поле в `data` или `filter` названо неверно либо тип значения не тот | Сверить коды и типы через `get_app_schema` |
| `ELMA365 HTTP 400` при `complete_task` | Неверный `exitId` или `instanceId` | `get_task_exits` для исхода, `get_task` для `instanceId`; угадывать нельзя |
| `ELMA365 HTTP 429` | Лимит платформы; три повтора уже израсходованы | Пауза; уменьшить `size` и частоту |
| `ELMA365 HTTP 5xx` | Сбой на стороне платформы; три повтора израсходованы | Повторить позже. Для записи сначала проверить, не создан ли объект |
| `ELMA365 API: все попытки исчерпаны` | Три попытки подряд закончились повторяемой ошибкой | То же: проверить фактическое состояние, потом повторять |
| `This operation was aborted` / таймаут | Ответ не пришёл за `ELMA365_TIMEOUT` (по умолчанию 10 секунд) | Поднять таймаут или уменьшить `size`; для записи — проверить результат перед повтором |
| `Host '…' не разрешён. Настройте ELMA365_ALLOWED_HOSTS.` | HTTP-режим: обращение пришло с адресом, которого нет в списке | Добавить хост в `ELMA365_ALLOWED_HOSTS` через запятую |
| Пустой массив в `result` | Запрос отработал, совпадений нет | Проверить `filter` (коды полей, не названия), `active`, `closed`; убедиться, что у пользователя есть доступ |
| `get_user_by_id` вернул весь список вместо одного | Конверт ответа не совпал с ожидаемым, сервер честно отдал полный ответ | Взять нужный элемент из `result` вручную |

Журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. Туда же пишутся
строки повторов (`<код>, повтор через <N>мс`) и строка запуска с числом инструментов.
