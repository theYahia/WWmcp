# Руководство пользователя yookassa-mcp

Пакет `@theyahia/yookassa-mcp`, версия 3.0.0, 20 инструментов. Node.js 18 и выше.
API ЮKassa версии 3, адрес `https://api.yookassa.ru/v3`.

## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ к платёжному контуру ЮKassa: выставить счёт и получить ссылку
на оплату, подтвердить или отменить холд, вернуть деньги, выбить чек по 54-ФЗ, сделать
выплату на карту или через СБП, разложить платёж между партнёрами маркетплейса, подписаться
на уведомления. Задача, которую это снимает, — ручная работа в кабинете и в биллинге:
«выстави счёт на 4 500 рублей за консультацию», «верни клиенту половину заказа», «где
платёж от вчерашнего вечера, он прошёл?».

Кому это нужно: тому, кто выставляет счета и разбирает возвраты руками; поддержке, которой
нужно за секунду понять статус платежа; разработчику, который собирает интеграцию и
проверяет поведение API до написания кода.

> ⚠️ **Сервер двигает настоящие деньги.** Шесть инструментов — `create_payment`,
> `capture_payment`, `create_refund`, `create_recurring_payment`, `save_payment_method`,
> `create_payout` — необратимы. Они помечены как разрушающие, и клиент MCP может
> спрашивать подтверждение, но полагаться на это как на защиту нельзя. До боевого запуска
> работайте на тестовом магазине и проверяйте это вызовом `get_shop_info` (ожидается
> `"test": true`).

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "yookassa": {
      "command": "npx",
      "args": ["-y", "@theyahia/yookassa-mcp"],
      "env": {
        "YOOKASSA_SHOP_ID": "ваш_shop_id",
        "YOOKASSA_SECRET_KEY": "ваш_секретный_ключ"
      }
    }
  }
}
```

Клиент читает конфигурацию при старте — после правки его нужно перезапустить.

### Claude Code

```
claude mcp add yookassa -e YOOKASSA_SHOP_ID=ваш_id -e YOOKASSA_SECRET_KEY=ваш_ключ -- npx -y @theyahia/yookassa-mcp
```

### Cursor / Windsurf / VS Code (Copilot)

Cursor и Windsurf принимают тот же блок `mcpServers` в `.cursor/mcp.json` или
`.windsurf/mcp.json`. У VS Code файл `.vscode/mcp.json`, и корневой ключ там — `servers`,
а не `mcpServers`. Файл рабочей области обычно попадает в систему контроля версий —
`YOOKASSA_SECRET_KEY` в нём хранить нельзя: этим ключом снимают деньги.

### Режим Streamable HTTP

```bash
HTTP_PORT=3000 MCP_AUTH_TOKEN=длинный_случайный_секрет npx @theyahia/yookassa-mcp --http
```

Режим включается флагом `--http` либо самой переменной `HTTP_PORT` (по умолчанию 3000).
В отличие от прочих серверов монорепозитория, здесь **HTTP-режим отказывается стартовать
без `MCP_AUTH_TOKEN`**: открывать денежные инструменты без аутентификации сервер не станет.

| Метод и путь | Поведение |
|---|---|
| `POST /mcp` | Приём запросов MCP. Требует заголовок `Authorization: Bearer <MCP_AUTH_TOKEN>`, сравнение постоянного времени |
| `GET` или `DELETE /mcp` | `405` — транспорт stateless, сессий и SSE нет |
| `GET /health` | `{status, server, tools}`; без аутентификации |
| прочее | `404` |

Привязка по умолчанию — `127.0.0.1`. Защита от DNS-rebinding включена всегда: `Host`
проверяется по `MCP_ALLOWED_HOSTS` (по умолчанию `127.0.0.1:<порт>,localhost:<порт>`),
браузерный `Origin` — по `MCP_ALLOWED_ORIGINS` (по умолчанию список пуст, то есть все
браузерные источники отклоняются). Символ `*` в CORS не используется никогда.
Выставлять порт в интернет напрямую нельзя даже с токеном — только за обратным прокси со
своей аутентификацией.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `YOOKASSA_SHOP_ID` | да | Идентификатор магазина; вместе с ключом уходит как HTTP Basic |
| `YOOKASSA_SECRET_KEY` | да | Секретный ключ магазина |
| `YOOKASSA_PAYOUT_AGENT_ID` | для выплат | Идентификатор шлюза продукта «Выплаты» |
| `YOOKASSA_PAYOUT_SECRET_KEY` | для выплат | Секретный ключ шлюза выплат |
| `HTTP_PORT` | нет | Порт HTTP-режима; заданная переменная сама включает режим |
| `MCP_AUTH_TOKEN` | в HTTP-режиме | Bearer-токен для `/mcp`; без него режим не стартует |
| `HTTP_HOST` | нет | Адрес привязки, по умолчанию `127.0.0.1` |
| `MCP_ALLOWED_HOSTS` | нет | Допустимые `Host` через запятую |
| `MCP_ALLOWED_ORIGINS` | нет | Допустимые браузерные `Origin` через запятую |
| `YOOKASSA_DEBUG` | нет | `1` или `true` — трассировка запросов в stderr: метод, путь, код, время, ключ идемпотентности. Секреты, заголовок авторизации и тела запросов не пишутся |

Отсутствие ключей обнаруживается **при первом вызове инструмента**, а не при старте:
клиент создаётся лениво.

## 3. Где взять ключи доступа

Два обязательных значения выдаются в кабинете ЮKassa:

1. `YOOKASSA_SHOP_ID` — **Настройки → Магазин** (идентификатор магазина).
2. `YOOKASSA_SECRET_KEY` — **Интеграция → Ключи API** (этот путь сервер называет сам в
   сообщении об отсутствующих переменных).

Аутентификация — HTTP Basic: пара `shopId:secretKey` кодируется в base64 и уходит в
заголовке `Authorization`. Никакого OAuth и обновления токенов здесь нет.

**Тестовый магазин.** Тестовый магазин создаётся в кабинете
(`https://yookassa.ru/my/shop-settings`) и выдаёт собственную пару `shop_id` /
`secret_key`. Отдельного адреса песочницы у API нет — контур определяется тем, чьи ключи
подставлены. Проверка одна: вызвать `get_shop_info` и убедиться, что в ответе `"test":
true`. Делать это следует **до** первой денежной операции, а не после.

**Выплаты — отдельный продукт с отдельными ключами.** «ЮKassa Выплаты» подключается
отдельно и аутентифицируется собственной парой: `YOOKASSA_PAYOUT_AGENT_ID` (идентификатор
шлюза, agentId) и `YOOKASSA_PAYOUT_SECRET_KEY` — **Настройки → Выплаты**. Если эти
переменные не заданы, `create_payout` и `get_payout` пойдут с ключами магазина, и
ЮKassa почти наверняка их не примет: это не ошибка сервера, а отсутствие подключённого
продукта.

## 4. Инструменты по задачам

Суммы во всех инструментах принимаются двумя способами: строкой с двумя знаками после
точки (`"4500"`, `"99.50"` — точный вариант) или положительным числом. Внутри сервер
переводит сумму в копейки целым числом и обратно в формат ЮKassa `{"value": "4500.00",
"currency": "RUB"}` — так дробная часть не теряется на плавающей арифметике. Валюта —
трёхбуквенный код ISO-4217 **заглавными**, по умолчанию `RUB`; `rub` или `руб` будут
отвергнуты проверкой параметров.

### 4.1 Принять платёж

**`create_payment`** — основной инструмент. Обязательны `amount` и `description` (не
длиннее 128 символов). Ключевые необязательные параметры:

| Параметр | Значения | По умолчанию |
|---|---|---|
| `capture` | `true` — одностадийный платёж, `false` — холд с последующим `capture_payment` | `true` |
| `confirmation_type` | `redirect`, `embedded`, `qr` | `redirect` |
| `return_url` | Адрес возврата плательщика; **обязателен при `redirect`** | — |
| `payment_method_type` | `bank_card`, `sbp`, `yoo_money`, `sberbank`, `tinkoff_bank`, `mobile_balance`, `cash`, `installments` | не задан — плательщик выбирает сам |
| `metadata` | Произвольные пары «строка: строка» | — |
| `receipt_email`, `receipt_items`, `receipt_tax_system_code` | Чек 54-ФЗ вместе с платежом | — |

При `confirmation_type: "redirect"` без `return_url` сервер откажет **до** обращения к
ЮKassa: подставлять выдуманный адрес нельзя — по нему уйдёт реальный плательщик после
оплаты. Чек прикрепляется к платежу только если заданы **оба** параметра `receipt_email` и
`receipt_items`; при одном из двух чек просто не будет сформирован, и ошибки не возникнет.

**`get_payment`** — платёж по `payment_id`: статус, сумма, способ оплаты, ссылка
подтверждения, метаданные.

**`list_payments`** — выборка. `limit` (1–100, по умолчанию 10), `status` (`pending`,
`waiting_for_capture`, `succeeded`, `canceled`), `created_at_gte` и `created_at_lte` (дата
и время в ISO-8601), `cursor` для следующей страницы.

**`capture_payment`** — подтверждение двухстадийного платежа. Обязателен `payment_id`,
необязательный `amount` списывает часть удержанной суммы. Списать больше, чем удержано,
ЮKassa не даст.

**`cancel_payment`** — отмена платежа в статусе `pending` или `waiting_for_capture`;
удержанные средства освобождаются.

**`create_sbp_payment`** — платёж через СБП. Обязательны `amount` и `description`,
необязательны `confirmation_type` и `return_url` (правило то же). Отличается от
`create_payment` тем, что способ оплаты жёстко задан как `sbp`, а `capture` всегда `true`.

**`create_split_payment`** — платёж с распределением между партнёрскими магазинами
(маркетплейсы). Обязателен непустой массив `transfers`, у каждой доли — `account_id`
(идентификатор магазина-партнёра) и `amount`, необязательны `platform_fee_amount`
(комиссия площадки), `description`, `metadata`. **Сумма долей обязана в точности совпасть
с `amount`** — сервер сверяет это в копейках до обращения к API и отказывает с указанием
обеих сумм. Требуется подключённый продукт «Сплитование платежей».

### 4.2 Повторные списания

**`save_payment_method`** — привязка способа оплаты для будущих списаний. Обязательны
`amount` и `return_url`; `payment_method_type` — `bank_card` (по умолчанию), `yoo_money`
или `sberbank`. Это **настоящий платёж**: сумма списывается с карты (минимум рубль) и
затем возвращается вручную через `create_refund`. Идентификатор сохранённого способа
берётся из поля `payment_method.id` результата.

**`create_recurring_payment`** — списание по сохранённому способу. Обязательны
`payment_method_id`, `amount` и `description`. Проходит **без участия плательщика** —
никакого подтверждения, ссылки и редиректа: деньги списываются сразу.

### 4.3 Возвраты

**`create_refund`** — обязательны `payment_id` и `amount` (полный или частичный возврат),
необязателен `description`. Валюта возврата не задаётся отдельно — используется рублёвое
форматирование суммы.

**`get_refund`** — возврат по `refund_id`. **`list_refunds`** — список; необязательный
фильтр `payment_id` и `limit` (1–100, по умолчанию 10).

### 4.4 Чеки по 54-ФЗ

**`create_receipt`** — отдельный чек, не привязанный к созданию платежа. Обязательны
`type` (`payment` или `refund`) и непустой массив `items`. У позиции обязательны
`description`, `quantity`, `amount` и `vat_code`:

| `vat_code` | Ставка |
|---|---|
| 1 | Без НДС |
| 2 | 0 % |
| 3 | 10 % |
| 4 | 20 % |
| 5 | Расчётная 10/110 |
| 6 | Расчётная 20/120 |

Необязательные реквизиты позиции подставляются значениями по умолчанию:
`payment_subject` — `commodity` (тег 1212), `payment_mode` — `full_payment` (тег 1214),
`measure` — `piece` (тег 2108, обязателен для ФФД 1.2). Прочее: `payment_id` (для
`type: "payment"`), `refund_id` (для `type: "refund"`), `customer_email` либо
`customer_phone`, `tax_system_code` (тег 1055, только если у магазина несколько систем
налогообложения), `send` (по умолчанию `true`), `settlement_id`.

Массив `settlements` необязателен: если он не передан, сервер сам собирает один расчёт
типа `cashless` на сумму позиций (цена за единицу × количество, с округлением до копейки
по каждой строке).

**`list_receipts`** — фильтры `payment_id`, `refund_id`, `limit` (1–100), `cursor`.

### 4.5 Выплаты

**`create_payout`** — обязателен `amount`. Получатель задаётся **одним из двух взаимно
исключающих способов**, и передать оба сразу нельзя:

- `payout_token` — токен из виджета выплат. Предпочтительный вариант: не требует
  сертификата PCI DSS;
- `destination_type` вместе с `destination_value`: `bank_card` (номер карты — **требует
  PCI DSS**), `yoo_money` (номер кошелька) или `sbp` (телефон в формате `79XXXXXXXXX`,
  и тогда обязателен ещё `bank_id` — идентификатор банка-участника СБП).

Ни один из способов не задан — сервер откажет до обращения к API. Необязательны
`description` (до 128 символов) и `metadata`. Операция **асинхронная**: если в ответе
`status: "pending"`, сервер добавляет отдельным блоком напоминание опросить `get_payout`
или дождаться уведомления, прежде чем считать выплату выполненной.

**`get_payout`** — состояние выплаты по `payout_id`.

Оба инструмента используют клиент выплат: пару `YOOKASSA_PAYOUT_AGENT_ID` /
`YOOKASSA_PAYOUT_SECRET_KEY`, если она задана, иначе — ключи магазина.

### 4.6 Уведомления и сведения о магазине

**`create_webhook`** — подписка. Обязательны `url` (HTTPS) и `event` — одно из
`payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled`,
`refund.succeeded`, `payout.succeeded`, `payout.canceled`, `deal.closed`.
**`list_webhooks`** — все подписки магазина, параметров нет. **`delete_webhook`** —
удаление по `webhook_id`.

**`get_shop_info`** — сведения о магазине: идентификатор, статус, признак тестового режима
`test`, настройки фискализации. **Баланса ЮKassa через API не отдаёт** — несмотря на имя
файла реализации, денежного остатка здесь нет.

## 5. Готовые сценарии

**1. «Выстави счёт на 4 500 рублей за консультацию.»**
`create_payment` (`amount: "4500"`, `description: "Консультация"`,
`return_url: "https://ваш-сайт/thanks"`). Из ответа берётся `confirmation.confirmation_url`
— эту ссылку отправляют плательщику. Структурированный результат содержит `id`, `status`,
`paid`, `amount` и `confirmation_url` отдельными полями.

**2. «Проверь, оплатил ли клиент счёт 2f0…»**
`get_payment` (`payment_id`). Смотреть `status`: `succeeded` — деньги у магазина,
`pending` — плательщик ещё не подтвердил, `waiting_for_capture` — холд ждёт `capture`,
`canceled` — отменён.

**3. «Заморозь деньги, а спишем после отгрузки.»**
`create_payment` (`capture: false`) → плательщик подтверждает → статус становится
`waiting_for_capture` → после отгрузки `capture_payment` (`payment_id`, при частичной
отгрузке — `amount` меньше удержанного). Если отгрузки не будет — `cancel_payment`.

**4. «Верни клиенту половину заказа.»**
`get_payment` (убедиться, что `status: "succeeded"` и какая сумма) → `create_refund`
(`payment_id`, `amount` — половина, `description` с причиной) → `get_refund` для проверки
статуса.

**5. «Выбей чек на две позиции с НДС 20 %.»**
`create_receipt` (`type: "payment"`, `payment_id`, `customer_email`, `items` — по каждой
позиции `description`, `quantity`, `amount`, `vat_code: 4`). `settlements` не передавать —
сервер посчитает сам.

**6. «Настрой ежемесячное списание с карты клиента.»**
`save_payment_method` (`amount: "1"`, `return_url`) → клиент подтверждает привязку →
`get_payment` по идентификатору из ответа, взять `payment_method.id` → `create_refund` на
привязочный рубль → дальше каждый месяц `create_recurring_payment`
(`payment_method_id`, `amount`, `description`).

**7. «Раздели оплату 10 000 между двумя партнёрами поровну.»**
`create_split_payment` (`amount: "10000"`, `transfers: [{account_id: "…", amount: "5000"},
{account_id: "…", amount: "5000"}]`, `return_url`). Сумма долей обязана совпасть с общей —
иначе отказ до обращения к API.

**8. «Выплати исполнителю 12 000 на карту по токену из виджета.»**
`create_payout` (`amount: "12000"`, `payout_token`, `description`) → если в ответе
`status: "pending"`, опрашивать `get_payout` (`payout_id`) до `succeeded` или `canceled`.

**9. «Подпишись на успешные платежи.»**
`create_webhook` (`event: "payment.succeeded"`, `url: "https://ваш-сервер/hook"`) →
`list_webhooks` для проверки. Изменить адрес подписки нельзя — старую удаляют
(`delete_webhook`) и создают новую.

## 6. Ограничения и подводные камни

### 6.1 Ключ идемпотентности защищает от двойного списания

На каждый `POST` и `DELETE` сервер формирует заголовок `Idempotence-Key` **один раз на
логическую операцию** и переиспользует его во всех повторах. Это принципиально: ЮKassa
считает повтор с тем же телом, но другим ключом, **новым запросом** — при генерации ключа
на каждую попытку повтор после таймаута создал бы второй платёж.

Отсюда следует, что повторы здесь безопасны и выполняются для всех методов, включая
записывающие: ответы `429` и `5xx` повторяются до трёх раз с задержкой
`1000 × 2^(попытка−1)` мс, но не дольше 8 секунд. При `5xx` на записи в stderr пишется
предупреждение: результат операции на стороне ЮKassa не определён, повтор идёт с тем же
ключом.

Если все три попытки исчерпаны, **не повторяйте вызов** — проверьте фактическое состояние
через `get_payment`, `get_refund` или `get_payout`.

### 6.2 Таймаут — 35 секунд, и это не опечатка

ЮKassa может формировать ответ до 30 секунд (её `HTTP 500` означает «не успели ответить»).
Клиентский таймаут поэтому поднят до 35 секунд, чтобы не оборвать медленное, но успешное
создание платежа. Переменной окружения он не настраивается. Таймаут повторяется до трёх
раз — ключ идемпотентности не даёт задвоить операцию.

Практический вывод: денежный вызов может честно думать полминуты. Это не зависание.

### 6.3 Двухстадийный платёж и `capture: false`

`capture: true` (по умолчанию) — деньги списываются сразу. `capture: false` — средства
удерживаются, платёж переходит в `waiting_for_capture` и ждёт `capture_payment`. Забытый
холд не превращается в оплату сам: по истечении срока удержания ЮKassa его отменяет, и
деньги возвращаются плательщику. Частичное списание допустимо, превышение удержанной суммы
— нет.

### 6.4 Что именно двигает деньги

| Инструмент | Что происходит |
|---|---|
| `create_payment`, `create_sbp_payment`, `create_split_payment` | Счёт выставлен; списание — после подтверждения плательщиком |
| `capture_payment` | Удержанные средства списываются окончательно |
| `save_payment_method` | **Настоящее списание** привязочной суммы; возвращается только вручную |
| `create_recurring_payment` | Списание **без участия плательщика**, немедленно |
| `create_refund` | Деньги уходят обратно плательщику |
| `create_payout` | Деньги уходят получателю |

Отдельного «режима подтверждения» у сервера нет. Единственный барьер — аннотации
`destructiveHint` и текст инструкций сервера, которые клиент MCP *может* использовать для
вопроса пользователю. Барьер настоящий — это тестовый магазин.

### 6.5 Пагинация курсорная, а не постраничная

`list_payments` и `list_receipts` листаются полем `cursor`: значение `next_cursor` из
предыдущего ответа передаётся в следующий вызов. Номера страницы нет. `limit` — максимум
100. `list_refunds` курсор не принимает вовсе: только `limit` и фильтр `payment_id`.

Даты в `created_at_gte` / `created_at_lte` — ISO-8601 с временем, а не просто дата.

### 6.6 Ответы возвращаются целиком, без сокращения

Инструменты отдают ответ ЮKassa как есть, форматированным JSON. Ни обрезки, ни выжимки
полей здесь нет: `list_payments` с `limit: 100` вернёт сто полных объектов платежей.
Для обзорных задач берите меньший `limit` и сужайте период.

Отдельно у одиночных объектов (`create_payment`, `get_payment`, `capture_payment`,
`cancel_payment`, `save_payment_method`, `create_recurring_payment`, `create_sbp_payment`,
`create_split_payment`, `create_refund`, `get_refund`, `create_payout`, `get_payout`)
заполняется структурированный результат: `id`, `status`, `paid`, `amount` и
`confirmation_url`.

### 6.7 Продукты подключаются отдельно

Три возможности требуют подключения в кабинете и без него вернут отказ от API, а не от
сервера:

- **Выплаты** — плюс собственная пара ключей (раздел 3);
- **Сплитование платежей** — для `create_split_payment`;
- **Приём номера карты в выплате** (`destination_type: "bank_card"`) — требует
  сертификата PCI DSS. Без него используйте `payout_token` из виджета.

### 6.8 Форматы

| Что | Формат |
|---|---|
| Сумма | Строка `"4500"` / `"99.50"` (до двух знаков) либо положительное число |
| Валюта | Три заглавные буквы ISO-4217, по умолчанию `RUB` |
| Описание платежа | До 128 символов |
| Даты фильтра | ISO-8601 с временем |
| Телефон получателя СБП | `79XXXXXXXXX` |
| Количество в чеке | Положительное число (дробное допустимо) |

## 7. Частые ошибки

Ошибка ЮKassa приходит текстом вида `YooKassa [код]: описание (param: поле)`. Код и поле
берутся из ответа API; при `401` дописывается подсказка проверить `YOOKASSA_SHOP_ID` и
`YOOKASSA_SECRET_KEY`. Если тело ответа не JSON (страница прокси, ошибка шлюза), сервер не
пересказывает её целиком, а возвращает `YooKassa HTTP <код>: non-JSON error body` с
фрагментом до 200 символов.

| Что видно | Что это значит | Что делать |
|---|---|---|
| `Environment variables YOOKASSA_SHOP_ID and YOOKASSA_SECRET_KEY are required…` | Ключи не дошли до процесса; проявляется при первом вызове, а не при старте | Задать обе переменные в блоке `env` и перезапустить клиент |
| `YooKassa [invalid_credentials]…` / HTTP 401 | Пара `shopId` + ключ не принята: опечатка, ключ отозван, ключ от другого магазина | Сверить в кабинете: Настройки → Магазин и Интеграция → Ключи API |
| `YooKassa [invalid_request]: … (param: confirmation.return_url)` | Адрес возврата не принят API | Передать полный `https://`-адрес |
| `return_url is required when confirmation_type=redirect…` | Проверка сервера до обращения к API | Указать реальный `return_url` либо выбрать `embedded` / `qr` |
| `The sum of transfers (…) must equal the total payment amount (…)` | Доли сплита не сходятся с общей суммой; сверка в копейках | Пересчитать доли; проверить, не вычтена ли комиссия площадки дважды |
| `Provide either payout_token or destination_type/destination_value, not both…` | В выплате заданы оба способа указания получателя | Оставить один |
| `An SBP payout requires bank_id…` | Для выплаты через СБП мало телефона | Добавить `bank_id` банка-участника |
| `YooKassa [forbidden]` / HTTP 403 | Операция не разрешена для магазина: не подключён продукт (выплаты, сплит), нет PCI DSS для номера карты | Подключить продукт в кабинете; для карты — `payout_token` из виджета |
| `YooKassa [not_found]` / HTTP 404 | Идентификатор не найден. Частая причина — ключи тестового магазина при боевом идентификаторе платежа (и наоборот) | Проверить `get_shop_info` → поле `test` |
| `YooKassa [invalid_request]: … (param: amount)` | Сумма вне допустимого диапазона либо не соответствует операции (возврат больше платежа, `capture` больше удержанного) | Сверить с `get_payment` |
| `Amount as '100' or '100.50' (up to 2 decimals)` | Ошибка проверки параметров: сумма передана строкой другого вида | Привести к двум знакам после точки |
| `Currency as an uppercase ISO-4217 code (e.g. RUB, USD)` | Валюта строчными буквами или по-русски | Писать `RUB` |
| `YooKassa: request timeout (35s). Try again later.` | Три попытки по 35 секунд исчерпаны | Не повторять вслепую: проверить состояние через `get_payment` / `get_refund` / `get_payout` |
| `YooKassa: all retries exhausted` | Три попытки закончились повторяемой ошибкой (`429` или `5xx`) | То же: сначала проверить фактическое состояние |
| `YooKassa HTTP 5xx: non-JSON error body…` | Ответ пришёл не от API, а от промежуточного узла | Повторить позже; проверить сетевой контур |
| `HTTP transport requires MCP_AUTH_TOKEN…` | Попытка запустить HTTP-режим без токена | Задать `MCP_AUTH_TOKEN` длинной случайной строкой |
| `Unauthorized` (401 от `/mcp`) | Клиент не прислал или прислал неверный Bearer-токен | Сверить токен; заголовок — `Authorization: Bearer <токен>` |
| Выплата зависла в `pending` | Выплаты асинхронны; это штатное промежуточное состояние | Опрашивать `get_payout` либо подписаться на `payout.succeeded` / `payout.canceled` |

Журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. `YOOKASSA_DEBUG=1`
добавляет по строке на каждый запрос с методом, путём, кодом ответа, длительностью и
ключом идемпотентности — этого достаточно, чтобы отличить «повтор с тем же ключом» от
«новая операция». Секреты и тела запросов в журнал не попадают.
