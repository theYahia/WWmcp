# Руководство пользователя planfix-mcp

Пакет `@theyahia/planfix-mcp`, версия 1.2.0, 20 инструментов и 2 сценария-промпта.
Node.js 18 и выше. REST API Планфикса, точка входа
`https://<аккаунт>.planfix.com/rest/`.

## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ к рабочему пространству Планфикса: задачи, контакты и
компании, проекты, комментарии, сотрудники, справочники, кастомные поля, дата-теги, файлы.
Всё, ради чего обычно открывают вкладку с Планфиксом и настраивают фильтр, выполняется
репликой в чате: «что у меня горит на этой неделе», «заведи задачу на Петрова по проекту
„Сайт“», «покажи переписку по задаче 4821», «найди контакт по телефону».

Кому это нужно: руководителю, который каждое утро собирает статус по задачам; менеджеру,
который заводит задачи с чужих слов; интегратору, которому нужно понять структуру
аккаунта — какие есть справочники, кастомные поля и наборы статусов — не листая настройки.

Ответы приходят человекочитаемыми строками, а не сырым JSON: задача рендерится как
`#4821 | Название | статус: В работе (#3) | исполнители: Петров И. (#12) | дедлайн: …`.
Если форма ответа сервером не опознана, он честно отдаёт исходный JSON, а не выдумывает
структуру.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "planfix": {
      "command": "npx",
      "args": ["-y", "@theyahia/planfix-mcp"],
      "env": {
        "PLANFIX_ACCOUNT": "mycompany",
        "PLANFIX_API_KEY": "ваш_ключ"
      }
    }
  }
}
```

`PLANFIX_ACCOUNT` — это **субдомен**, то есть `mycompany` из `mycompany.planfix.com`, а не
полный адрес. Клиент читает конфигурацию при старте — после правки его нужно перезапустить.

### Claude Code

```
claude mcp add planfix -e PLANFIX_ACCOUNT=mycompany -e PLANFIX_API_KEY=ваш_ключ -- npx -y @theyahia/planfix-mcp
```

### Cursor / Windsurf / VS Code (Copilot)

Cursor и Windsurf принимают тот же блок `mcpServers` в `.cursor/mcp.json` или
`.windsurf/mcp.json`. У VS Code файл `.vscode/mcp.json`, и корневой ключ там — `servers`,
а не `mcpServers`; поля `command`, `args`, `env` те же. Файл рабочей области обычно
попадает в систему контроля версий — `PLANFIX_API_KEY` в нём хранить не следует.

### Режим Streamable HTTP

```bash
HTTP_PORT=3000 npx @theyahia/planfix-mcp --http
```

Режим включается флагом `--http` либо самой переменной `HTTP_PORT` (по умолчанию 3000).
Эндпоинты: `POST /mcp` (запросы; инициализация создаёт сессию), `GET /mcp` (поток SSE
существующей сессии), `DELETE /mcp` (завершение сессии), `GET /health` (`status`, `server`,
`version`, `uptime`, `memory_mb`, `tools`). Сессии различаются заголовком `mcp-session-id`;
`GET` и `DELETE` без известного идентификатора отклоняются с кодом 400. Кросс-доменные
браузерные вызовы по умолчанию запрещены — список разрешённых источников пуст.

Ключ берётся из окружения процесса и один на все сессии: все подключившиеся работают в
Планфиксе от имени одного и того же ключа. Собственной аутентификации у `/mcp` нет,
поэтому порт в недоверенной сети не публикуют.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PLANFIX_ACCOUNT` | да | Субдомен аккаунта (`mycompany`). Общего хоста у REST API нет, поэтому без него адрес не собрать |
| `PLANFIX_API_KEY` | да | Ключ REST API, уходит заголовком `Authorization: Bearer …` |
| `PLANFIX_TOKEN` | нет | Устаревшее имя для того же ключа; используется, если `PLANFIX_API_KEY` не задан |
| `PLANFIX_HOST` | нет | Хост для региональных установок, по умолчанию `planfix.com` (например, `planfix.ru`) |
| `HTTP_PORT` | нет | Порт HTTP-режима; заданная переменная сама включает режим |
| `MCP_DISABLE_SANITIZE` | нет | `true` отключает фильтрацию ответов от инъекций |

Отсутствие переменных обнаруживается **при первом вызове инструмента**, а не при старте:
клиент создаётся лениво. Сообщения об этом отдельные для субдомена и для ключа, и оба
называют, где взять значение.

## 3. Где взять ключ доступа

Ключ создаётся в кабинете Планфикса: **Управление аккаунтом → Доступ к API → REST API**
(этот путь сервер называет сам в сообщении об отсутствующем ключе). Авторизация —
заголовок `Authorization: Bearer <ключ>`, никакого OAuth и обновления токенов.

Второе обязательное значение — субдомен. Возьмите его из адреса своего кабинета:
у `https://mycompany.planfix.com` субдомен `mycompany`. Итоговый адрес запросов
складывается как `https://<PLANFIX_ACCOUNT>.<PLANFIX_HOST>/rest`, где `PLANFIX_HOST` по
умолчанию `planfix.com`. Для установки в зоне `.ru` задайте `PLANFIX_HOST=planfix.ru`.

**Права ключа определяют реальную границу возможного.** Ключ работает от имени
сотрудника, которому он выдан: видны те задачи, проекты и контакты, что видны этому
сотруднику. Инструмент, на который прав нет, не исчезнет из списка — он вернёт отказ от
API. Если требуется ограничить область работы агента, ограничивать нужно права сотрудника
в Планфиксе, а не формулировки запросов.

## 4. Инструменты по задачам

Все списочные инструменты работают по схеме `offset` (по умолчанию 0) и `pageSize` (по
умолчанию 100) и принимают `fields` — список полей через запятую. Значение `fields` по
умолчанию задано в коде для каждого типа объекта: без него Планфикс возвращает почти
пустые объекты с одним `id`.

### 4.1 Задачи

**`get_tasks`** — список задач. Все параметры необязательны: `offset`, `pageSize`,
`fields` (по умолчанию
`id,name,description,status,priority,assignees,project,startDateTime,endDateTime`),
`filterId` — идентификатор сохранённого в Планфиксе фильтра, `filters` — массив
произвольных фильтров.

Произвольный фильтр — это объект `{type, operator, value}`: `type` — числовой код типа
фильтра Планфикса, `operator` — строка вида `equal`, `gt`, `lt`, `value` — значение.
Несколько фильтров объединяются по «И». Коды типов берутся из документации Планфикса;
в самом сервере их справочника нет.

**`get_task`** — одна задача по `taskId`, необязательный `fields`. Выводит строку задачи и
отдельным блоком описание, если оно есть.

**`create_task`** — обязателен `name`. Необязательны `description`, `projectId`,
`assigneeId` (идентификатор сотрудника — искать через `list_users`) и `priority`.

> `priority` передаётся строкой как есть. **Допустимые значения не проверены против
> живого API** — так и записано в коде. Если Планфикс отклонит значение, приоритет проще
> выставить в интерфейсе.

**`update_task`** — обязателен `taskId`. Необязательны `name`, `description`, `status`
(числовой идентификатор статуса — искать через `list_directories` и
`list_directory_entries`) и `assigneeId`. Отправляются только переданные поля.

Планфикс на изменение отвечает **пустым телом** (200 — применено, 202 — поставлено в
очередь), поэтому подтверждение `✓ Задача #N обновлён.` собирается сервером из
переданного идентификатора, а не из ответа API. Проверять результат следует отдельным
`get_task`.

### 4.2 Комментарии

**`get_comments`** — переписка по задаче. Обязателен `taskId`; необязательны `offset`,
`pageSize`, `fields` (по умолчанию `id,dateTime,owner,description,isPinned,isHidden`).

**`add_comment`** — обязательны `taskId` и `body`. Текст уходит в поле `description`
запроса Планфикса.

### 4.3 Контакты и компании

**`get_contacts`** — список. `offset`, `pageSize`, `fields` (по умолчанию
`id,name,midname,lastname,email,phones,company`) и `filterId` — идентификатор сохранённого
фильтра контактов.

**`get_contact`** — один контакт по `contactId`.

**`create_contact`** — обязателен `name`. Необязательны `email`, `phone` (уходит массивом
телефонов), `companyId` (привязка к компании) и `isCompany` — при `true` создаётся
**компания**, а не персона.

**`update_contact`** — обязателен `contactId`; необязательны `name`, `email`, `phone`.
Ответ пустой, подтверждение формируется по идентификатору — как и у задач.

### 4.4 Проекты

**`get_projects`** — список; `offset`, `pageSize`, `fields` (по умолчанию
`id,name,description,status`). Сохранённых фильтров у проектов нет: параметр `filterId`
поддерживается только контактами и задачами, и сервер намеренно его не отправляет.

**`get_project`** — один проект по `projectId`, со списком и описанием.

### 4.5 Сотрудники

**`list_users`** — список сотрудников; `offset`, `pageSize`, `fields` (по умолчанию
`id,name,midname,lastname,email,position`). Это способ найти числовой `assigneeId` по
имени **до** вызова `create_task` или `update_task`.

**`get_user`** — один сотрудник по `userId`.

### 4.6 Структура аккаунта: справочники, поля, теги

**`list_directories`** — справочники Планфикса. В них же хранятся наборы статусов задач,
поэтому именно отсюда начинают, когда нужно узнать числовой идентификатор статуса.

**`list_directory_entries`** — записи конкретного справочника по `directoryId`
(`offset`, `pageSize`). Например, варианты статусов.

**`list_custom_fields`** — кастомные поля. Обязателен `objectType` — одно из `task`,
`contact`, `project`, `user`, `main`. Отдаёт идентификаторы, названия и типы полей.

**`list_datatags`** — дата-теги аккаунта; `offset`, `pageSize`, `fields`.

### 4.7 Файлы

**`upload_file_from_url`** — загрузка файла **по прямой ссылке**: обязателен `url`,
необязательно `name` (если не задано, имя берётся из ссылки). Прямой загрузки файла с
диска (multipart) в сервере нет.

**`get_file`** — метаданные файла по `fileId`: идентификатор, имя, размер.

### 4.8 Сценарии-промпты

Кроме инструментов сервер регистрирует два промпта: `skill-my-tasks` (задачи с дедлайном
на сегодня и просроченные) и `skill-create-task` с параметром `description` (проводит
через выбор проекта и создание задачи). В счёт 20 инструментов они не входят.

## 5. Готовые сценарии

**1. «Что у меня просрочено?»**
Промпт `skill-my-tasks` либо напрямую `get_tasks` (`pageSize: 100`) с последующей
фильтрацией по `endDateTime` на стороне модели. Серверного фильтра «просроченные» нет —
для регулярной работы удобнее один раз сохранить фильтр в Планфиксе и вызывать
`get_tasks` с его `filterId`.

**2. «Заведи задачу „Подготовить отчёт за март“ на Петрова в проекте „Сайт“.»**
`get_projects` (найти идентификатор проекта) → `list_users` (найти идентификатор
Петрова) → `create_task` (`name`, `description`, `projectId`, `assigneeId`). В ответ
придёт `✓ Задача создана, ID: N`.

**3. «Покажи переписку по задаче 4821 и добавь комментарий.»**
`get_comments` (`taskId: 4821`) → `add_comment` (`taskId: 4821`, `body`). Комментарии
листаются `offset` / `pageSize`; если вернулось ровно `pageSize` записей, сервер сам
подсказывает следующий `offset`.

**4. «Переведи задачу 4821 в статус „Выполнена“.»**
`list_directories` (найти справочник со статусами) → `list_directory_entries`
(`directoryId`, взять числовой идентификатор нужного статуса) → `update_task`
(`taskId: 4821`, `status: <идентификатор>`) → `get_task` для проверки: ответ на
обновление приходит пустым.

**5. «Найди контакт „Иванов“ и заведи компанию.»**
`get_contacts` (пролистать `offset` / `pageSize`; серверного поиска по подстроке нет —
либо сохранённый фильтр через `filterId`, либо просмотр страниц) → `create_contact`
(`name`, `isCompany: true`) → `update_contact` для привязки телефона и почты.

**6. «Какие кастомные поля есть у задач?»**
`list_custom_fields` (`objectType: "task"`). Тот же вызов с `contact`, `project`, `user`
или `main` даёт поля остальных объектов. Это первый шаг при разборе чужого аккаунта.

**7. «Приложи к задаче документ по ссылке.»**
`upload_file_from_url` (`url`, `name`) → из ответа взять идентификатор → `get_file` для
проверки имени и размера. Загрузка файла с локального диска этим сервером не
поддерживается — только по ссылке, доступной Планфиксу.

**8. «Собери сводку по проекту: задачи и кто на них.»**
`get_project` (`projectId`) → `get_tasks` (`filters: [{type: …, operator: "equal",
value: <projectId>}]` либо `filterId` сохранённого фильтра) → при необходимости
`list_users` для расшифровки исполнителей. Числовые коды `type` берутся из документации
Планфикса.

## 6. Ограничения и подводные камни

### 6.1 Ошибка может прийти с кодом 200

Планфикс отвечает `HTTP 200` и на часть логических отказов: в теле приходит конверт
`{"result": "fail", "code": N, "error": "…"}`. Сервер разбирает такой конверт и
превращает его в ошибку `Planfix API error <код>: <текст>` — успехом он его не считает.

Отдельно обрабатывается **код 22 — логическое превышение лимита запросов**. Он считается
повторяемым: до трёх попыток с задержкой `1000 × 2^(попытка−1)` мс, но не дольше
8 секунд. Все прочие коды отказа повторно не отправляются — они означают, что запрос
неверен по существу.

### 6.2 Повторы вложенные, и это стоит помнить

Транспортные сбои (`429`, `5xx`, таймаут) обрабатывает общий HTTP-клиент: до трёх попыток
с той же экспоненциальной задержкой, таймаут одного запроса — 15 секунд. Поверх этого
работают повторы конвертных ошибок с кодом 22 — тоже до трёх. В худшем случае один вызов
инструмента даёт до девяти сетевых обращений и занимает заметное время. Это отмечено
комментарием в коде как осознанный размен.

Важное следствие: **изменяющие вызовы транспортом не повторяются.** Все инструменты
записи (`create_task`, `update_task`, `create_contact`, `update_contact`, `add_comment`,
`upload_file_from_url`) отправляются методом POST, и при таймауте или `5xx` повтор не
выполняется — к тексту ошибки дописывается предупреждение проверить, не создан ли объект.
Слепой повтор создал бы вторую задачу или второй комментарий.

### 6.3 Ответы на запись приходят пустыми

`update_task` и `update_contact` получают от Планфикса пустое тело: код 200 означает
«применено», 202 — «поставлено в очередь». Поэтому подтверждение
`✓ Задача #N обновлён.` — это сообщение сервера, а не подтверждение API. Признать
изменение состоявшимся можно только повторным чтением (`get_task`, `get_contact`).

Создание отвечает содержательно: из ответа берётся `id`, и сообщение выглядит как
`✓ Задача создана, ID: 4821`.

### 6.4 Пагинация без счётчика записей

Общего числа записей Планфикс в этих ответах не даёт. Признак «есть ещё» —
косвенный: если вернулось ровно `pageSize` элементов, сервер дописывает строку
`…возможно есть ещё — запросите offset=<следующий>`. Полная выгрузка — цикл, пока
количество вернувшихся записей меньше `pageSize`.

`pageSize` в схемах не ограничен сверху: верхний предел задаёт сам Планфикс, и слишком
большое значение он отклонит своим конвертом ошибки.

### 6.5 Поиска по подстроке у списков нет

Ни один списочный инструмент не принимает строку поиска. Отбор делается двумя способами:
`filterId` — сохранённый в интерфейсе Планфикса фильтр (доступен у задач и контактов), и
`filters` — массив произвольных фильтров с числовыми кодами типов (только у задач).
У проектов, сотрудников, справочников и дата-тегов не поддерживается ни то, ни другое:
их листают страницами.

### 6.6 Идентификаторы исполнителей имеют префикс

Сервер принимает `assigneeId` числом, но в запрос Планфикса он уходит в виде
`{"assignees": {"users": [{"id": "user:12"}]}}` — со строковым префиксом `user:`. Это
сделано за вас; знать об этом нужно только при чтении журнала или при сверке с
документацией API.

Статус в `update_task` — напротив, чистое число: `{"status": {"id": N}}`. Взять его можно
из записей справочника статусов.

### 6.7 Объём ответа и фильтрация текста

Ответ длиннее 50 000 символов обрезается с пометкой о срезке — при выгрузке сотен задач
уменьшайте `pageSize` и идите страницами. Тексты из ответов (названия, описания,
комментарии) проходят фильтр: конструкции вида «игнорируй предыдущие инструкции» и теги
`<system>` заменяются на `[filtered]`. Отключается переменной
`MCP_DISABLE_SANITIZE=true`.

Просить меньше полей через `fields` — самый дешёвый способ уменьшить ответ: значение по
умолчанию включает описание задачи, а оно бывает длинным.

## 7. Частые ошибки

| Что видно | Что это значит | Что делать |
|---|---|---|
| `Не задан PLANFIX_ACCOUNT — субдомен аккаунта…` | Субдомен не дошёл до процесса; проявляется при первом вызове инструмента, а не при старте | Задать `PLANFIX_ACCOUNT` (только субдомен, без `https://` и без домена) и перезапустить клиент |
| `Не задан ключ авторизации. Установите PLANFIX_API_KEY…` | Нет ключа | Создать ключ: Управление аккаунтом → Доступ к API → REST API |
| `Planfix API error 22: …` | Логический лимит запросов Планфикса. Три попытки уже израсходованы | Пауза; уменьшить `pageSize` и частоту вызовов |
| `Planfix API error <код>: <текст>` (иной код) | Отказ по существу: неверный идентификатор, недопустимое значение поля, нет прав на объект | Прочитать текст — он приходит от Планфикса как есть; проверить идентификаторы через соответствующий `list_*` |
| `Planfix API: все попытки исчерпаны` | Три попытки подряд закончились кодом 22 | Продолжать бессмысленно; вернуться позже |
| `Отказ в доступе (HTTP 401)` | Ключ не принят: опечатка, ключ отозван, ключ от другого аккаунта | Сверить ключ и `PLANFIX_ACCOUNT` — ключ одного аккаунта в другом не работает |
| `Отказ в доступе (HTTP 403)` | Ключ верен, но у сотрудника нет прав на объект или операцию | Выдать права сотруднику в Планфиксе; область работы задаётся правами, а не параметрами |
| `Ресурс не найден` (HTTP 404) | Нет объекта с таким идентификатором либо неверный субдомен в адресе | Проверить идентификатор через `get_tasks` / `get_contacts` / `list_users`; проверить `PLANFIX_ACCOUNT` |
| `Rate limit. Повторите через Nс` (HTTP 429) | Транспортный лимит; повтор уже выполнялся автоматически | Пауза; снизить частоту |
| `Таймаут запроса` | Ответ не пришёл за 15 секунд | Для чтения — повторить с меньшим `pageSize`; для записи — сначала проверить, не создан ли объект |
| `Повтор не выполнен автоматически, потому что операция изменяет данные…` | Сбой на записи, результат неизвестен | Проверить `get_tasks` / `get_comments`, прежде чем повторять |
| Ответ — сырой JSON вместо строки задачи | Форма ответа не опознана форматтером (нестандартный набор `fields`, незнакомая структура) | Это не ошибка: данные не потеряны. Вернуть `fields` к значению по умолчанию, если нужен привычный вид |
| `Задачи: ничего не найдено.` | Запрос отработал, совпадений нет | Проверить `filterId` и `filters`; убедиться, что у сотрудника есть доступ к этим задачам |
| `✓ Задача #N обновлён.`, но изменений не видно | Подтверждение формируется сервером, а не Планфиксом (раздел 6.3): код 202 означает очередь | Перечитать `get_task` через несколько секунд |
| Приоритет не применился | Допустимые значения `priority` в коде не проверены против живого API | Выставить приоритет в интерфейсе Планфикса |

Журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. Туда же пишутся
предупреждения о повторах: `Planfix rate limit (code 22), backing off` — конвертный
лимит, `Retryable error, backing off` — транспортный.
