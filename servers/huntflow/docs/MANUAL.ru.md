# Руководство пользователя huntflow-mcp

Пакет `@theyahia/huntflow-mcp`, версия 1.2.0, 14 инструментов. Node.js 18 и выше.
API Huntflow версии 2, точка входа `https://api.huntflow.ru/v2`.

## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ на чтение к системе подбора Huntflow: вакансии, кандидаты,
их резюме, этапы воронки, сотрудники аккаунта и справочники — источники, причины отказа,
подразделения, теги. Задача, которую это снимает: «сколько кандидатов на вакансии
разработчика и на каких они этапах», «найди кандидата по телефону», «покажи резюме
Иванова», «кто из рекрутеров ведёт эту вакансию».

Кому это нужно: рекрутеру, который каждый день собирает статус по воронке; нанимающему
менеджеру, которому нужен срез по своим вакансиям без входа в систему; аналитику,
сверяющему данные подбора с внешней отчётностью.

**Сервер работает только на чтение.** Инструментов создания, изменения и удаления в нём
нет: нельзя завести кандидата, перевести его по этапу или отклонить. Это ограничение
набора, а не прав токена.

Списочные инструменты возвращают **курированный** набор полей — ровно те, что нужны для
ответа, а не полный документ Huntflow. Полный ответ доступен параметром `raw: true`.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "huntflow": {
      "command": "npx",
      "args": ["-y", "@theyahia/huntflow-mcp"],
      "env": {
        "HUNTFLOW_TOKEN": "ваш_access_token",
        "HUNTFLOW_REFRESH_TOKEN": "ваш_refresh_token"
      }
    }
  }
}
```

Задавайте **обе** переменные: без токена обновления сервер проработает только до
истечения токена доступа. Клиент читает конфигурацию при старте — после правки его нужно
перезапустить.

### Claude Code

```
claude mcp add huntflow -e HUNTFLOW_TOKEN=ваш_токен -e HUNTFLOW_REFRESH_TOKEN=refresh -- npx -y @theyahia/huntflow-mcp
```

### Cursor / Windsurf / VS Code (Copilot)

Cursor и Windsurf принимают тот же блок `mcpServers` в `.cursor/mcp.json` или
`.windsurf/mcp.json`. У VS Code файл `.vscode/mcp.json`, и корневой ключ там — `servers`,
а не `mcpServers`; поля `command`, `args`, `env` те же. Файл рабочей области обычно
попадает в систему контроля версий — токены в нём хранить не следует.

### Режим Streamable HTTP

```bash
HUNTFLOW_TOKEN=ваш_токен npx @theyahia/huntflow-mcp --http
```

Транспорт stateless: `POST /mcp` и `GET /health` (`status`, `version`, `tools`).
Привязка по умолчанию — `127.0.0.1:3000`, меняется переменными `HUNTFLOW_HTTP_HOST` и
`PORT`. Защита от DNS-rebinding включена всегда: `Host` проверяется по
`HUNTFLOW_ALLOWED_HOSTS` (по умолчанию `127.0.0.1:<порт>,localhost:<порт>`).

В отличие от большинства серверов монорепозитория, здесь есть **необязательная защита
эндпоинта**: если задан `HUNTFLOW_HTTP_SECRET`, запросы к `/mcp` без заголовка
`Authorization: Bearer <секрет>` получают `401`. Задавать его следует всегда, когда порт
доступен кому-то ещё: данные кандидатов — персональные.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `HUNTFLOW_TOKEN` | да | Токен доступа |
| `HUNTFLOW_REFRESH_TOKEN` | нет | Токен обновления; включает автоматическое обновление при `401` |
| `HUNTFLOW_TOKEN_FILE` | нет | Файл для хранения ротированной пары, по умолчанию `~/.huntflow-mcp/token.json` |
| `HUNTFLOW_BASE_URL` | нет | По умолчанию `https://api.huntflow.ru/v2` |
| `HUNTFLOW_USER_AGENT` | нет | Значение `User-Agent`; API **требует** его, значение по умолчанию задано |
| `HUNTFLOW_TIMEOUT_MS` | нет | Таймаут запроса в миллисекундах, по умолчанию 10 000 |
| `HUNTFLOW_BACKOFF_MS` | нет | База задержки повторов, по умолчанию 1000 |
| `HUNTFLOW_DISABLE_RATELIMIT` | нет | `1` отключает клиентское ограничение 10 запросов в секунду |
| `PORT`, `HUNTFLOW_HTTP_HOST` | нет | Адрес HTTP-режима |
| `HUNTFLOW_HTTP_SECRET` | нет | Общий секрет для `/mcp` |
| `HUNTFLOW_ALLOWED_HOSTS` | нет | Допустимые `Host` через запятую |

Отсутствие токена обнаруживается при первом вызове инструмента, а не при старте.

## 3. Где взять токены доступа

Пара токенов выдаётся в интерфейсе Huntflow: **Настройки → вкладка «API-токены»**
(этот путь сервер называет сам в сообщении об отсутствующем токене). Выдаются два
значения: **токен доступа** (живёт около 7 суток) и **токен обновления** (около
14 суток).

Как сервер с ними обращается:

1. При первом запросе состояние берётся из файла `HUNTFLOW_TOKEN_FILE`, а если файла нет
   — из переменных окружения. **Файл имеет приоритет**: в нём лежит последняя пара,
   полученная после обновления.
2. При `401` выполняется `POST /token/refresh`. Новая пара сохраняется в файл с правами
   `0600` и переживает перезапуск процесса.
3. Если обновление не помогло, а в переменных окружения лежит **другая** пара (вы
   перевыпустили токены и обновили конфигурацию), сервер переключается на неё и пробует
   ещё раз.
4. Одновременные обновления объединяются в одно.

Практический вывод: задавайте обе переменные. Только с `HUNTFLOW_TOKEN` сервер
проработает до истечения токена доступа — около недели, — а затем начнёт отвечать `401`,
и токен придётся выпускать заново.

**Права токена определяют границу видимого.** Токен привязан к пользователю Huntflow:
видны те вакансии и кандидаты, что видны ему. Фильтр `mine: true` у списка вакансий тоже
считается от владельца токена, а не от того, кто разговаривает с агентом.

## 4. Инструменты по задачам

**Почти все инструменты требуют `account_id`** — идентификатор аккаунта Huntflow. Он
берётся из `list_accounts`, и это обязательный первый шаг.

Списочные инструменты работают по схеме `page` (с 1) и `count` (1–100, по умолчанию 30) и
принимают `raw` — вернуть полный ответ без курирования. В курированном виде сохраняются
метаданные пагинации: `page`, `count`, `total`, `total_items`, `next_page_cursor`.

Числовые параметры принимаются и строками: значение приводится к числу до запроса.

### 4.1 Аккаунт и структура подбора

**`list_accounts`** — доступные аккаунты. Единственный инструмент без `account_id`.
Курируемые поля: `id`, `name`, `nick`, `member_type`.

**`list_stages`** — этапы воронки подбора (статусы вакансий). Обязателен `account_id`.
Поля: `id`, `name`, `type`, `order`, `removed`. Числовые идентификаторы отсюда идут в
фильтр `status` у поиска кандидатов.

**`list_coworkers`** — сотрудники и рекрутеры аккаунта; `page`, `count`. Поля: `id`,
`name`, `type`, `email`.

### 4.2 Справочники

Четыре инструмента с одинаковой схемой — обязательный `account_id` и необязательный
`raw`. Все возвращают поля `id`, `name`, `type`, `foreign`, `order`.

| Инструмент | Что отдаёт |
|---|---|
| `list_sources` | Источники кандидатов |
| `list_rejection_reasons` | Причины отказа |
| `list_divisions` | Подразделения |
| `list_tags` | Теги |

Нужны они для расшифровки числовых идентификаторов, которые приходят в карточках
кандидатов и вакансий, и для подстановки в фильтр `tag`.

### 4.3 Вакансии

**`list_vacancies`** — обязателен `account_id`. Необязательные: `opened` (по умолчанию
`true` — только открытые), `state` (`OPEN`, `CLOSED`, `HOLD` — альтернатива `opened`),
`mine` (только вакансии, где владелец токена участник), `page`, `count`, `raw`.
Курируемые поля: `id`, `position`, `company`, `money`, `state`, `created`, `priority`.

**`get_vacancy`** — полная карточка вакансии по `account_id` и `vacancy_id`. Ответ
отдаётся **без курирования**, целиком.

### 4.4 Кандидаты

**`search_applicants`** — поиск. Обязателен `account_id`; необязательные: `q` (строка —
ищет по имени, почте и телефону), `vacancy` (идентификатор вакансии), `status`
(идентификатор этапа из `list_stages`), `tag` (идентификатор тега из `list_tags`),
`page`, `count`, `raw`. Курируемые поля: `id`, `first_name`, `last_name`, `middle_name`,
`email`, `phone`, `position`, `created`.

**`list_vacancy_applicants`** — кандидаты конкретной вакансии. Обязательны `account_id` и
`vacancy_id`; необязательные `status`, `page`, `count`, `raw`. Это тот же поиск с
предустановленным фильтром по вакансии — отдельного эндпоинта у API нет.

**`get_applicant`** — полная карточка кандидата по `account_id` и `applicant_id`. Без
курирования.

### 4.5 Резюме

**`get_applicant_resumes`** — список резюме кандидата. Обязательны `account_id` и
`applicant_id`. Курируемые поля: `id`, `auth_type`, `account_source`, `created`,
`updated`.

Технически инструмент запрашивает **карточку кандидата целиком** и достаёт из неё поле
`external`: отдельного эндпоинта «список резюме» в API версии 2 нет. Это значит, что один
вызов стоит столько же, сколько `get_applicant`.

**`get_resume`** — полное тело резюме. Обязательны `account_id`, `applicant_id` и
`external_id` — идентификатор из `get_applicant_resumes`. Без курирования; это самый
объёмный ответ в наборе.

## 5. Готовые сценарии

**1. «С чего начать?»**
`list_accounts`. Без `account_id` не работает ни один другой инструмент; его берут один
раз и подставляют дальше.

**2. «Какие вакансии открыты и сколько на них кандидатов?»**
`list_vacancies` (`account_id`, `opened: true`) → по каждой интересующей
`list_vacancy_applicants` (`vacancy_id`, `count: 1`) и взять `total` из ответа: полный
список кандидатов ради счётчика тянуть не нужно.

**3. «Покажи воронку по вакансии разработчика.»**
`list_stages` (`account_id`, взять идентификаторы этапов) → `list_vacancy_applicants`
(`vacancy_id`, `status: <идентификатор этапа>`) для каждого этапа. Один вызов на этап;
названия этапов на экране и их числовые идентификаторы — разные вещи.

**4. «Найди кандидата по телефону.»**
`search_applicants` (`account_id`, `q: "+79001234567"`). Поле `q` ищет по имени, почте и
телефону одновременно.

**5. «Дай резюме Иванова.»**
`search_applicants` (`q: "Иванов"`, взять `applicant_id`) → `get_applicant_resumes`
(`applicant_id`) → `get_resume` (`external_id` нужного резюме). Последний вызов
возвращает полный текст — берите его только когда резюме действительно нужно целиком.

**6. «Кто ведёт наши вакансии?»**
`list_coworkers` (`account_id`, `count: 100`). Для вакансий, где участник — владелец
токена: `list_vacancies` (`mine: true`).

**7. «По каким причинам мы отказываем?»**
`list_rejection_reasons` (`account_id`). Справочник нужен, чтобы расшифровать числовые
идентификаторы в карточках кандидатов.

**8. «Выгрузи всех кандидатов вакансии.»**
`list_vacancy_applicants` (`vacancy_id`, `count: 100`, `page: 1`), дальше листать `page`,
пока сумма выданных не сравняется с `total`. Максимум — сто записей на страницу.

**9. «Мне нужны все поля кандидата, а не выжимка.»**
`get_applicant` (одна карточка целиком) либо любой списочный инструмент с `raw: true`.
Второй вариант применяйте с малым `count` — объём вырастает в разы.

## 6. Ограничения и подводные камни

### 6.1 Только чтение

В наборе нет ни одного изменяющего инструмента. Нельзя добавить кандидата, приложить
резюме, перевести по этапу, поставить тег, отклонить или нанять. Всё это делается в
интерфейсе Huntflow или другим интеграционным каналом.

Соответственно, все ограничения этого раздела касаются чтения: объёма выдачи, повторов и
лимитов.

### 6.2 Токены живут неделями и ротируются

Токен доступа Huntflow действует около 7 суток, токен обновления — около 14. Сервер
обновляет пару сам и сохраняет её в `~/.huntflow-mcp/token.json` (права `0600`), поэтому
перезапуск не сбрасывает состояние.

Два практических следствия:

- **Файл важнее переменных окружения.** Если файл существует, пара берётся из него. При
  перевыпуске токенов вручную обновите переменные окружения — сервер обнаружит, что в
  окружении лежит другая пара, и переключится на неё после неудачного обновления.
- **Файл содержит действующие учётные данные.** Его нельзя копировать вместе с домашним
  каталогом и класть в резервные копии без шифрования.

Если задан только `HUNTFLOW_TOKEN`, обновление невозможно: примерно через неделю все
инструменты начнут отвечать `401`.

### 6.3 Ограничитель частоты — 10 запросов в секунду

Клиент несёт встроенное ограничение по схеме «маркерное ведро»: 10 запросов в секунду —
это документированный лимит Huntflow на токен. При превышении вызов не отклоняется, а
ждёт своей очереди.

Отключается `HUNTFLOW_DISABLE_RATELIMIT=1`, но делать этого не стоит: без него API
ответит `429`, а обходить лимит поставщика клиентской настройкой бессмысленно.

### 6.4 Повторы и заголовок `User-Agent`

Повторяются `429`, `5xx` и сетевые сбои (`ECONNRESET`, `ETIMEDOUT`, `EAI_AGAIN`,
`ECONNREFUSED`, `EPIPE`, `ENOTFOUND`, таймаут): до трёх попыток, задержка
`HUNTFLOW_BACKOFF_MS × 2^(попытка−1)` мс, но не дольше 8 секунд, со случайным разбросом
50–100 % от базы. Если сервер прислал заголовок `Retry-After`, берётся большее из двух
значений. Обновление токена в счёт попыток не идёт.

Так как все инструменты только читают, автоматический повтор здесь безопасен и никаких
дублей не создаёт.

Отдельно: **API требует заголовок `User-Agent`.** Без него приходит `400 bad_user_agent`.
Значение по умолчанию сервер подставляет сам; переопределять его через
`HUNTFLOW_USER_AGENT` нужно только если Huntflow попросил указать имя вашей интеграции.

### 6.5 Курирование полей и параметр `raw`

Списочные инструменты оставляют в записях фиксированный набор ключей:

| Сущность | Поля |
|---|---|
| Вакансия | `id`, `position`, `company`, `money`, `state`, `created`, `priority` |
| Кандидат | `id`, `first_name`, `last_name`, `middle_name`, `email`, `phone`, `position`, `created` |
| Этап | `id`, `name`, `type`, `order`, `removed` |
| Аккаунт | `id`, `name`, `nick`, `member_type` |
| Резюме | `id`, `auth_type`, `account_source`, `created`, `updated` |
| Сотрудник | `id`, `name`, `type`, `email` |
| Справочник | `id`, `name`, `type`, `foreign`, `order` |

Всё остальное — комментарии, история этапов, вложения, произвольные поля — в курированный
ответ **не попадает**. Если нужного поля нет, есть два пути: `raw: true` у списка либо
`get_applicant` / `get_vacancy`, которые и так отдают карточку целиком.

Одиночные инструменты (`get_applicant`, `get_vacancy`, `get_resume`) параметра `raw` не
имеют — они всегда полные.

### 6.6 Пагинация ограничена сотней записей

`count` — максимум 100, `page` начинается с 1. Полная выгрузка — цикл по страницам с
опорой на `total` из ответа. Помните про ограничитель в 10 запросов в секунду: выгрузка
тысячи кандидатов займёт не меньше десяти запросов и будет идти заметное время.

Ответ длиннее 50 000 символов обрезается с пометкой о срезке — это ещё один довод
не поднимать `count` до предела вместе с `raw: true`.

### 6.7 Персональные данные

Инструменты возвращают имена, телефоны, электронные адреса и тексты резюме — то есть
персональные данные кандидатов. Три следствия для развёртывания:

- в HTTP-режиме задавайте `HUNTFLOW_HTTP_SECRET` и не публикуйте порт;
- курированный вывод (без `raw`) отдаёт модели меньше данных — это разумная настройка по
  умолчанию, а не только экономия;
- `get_resume` выгружает резюме целиком: вызывайте его точечно, а не по всему списку.

### 6.8 Два инструмента устроены не так, как выглядят

- **`list_vacancy_applicants`** — это `search_applicants` с фильтром по вакансии.
  Отдельного эндпоинта нет, и никаких дополнительных полей связи «кандидат — вакансия» он
  не добавляет.
- **`get_applicant_resumes`** запрашивает карточку кандидата целиком и достаёт из неё
  поле `external`. Стоимость вызова равна `get_applicant`; если карточка уже прочитана,
  список резюме в ней уже есть.

## 7. Частые ошибки

| Что видно | Что это значит | Что делать |
|---|---|---|
| `HUNTFLOW_TOKEN обязателен. Получите в настройках HuntFlow: Настройки → API-токены.` | Токен не дошёл до процесса; проявляется при первом вызове инструмента | Задать `HUNTFLOW_TOKEN` (и `HUNTFLOW_REFRESH_TOKEN`) в блоке `env`, перезапустить клиент |
| `HuntFlow 401: … Проверьте/перевыпустите токен (Настройки → API-токены).` | Обновление не помогло: истёк и токен обновления, либо пара отозвана | Выпустить новую пару и обновить обе переменные окружения |
| `HuntFlow HTTP 400: bad_user_agent` | Запрос ушёл без `User-Agent` | Не переопределять `HUNTFLOW_USER_AGENT` пустой строкой; значение по умолчанию корректно |
| `HuntFlow HTTP 403: …` | Токен верен, но у пользователя нет доступа к этому аккаунту, вакансии или кандидату | Проверить `account_id` через `list_accounts`; права выдаются в Huntflow |
| `HuntFlow HTTP 404: …` | Нет объекта с таким идентификатором либо перепутан порядок аргументов | Сверить `account_id`, `vacancy_id`, `applicant_id`, `external_id` — все четыре числовые и легко меняются местами |
| `HuntFlow HTTP 422: …` | Параметр не принят: например, `count` больше 100 или неизвестное значение `state` | Привести к допустимым: `count` 1–100, `state` — `OPEN`, `CLOSED` или `HOLD` |
| `HuntFlow HTTP 429: …` | Лимит выбран, несмотря на клиентское ограничение; три попытки израсходованы | Пауза; не отключать `HUNTFLOW_DISABLE_RATELIMIT` |
| `HuntFlow HTTP 5xx: …` | Сбой на стороне Huntflow, три попытки израсходованы | Повторить позже |
| `HuntFlow: таймаут запроса (10000ms)` | Ответ не пришёл вовремя | Уменьшить `count`, поднять `HUNTFLOW_TIMEOUT_MS` |
| `HuntFlow: сетевая ошибка — …` | Соединение не установилось; повторы исчерпаны | Проверить сеть и доступность `api.huntflow.ru` |
| `не удалось сохранить токен в <путь>` (в журнале) | Файл состояния не записался: нет прав на каталог | Задать `HUNTFLOW_TOKEN_FILE` с доступным путём; иначе после перезапуска обновление начнётся заново |
| `unauthorized` (401 от `/mcp`) | HTTP-режим: задан `HUNTFLOW_HTTP_SECRET`, а клиент прислал не тот заголовок | Передавать `Authorization: Bearer <секрет>` |
| Пустой `items` в ответе | Запрос отработал, совпадений нет | Проверить `opened` (по умолчанию `true` — закрытые вакансии не попадут), `status`, `tag`; убедиться в доступе пользователя |
| В ответе нет нужного поля | Список курируется фиксированным набором ключей | Раздел 6.5: `raw: true` либо `get_applicant` / `get_vacancy` |

Журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. Туда же пишется
строка запуска HTTP-режима с признаком, защищён ли эндпоинт секретом.
