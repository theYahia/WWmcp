## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ к содержимому сайтов, собранных в конструкторе Tilda: список
проектов, настройки проекта, список страниц и сам код страниц — HTML, CSS, JS. Отсюда две
рабочие задачи. Первая — читать сайт: попросить агента разобрать структуру страницы, вычитать
тексты, сверить заголовки и мета-описания, собрать перечень страниц с датами публикации.
Вторая — вынести сайт с хостинга Tilda: инструменты экспорта отдают страницу с
локализованными ссылками на ассеты, пригодную для размещения на своём сервере или вставки в
чужую CMS.

Сервер работает **только на чтение**. Ни создать, ни изменить, ни опубликовать страницу через
него нельзя — таких методов нет в самом Tilda API. Все семь методов API покрыты, и все семь
доступны как инструменты.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "tilda": {
      "command": "npx",
      "args": ["-y", "@theyahia/tilda-mcp"],
      "env": {
        "TILDA_PUBLIC_KEY": "публичный-ключ",
        "TILDA_SECRET_KEY": "секретный-ключ"
      }
    }
  }
}
```

Клиент читает конфигурацию при старте — после правки его нужно перезапустить.

### Claude Code

```bash
claude mcp add tilda -e TILDA_PUBLIC_KEY=публичный-ключ -e TILDA_SECRET_KEY=секретный-ключ -- npx -y @theyahia/tilda-mcp
```

### Cursor / Windsurf

Тот же блок `mcpServers` в настройках MCP среды.

### VS Code (Copilot)

Файл `.vscode/mcp.json`, корневой ключ — `servers`:

```json
{
  "servers": {
    "tilda": {
      "command": "npx",
      "args": ["-y", "@theyahia/tilda-mcp"],
      "env": {
        "TILDA_PUBLIC_KEY": "публичный-ключ",
        "TILDA_SECRET_KEY": "секретный-ключ"
      }
    }
  }
}
```

Файл лежит в рабочей области и обычно попадает в систему контроля версий — секретный ключ в
нём хранить не следует.

### Режим Streamable HTTP

```bash
TILDA_PUBLIC_KEY=xxx TILDA_SECRET_KEY=yyy npx @theyahia/tilda-mcp --http --port 3001
```

Порт задаётся флагом `--port`; без него используется 3001. В отличие от большинства серверов
монорепозитория, переменная `HTTP_PORT` здесь не читается.

| Метод и путь | Поведение |
|---|---|
| `POST /mcp` | Запросы MCP. Режим **stateless**: на каждый запрос создаётся новый сервер и транспорт, по закрытии ответа они уничтожаются |
| любой другой метод на `/mcp` | `405` с заголовком `Allow: POST, OPTIONS` |
| `GET /health` | `{"status":"ok","tools":7}` |
| `OPTIONS` | `204`, CORS открыт для всех источников (`Access-Control-Allow-Origin: *`) |
| прочие пути | `404` |

Тело запроса больше 1 000 000 байт отклоняется с кодом `413`, невалидный JSON — с `400`.
Собственной аутентификации у `/mcp` нет: доступ к порту равносилен доступу к вашим ключам
Tilda. CORS здесь открыт полностью, поэтому порт нельзя публиковать без обратного прокси
со своей аутентификацией.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `TILDA_PUBLIC_KEY` | да | Публичный ключ API |
| `TILDA_SECRET_KEY` | да | Секретный ключ API |

Обе проверяются не при старте процесса, а при первом вызове любого инструмента: без них
запрос завершается ошибкой `TILDA_PUBLIC_KEY и TILDA_SECRET_KEY не заданы`.

## 3. Где взять ключи доступа

Ключи выдаются в настройках аккаунта Tilda: `https://tilda.cc/identity/apikeys/`. Там же
видно, для каких проектов ключи действуют. Нужны оба значения — публичное и секретное.

Особенность самого Tilda API: ключи передаются **query-параметрами** `publickey` и
`secretkey` в каждом запросе, а не заголовком. Это не решение сервера, а требование API.
Практические следствия описаны в разделе 6.4.

## 4. Инструменты по задачам

Все инструменты возвращают JSON с отступами — ответ Tilda как есть, из конверта берётся
поле `result`.

### 4.1 Найти проект и страницу

**`get_projects`** — список проектов аккаунта. Параметров нет. Отсюда берётся `id` проекта.

**`get_project_info`** — сведения о проекте: домен, настройки экспорта. Обязателен
`projectid`. Необязательный `webconfig` со значением `htaccess` или `nginx` добавляет в
ответ пример конфигурации веб-сервера для самостоятельного хостинга.

**`get_pages`** — список страниц проекта. Обязателен `projectid`. Возвращает по каждой
странице `id`, `title`, `descr`, `alias`, `filename`, `date`, `sort`, `published` — то есть
всё, что нужно, чтобы выбрать страницу для чтения или экспорта.

### 4.2 Прочитать страницу

Два инструмента отличаются объёмом: один отдаёт документ целиком, другой — только тело.
Оба ссылаются на ассеты, лежащие на CDN Tilda, поэтому для самостоятельного хостинга не
годятся — для этого есть пара из 4.3.

**`get_page_body`** — тело страницы: HTML без секции `<head>`. Обязателен `pageid`.
Подходит для быстрого чтения и предпросмотра.

**`get_page`** — страница целиком: HTML вместе с `<head>`, а также CSS и JS. Обязателен
`pageid`.

Оба принимают необязательный `metadata_only`. При `true` тяжёлые поля `html`, `css`, `js`
из ответа удаляются, а вместо них появляются `html_info`, `css_info`, `js_info` со строкой
вида «12345 символов (опущено)» или «7 элементов (опущено)». Это единственный способ
посмотреть карточку страницы, не втягивая её код в контекст модели.

### 4.3 Вынести страницу на свой хостинг

**`get_page_export_body`** — тело страницы (без `<head>`) с локализованными ассетами.
Обязателен `pageid`, поддерживает `metadata_only`. Для вставки в собственный шаблон или CMS.

**`get_page_export`** — полная самостоятельная страница с `<head>` и локализованными
ассетами. Обязателен `pageid`, поддерживает `metadata_only`. Для размещения на своём
сервере.

Ассеты в экспортных ответах приходят массивом `img` из пар `{from, to}`: `from` — исходный
адрес файла на CDN Tilda, `to` — путь, по которому файл должен лежать у вас. Сами файлы
сервер не скачивает — это делает тот, кто собирает выгрузку.

Отдельного метода «экспортировать весь проект» в Tilda API нет. Экспорт сайта целиком
собирается вручную: `get_pages` → цикл `get_page_export` по каждому `id`.

## 5. Готовые сценарии

**1. «Покажи мои проекты в Tilda.»**
`get_projects`. Одна операция, дальше всё пляшет от полученного `id`.

**2. «Сколько страниц на сайте 12345 и когда их последний раз меняли?»**
`get_pages` (`projectid: "12345"`). Даты и признак публикации есть в каждом элементе списка —
дополнительных вызовов не нужно.

**3. «Вычитай тексты главной страницы — заголовки и мета-описание.»**
`get_pages` (найти `id` нужной страницы) → `get_page` (`pageid`). `<head>` нужен именно
здесь: title и мета-теги лежат в нём, в `get_page_body` их нет.

**4. «Что за страница 67890 — не тяни её код.»**
`get_page` с `metadata_only: true`. Вернутся только метаданные и размеры опущенных блоков.
Этим стоит начинать любую работу с незнакомой страницей: длинная страница Tilda легко
занимает сотни килобайт.

**5. «Выгрузи страницу 67890 для размещения на своём сервере.»**
`get_page_export` (`pageid: "67890"`) → скачать файлы по адресам `from` из массива `img` и
разложить их по путям `to` → положить HTML рядом.

**6. «Перенеси лендинг в нашу CMS.»**
`get_page_export_body` (`pageid`) — тело без `<head>`, вставляется в шаблон CMS; ассеты
переносятся так же, по парам `{from, to}`.

**7. «Дай конфиг nginx для проекта 12345.»**
`get_project_info` (`projectid: "12345"`, `webconfig: "nginx"`). Значение `htaccess` даёт
конфигурацию для Apache.

## 6. Ограничения и подводные камни

### 6.1 Лимит запросов Tilda не соблюдается автоматически

Tilda ограничивает API примерно 150 запросами в час (значение из документации Tilda;
в коде сервера оно не задано и не проверяется). Ограничителя частоты на стороне сервера
**нет** — счётчика запросов он не ведёт и заранее не притормаживает. Есть только реакция
постфактум: при ответе `429` запрос повторяется после паузы.

Практический вывод: цикл «экспортировать 200 страниц подряд» упрётся в лимит и часть
страниц вернёт ошибками. Крупные выгрузки нужно разбивать на порции вручную.

### 6.2 Повторы, паузы и таймаут

Попыток не более трёх. Повтор выполняется при `429` и при любом статусе `500` и выше, а также
при таймауте.

Пауза перед повтором считается так: базовая задержка — экспоненциальная, `1000 × 2^(попытка−1)`
миллисекунд, но не больше 8 секунд; если в ответе есть заголовок `Retry-After`, берётся
большее из двух значений; итог в любом случае ограничен 60 секундами. Заголовок понимается в
обеих формах — и как число секунд, и как дата HTTP.

Таймаут одного запроса — 10 секунд, переменной окружения не настраивается. По таймауту
повтор идёт **без паузы**: соединение уже разорвано, ждать нечего.

### 6.3 Объём ответа ничем не ограничен

Этот сервер, в отличие от большинства в монорепозитории, не пропускает ответы через общий
фильтр ядра: ни обрезки по длине, ни фильтрации инъекций к содержимому страниц не
применяется. Страница Tilda со всеми стилями и скриптами уходит в контекст модели целиком.

Отсюда правило работы: незнакомую страницу сначала запрашивать с `metadata_only: true` и
только потом, зная размер, решать, тянуть ли код.

Заодно учтите, что содержимое страниц — это текст, который написали авторы сайта. Модель
читает его как данные, но фильтра здесь нет; к чужому проекту, полученному «на аудит»,
относиться следует соответственно.

### 6.4 Ключи уходят в адресную строку

Tilda принимает ключи только как query-параметры. Сервер не пишет в журнал URL с ключами, но
всё остальное на пути запроса — прокси, корпоративный TLS-инспектор, сетевые логи — увидит их
целиком. Ключи следует держать в `env` конфигурации клиента и не гонять сервер через
незашифрованные или чужие прокси.

### 6.5 Пагинации нет

Ни один из семи методов не принимает параметров постраничного вывода: списки проектов и
страниц приходят целиком. Для аккаунта с крупным проектом это означает один большой ответ,
а не серию мелких.

## 7. Частые ошибки

Ошибки возвращаются модели как результат с признаком `isError: true` и текстом
`Ошибка Tilda: <сообщение>`.

| Сообщение | Что это значит | Что делать |
|---|---|---|
| `TILDA_PUBLIC_KEY и TILDA_SECRET_KEY не заданы` | Переменные не дошли до процесса сервера | Задать обе в блоке `env` конфигурации клиента (не в окружении оболочки) и перезапустить клиент |
| `Tilda ошибка: <текст>` | HTTP-запрос прошёл, но Tilda вернула конверт со `status: "ERROR"` — неверный ключ, чужой `projectid`, несуществующий `pageid` | Прочитать текст: он приходит от Tilda и обычно называет причину. Проверить, что идентификатор принадлежит вашему аккаунту |
| `Tilda HTTP 401` / `403` | Ключи не приняты или не дают доступа к этому проекту | Сверить ключи в `https://tilda.cc/identity/apikeys/` |
| `Tilda HTTP 404` | Метод или объект не найден | Проверить `projectid` / `pageid` через `get_projects` и `get_pages` |
| `Tilda HTTP 429` в тексте после исчерпания попыток | Часовой лимит запросов выбран | Пауза; дробить массовые выгрузки (раздел 6.1) |
| `Tilda API: все попытки исчерпаны` | Три попытки закончились повторяющимся `429`, `5xx` или таймаутом | Повторить позже; при устойчивом повторении — проверить доступность `api.tildacdn.info` |
| Ответ пришёл, но `html` в нём нет, зато есть `html_info` | В вызове был `metadata_only: true` | Повторить вызов без этого параметра |
| Ссылки на картинки ведут на CDN Tilda, а нужен свой хостинг | Использован `get_page` / `get_page_body` вместо экспортных | Взять `get_page_export` или `get_page_export_body` (раздел 4.3) |

Ошибка `413` или `400` при работе в режиме HTTP относится не к Tilda, а к самому транспорту:
тело запроса превысило 1 МБ либо не разобралось как JSON.

Весь журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC.
