## 1. Что это и кому нужно

Сервер даёт ИИ-агенту доступ к учётной базе МойСклад через её JSON API 1.2: товары и услуги,
остатки в разрезе складов, контрагенты, заказы покупателей и поставщикам, отгрузки, приёмки,
перемещения, оприходования, списания, инвентаризации, возвраты, счета, банковские и кассовые
платежи, отчёты о прибыли, продажах, оборотах и деньгах, справочники и журнал аудита.
Практическая задача — снять с человека переключение между вопросом и интерфейсом:
«сколько осталось артикула XR-12», «подними цену на эту позицию», «заведи заказ на ООО
„Ромашка“», «посчитай маржу за июнь» выполняются репликой в чате, а не десятком кликов.

Все денежные величины в инструментах — **в рублях**. API МойСклад работает в копейках;
перевод в обе стороны сервер делает сам, и в ответах цены и суммы приходят в полях с
суффиксом `_rubles`.

Сервер покрывает 60 операций из раздела 4. Печатных форм, розничных смен, задач и
пользовательских справочников здесь нет — но для типов документов без отдельного инструмента
есть универсальные `get_documents` и `get_document` (раздел 4.10), принимающие любой
`entity_type` МойСклада.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "moysklad": {
      "command": "npx",
      "args": ["-y", "@theyahia/moysklad-mcp"],
      "env": { "MOYSKLAD_TOKEN": "ваш-токен" }
    }
  }
}
```

Вариант с логином и паролем вместо токена:

```json
"env": {
  "MOYSKLAD_LOGIN": "user@company",
  "MOYSKLAD_PASSWORD": "пароль"
}
```

Клиент читает конфигурацию при старте — после правки его нужно перезапустить.

### Claude Code

```bash
claude mcp add moysklad -e MOYSKLAD_TOKEN=ваш-токен -- npx -y @theyahia/moysklad-mcp
```

### Cursor / Windsurf

Тот же блок `mcpServers` в настройках MCP среды.

### VS Code (Copilot)

Файл `.vscode/mcp.json`, корневой ключ — `servers`:

```json
{
  "servers": {
    "moysklad": {
      "command": "npx",
      "args": ["-y", "@theyahia/moysklad-mcp"],
      "env": { "MOYSKLAD_TOKEN": "ваш-токен" }
    }
  }
}
```

Файл обычно попадает в систему контроля версий — токен и тем более пароль в нём хранить
не следует.

### Режим Streamable HTTP

```bash
HTTP_PORT=3000 MOYSKLAD_TOKEN=ваш-токен npx -y @theyahia/moysklad-mcp
# либо: npx -y @theyahia/moysklad-mcp --http   (порт 3000 по умолчанию)
```

| Метод и путь | Назначение |
|---|---|
| `POST /mcp` | Запросы MCP; запрос инициализации создаёт сессию |
| `GET /mcp` | Поток SSE существующей сессии |
| `DELETE /mcp` | Завершение сессии |
| `GET /health` | `status`, `server`, `version`, `uptime`, `memory_mb`, `tools` |

Сессии различаются по заголовку `mcp-session-id`; кросс-доменные браузерные вызовы по
умолчанию запрещены. Учётные данные берутся из окружения процесса и **одни на все сессии**:
все подключившиеся работают в базе от имени одной учётной записи МойСклад. Собственной
аутентификации у `/mcp` нет — порт нельзя публиковать в недоверенной сети.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `MOYSKLAD_TOKEN` | да, если не заданы логин и пароль | Токен доступа. Уходит заголовком `Authorization: Bearer` |
| `MOYSKLAD_LOGIN` | да, если не задан токен | Логин пользователя МойСклад (HTTP Basic) |
| `MOYSKLAD_PASSWORD` | да, если не задан токен | Пароль того же пользователя |
| `HTTP_PORT` | нет | Если задана — сервер стартует в режиме HTTP на этом порту |
| `MCP_DISABLE_SANITIZE` | нет | `true` отключает фильтрацию ответов от инъекций |

Токен имеет приоритет: если он задан, логин и пароль не используются. Если не задано
ничего, процесс завершается сразу при старте с ошибкой `Auth not configured. Provide token
OR login+password.` — проверка происходит на этапе загрузки модуля клиента, а не при первом
вызове инструмента.

## 3. Где взять доступ

Доступ бывает двух видов, и оба принимаются сервером.

**Токен доступа.** Выпускается в веб-интерфейсе МойСклад в настройках учётной записи
пользователя. Точный путь по разделам кабинета в исходном коде и README сервера не указан —
уточняйте его в документации МойСклад; в коде зафиксировано только то, что значение
подставляется в заголовок `Authorization: Bearer <токен>`.

**Логин и пароль.** Те же, под которыми пользователь входит в МойСклад; уходят стандартным
HTTP Basic. Вариант проще в настройке, но пароль оказывается в конфигурационном файле
клиента в открытом виде, поэтому предпочтителен токен.

Права доступа определяются **ролью того пользователя МойСклад**, чей токен или пароль указан,
а не аргументами инструментов. Если агенту не нужно создавать документы — заведите отдельного
пользователя с ролью только на чтение и выпустите токен под ним. Это единственный надёжный
способ ограничить область работы: своего режима «только чтение» у сервера нет.

Базовый адрес API зашит в код: `https://api.moysklad.ru/api/remap/1.2`. Переменной окружения
он не переопределяется.

## 4. Инструменты по задачам

Все инструменты возвращают JSON с отступами. Ответы не пересылаются целиком: сервер выбирает
из ответа МойСклад значимые поля и пересчитывает деньги в рубли.

### 4.1 Найти товар

**`search_products`** — поиск по названию или артикулу. Все параметры необязательны:
`search` (подстрока в названии), `filter_article` (точное совпадение по артикулу),
`limit` (1–1000, по умолчанию 25), `offset` (по умолчанию 0). Возвращает `total` (сколько
всего нашлось) и `products` с полями `id`, `name`, `article`, `code`, `sale_price_rubles`,
`buy_price_rubles`.

**`get_product`** — товар целиком. Обязателен `id` — UUID товара из результата поиска.
Дополнительно к полям списка возвращает `description`, `weight`, `volume`, `sale_prices`
(все цены продажи с названиями типов цен) и `updated`. Флаг `raw: true` возвращает объект
МойСклада без обработки — когда нужно поле, которого нет в сводке.

**`search_assortment`** — единый поиск сразу по товарам, модификациям, услугам и комплектам
(`/entity/assortment`). Параметры: `search`, `limit`, `offset`. В каждой строке — `type`
(что именно нашлось) и **`meta_href`**, готовый для подстановки в документ.

**`search_variants`**, **`search_bundles`**, **`search_services`** — то же по одному типу:
модификации, комплекты, услуги. Возвращают `meta_href`.

**`create_service`** — заводит услугу: `name`, необязательные `description`, `code`,
`sale_price_rubles`, `price_type_href`, `vat`.

**`list_price_types`** — типы цен аккаунта. Первый в списке помечен `is_default: true`.
Отсюда берётся `price_type_href` для `create_product` и `create_service`.

### 4.2 Посмотреть остатки

**`get_stock`** — отчёт об остатках (`/report/stock/all`). Все параметры необязательны:

| Параметр | Значения | По умолчанию |
|---|---|---|
| `search` | подстрока в названии товара | — |
| `limit` | 1–1000 | 25 |
| `offset` | смещение | 0 |
| `group_by` | `product`, `variant`, `store` | `product` |
| `stock_mode` | `all`, `positiveOnly`, `negativeOnly`, `empty`, `nonEmpty` | `all` |

По каждой позиции возвращает `name`, `article`, `code`, `stock` (остаток), `reserve`
(резерв), `inTransit` (ожидание), `quantity` (доступно) и `sale_price_rubles`.

**`get_stock_by_store`** — тот же отчёт в разрезе складов (`/report/stock/bystore`):
по каждой позиции массив `by_store` с названием склада, остатком, резервом и ожиданием.
Параметры: `search`, `limit`, `offset`.

**`get_stock_current`** — быстрый текущий остаток (`/report/stock/all/current`) без
пагинации; необязательный `store_href` ограничивает одним складом. Отдаёт компактный
машинный срез, а не разложенную по полям сводку.

Оба отчёта по остаткам МойСклад тарифицирует **впятеро дороже** обычного запроса — сервер
списывает за них 5 единиц из корзины лимита (раздел 6.1), а не одну.

### 4.3 Изменить цены и завести товар

**`update_prices`** — меняет цены существующего товара. Обязателен `id`; далее любые из
`sale_price_rubles`, `buy_price_rubles`, `min_price_rubles`. При изменении цены продажи
сервер сначала читает товар, чтобы сохранить привязку к типу цены, и правит значение первой
цены в списке — остальные типы цен не затрагиваются. Если цены продажи у товара ещё не было,
подставляется тип цены по умолчанию.

**`create_product`** — создаёт товар. Обязателен `name`. Необязательные: `article`,
`description`, `code`, `sale_price_rubles`, `buy_price_rubles`, `min_price_rubles`,
`price_type_href` (тип цены продажи; по умолчанию берётся первый из `list_price_types`),
`weight` (в граммах), `volume` (в литрах), `vat` (ставка НДС: 0, 10 или 20 — уходит в поле
`effectiveVat`). Возвращает созданный товар с присвоенным UUID.

### 4.4 Работать с контрагентами

**`get_counterparties`** — поиск покупателей и поставщиков. Все параметры необязательны:
`search` (подстрока в названии), `filter_inn` (точное совпадение по ИНН), `filter_phone`
(точное совпадение по телефону), `limit` (1–1000, по умолчанию 25), `offset`. Возвращает
`total` и список с полями `id`, `name`, `phone`, `email`, `inn`, `companyType`.

**`get_counterparty`** — один контрагент по `id`; `raw: true` отдаёт объект МойСклада целиком.

**`create_counterparty`** — заводит контрагента: обязателен `name`, необязательные `inn`,
`phone`, `email`, `description` и `companyType` (`legal` — по умолчанию, `entrepreneur`,
`individual`).

### 4.5 Оформлять документы

Все документы требуют **meta-ссылок**, а не идентификаторов — см. раздел 6.2.

**`create_customer_order`** — заказ покупателя. Обязательны:

| Параметр | Что это |
|---|---|
| `organization_href` | meta-ссылка организации-продавца |
| `agent_href` | meta-ссылка контрагента-покупателя |
| `positions` | массив позиций, минимум одна |

Позиция: `assortment_href` (meta-ссылка товара) и `quantity` (не меньше 1) — обязательны;
`price_rubles` и `discount` (процент, 0–100) — нет. Необязательный `description` —
комментарий к заказу. Возвращает `id`, `name` (номер), `moment`, `sum_rubles`,
`description`, `created`, `updated`.

**`create_supply`** — приёмка товара от поставщика. Обязательны `organization_href`
(организация-получатель), `agent_href` (поставщик) и `positions` (`assortment_href` +
`quantity`, цена позиции необязательна). Необязательные: `store_href` (склад),
`description`, `incoming_number` и `incoming_date` (номер и дата входящего документа
поставщика, ISO 8601). Возвращает `id`, `name`, `moment`, `sum_rubles`, `created`.

**`get_orders`** — список заказов покупателей. Все параметры необязательны: `search` (по
названию или номеру), `limit` (1–1000, по умолчанию 25), `offset`, `filter_state` (название
статуса), `filter_agent` (meta-ссылка контрагента), `order` (`created,desc` — по умолчанию,
а также `created,asc`, `moment,desc`, `moment,asc`, `sum,desc`, `sum,asc`), `expand`
(раскрытие вложенных сущностей). Возвращает `total` и список с `id`, `name`, `moment`,
`sum_rubles`, `description`.

**`get_customer_order`** — один заказ по `id` с развёрнутыми позициями, как его отдаёт
МойСклад.

**`update_customer_order_status`** — меняет статус заказа. Обязательны `id` и `state_href` —
meta-ссылка состояния. Список состояний берётся из `get_metadata` для `customerorder`
(раздел 4.9).

**`create_demand`** — отгрузка со склада. Обязательны `organization_href`, `agent_href`,
`store_href` и `positions`; необязательный `customer_order_href` привязывает отгрузку к
заказу покупателя.

### 4.6 Складские документы

Все создаются одинаково: организация, склад (или пара складов), позиции. Позиция —
`assortment_href` + `quantity`, необязательные `price_rubles` (в рублях) и `discount`.

| Инструмент | Документ | Обязательные ссылки |
|---|---|---|
| `create_move` | перемещение между складами | `organization_href`, `source_store_href`, `target_store_href` |
| `create_enter` | оприходование | `organization_href`, `store_href` |
| `create_loss` | списание | `organization_href`, `store_href` |
| `create_inventory` | инвентаризация | `organization_href`, `store_href` (позиции необязательны) |
| `create_purchase_order` | заказ поставщику | `organization_href`, `agent_href` (склад необязателен) |
| `create_sales_return` | возврат от покупателя | `organization_href`, `agent_href`, `store_href` |
| `create_purchase_return` | возврат поставщику | `organization_href`, `agent_href`, `store_href` |

Списки ранее созданных: **`get_moves`**, **`get_enters`**, **`get_losses`**,
**`get_inventories`**, **`get_purchase_orders`** — параметры у всех одинаковые (`search`,
`limit`, `offset`), ответ — `total` и документы с `id`, `name`, `moment`, `sum_rubles`,
`state`, `agent`.

`create_inventory` можно вызвать без позиций: документ создастся пустым, позиции
заполняются в интерфейсе. Расхождения после проведения инвентаризации оформляются
оприходованием (`create_enter`) и списанием (`create_loss`).

### 4.7 Счета и деньги

**`create_invoice_out`** (счёт покупателю) и **`create_invoice_in`** (счёт поставщика) —
`organization_href`, `agent_href`, `positions`. **`get_invoices_out`** перечисляет счета
покупателям.

Платежи принимают не позиции, а сумму `sum_rubles`:

| Инструмент | Документ | Особенности |
|---|---|---|
| `create_payment_in` | входящий банковский платёж | `incoming_number`, `incoming_date` необязательны |
| `create_payment_out` | исходящий банковский платёж | `expense_item_href` — статья расходов, в ряде баз обязательна |
| `create_cash_in` | приходный кассовый ордер | как `create_payment_in` |
| `create_cash_out` | расходный кассовый ордер | как `create_payment_out` |

### 4.8 Отчёты

**`get_profit_report`** — прибыль по товарам (`/report/profit/byproduct`). Все параметры
необязательны: `moment_from` и `moment_to` — даты в ISO 8601 (`2026-06-01`), `limit`
(1–1000, по умолчанию 25), `offset`. Границы периода сервер достраивает до суток сам:
`00:00:00` для начала и `23:59:59` для конца.

По каждой позиции возвращает `product_name`, `sell_quantity`, `sell_sum_rubles`,
`sell_cost_sum_rubles` (себестоимость), `return_quantity`, `return_sum_rubles`,
`profit_rubles` и `margin`.

**`get_sales_report`** — продажи по товарам (`/report/sales/byproduct`) с теми же
параметрами периода: `product_name`, `sell_quantity`, `sell_sum_rubles`.

**`get_turnover`** — обороты товаров за период (`/report/turnover/all`): по каждой позиции
четыре среза — `on_period_start`, `income`, `outcome`, `on_period_end`, в каждом `quantity`
и `sum_rubles`.

**`get_money_report`** — остатки денег по расчётным счетам и кассам
(`/report/money/byaccount`): `account`, `organization`, `balance_rubles`. Параметров нет.

**`get_dashboard`** — показатели за `day`, `week` или `month` (`/report/dashboard/…`).
Единственный инструмент, отдающий ответ как есть: **суммы в нём в копейках**, как их
возвращает МойСклад.

### 4.9 Справочники и метаданные

| Инструмент | Что возвращает |
|---|---|
| `list_organizations` | ваши юрлица: `id`, `name`, `inn`, **`meta_href`** |
| `list_stores` | склады: `id`, `name`, `address`, **`meta_href`** |
| `list_employees` | сотрудники: `id`, `name`, `email`, `phone`, `meta_href` |
| `list_currencies` | валюты: `code`, `iso_code`, `rate` |
| `list_product_folders` | товарные группы: `name`, `code`, `path_name` |

**`get_metadata`** — метаданные типа сущности (`entity_type`: `customerorder`, `product`,
`demand` и т. д.): статусы, дополнительные поля, типы цен. Отсюда берутся meta-ссылки
состояний для `update_customer_order_status`.

### 4.10 Документы без отдельного инструмента

**`get_documents`** — список документов любого типа: обязателен `entity_type`
(`retaildemand`, `commissionreportin`, `factureout` — любой тип API МойСклад), далее
`search`, `filter` (сырое выражение фильтра МойСклада), `limit`, `offset`.

**`get_document`** — один документ: `entity_type` + `id`, позиции развёрнуты.

Это запасной путь: если операции нет среди 58 остальных инструментов, читать её документы
всё равно можно.

### 4.11 Вебхуки

**`list_webhooks`**, **`create_webhook`** (`url` — обязательно HTTPS, `action`:
`CREATE` / `UPDATE` / `DELETE` / `PROCESSED`, `entityType`, необязательный `diffType`:
`NONE` или `FIELDS`), **`update_webhook`** (по `id` меняет URL, событие, тип сущности,
`enabled`), **`delete_webhook`** (удаляет по `id`).

### 4.12 Журнал аудита

**`get_audit`** — события аккаунта за период (`moment_from`, `moment_to`, `limit`,
`offset`): `moment`, `event_type`, `entity_type`, `name`, `source`, `uid`.

**`get_entity_audit`** — история изменений одной сущности: `entity_type` + `id`.

## 5. Готовые сценарии

**1. «Сколько осталось артикула XR-12?»**
`search_products` (`filter_article: "XR-12"`) → `get_stock` (`search` по названию из
результата). Отчёт об остатках ищет по названию, а не по артикулу, поэтому промежуточный
поиск товара нужен.

**2. «Каких товаров меньше пяти штук — покажи с артикулами.»**
`get_stock` (`stock_mode: "positiveOnly"`, `limit: 1000`) → отобрать позиции с `stock < 5`.
Порога по количеству в API нет, фильтрация делается агентом на полученном списке.

**3. «Подними цену на товар до 1490 ₽.»**
`search_products` (`search` по названию) → взять `id` → `update_prices`
(`id`, `sale_price_rubles: 1490`). Цена указывается в рублях; копейки допустимы
(`1490.50`), перевод выполняет сервер.

**4. «Найди контрагента по ИНН 7707083893 и покажи его заказы за квартал.»**
`get_counterparties` (`filter_inn: "7707083893"`) → `get_orders`. Фильтр `filter_agent`
принимает meta-ссылку, а не `id`, поэтому проще отобрать заказы по названию через `search`
либо собрать ссылку по правилу из раздела 6.2.

**5. «Заведи заказ покупателя на две позиции.»**
`list_organizations` (взять `meta_href`) → `get_counterparties` (собрать ссылку на
контрагента, раздел 6.2) → `search_assortment` по каждой позиции (сразу отдаёт `meta_href`)
→ `create_customer_order` с массивом `positions`. Ответ содержит номер документа (`name`)
и сумму в рублях.

**6. «Оформи приёмку по накладной поставщика № 145 от 3 июня.»**
`get_counterparties` (найти поставщика) → `search_products` по позициям →
`create_supply` (`incoming_number: "145"`, `incoming_date: "2026-06-03"`, `store_href`,
`positions`). Без `store_href` документ создастся на складе по умолчанию базы.

**7. «Посчитай прибыль и маржу за июнь — какие пять позиций дали больше всего.»**
`get_profit_report` (`moment_from: "2026-06-01"`, `moment_to: "2026-06-30"`, `limit: 1000`)
→ отсортировать по `profit_rubles`. Сортировки на стороне API у этого отчёта нет.

**8. «Какие заказы висят в статусе „Новый“?»**
`get_orders` (`filter_state: "Новый"`, `order: "created,desc"`). Название статуса
подставляется дословно, как оно заведено в вашей базе.

**9. «Перемести 10 штук LP15 с основного склада в розницу.»**
`list_stores` (взять `meta_href` обоих складов) → `list_organizations` →
`search_assortment` (`search: "LP15"`) → `get_stock_by_store`, чтобы убедиться, что на
складе-источнике товар есть → `create_move` (`source_store_href`, `target_store_href`,
`positions`).

**10. «Переведи заказ в статус „Отгружен“ и оформи отгрузку.»**
`get_metadata` (`entity_type: "customerorder"`) → найти состояние по названию, взять его
`meta.href` → `update_customer_order_status` → `create_demand` с `customer_order_href`
заказа и `store_href` склада отгрузки.

**11. «Сколько денег на счетах и в кассах прямо сейчас?»**
`get_money_report` — параметров нет, возвращает `balance_rubles` по каждому счёту и кассе.

**12. «Проведи инвентаризацию склада „Основной“.»**
`list_organizations` + `list_stores` → `get_stock_by_store` (текущие остатки, с чем
сверять) → `create_inventory`. Расхождения после проведения оформляются `create_enter`
и `create_loss`.

## 6. Ограничения и подводные камни

### 6.1 Ограничение частоты — 45 запросов за 3 секунды

Перед каждым запросом сервер берёт токен из корзины на 45 штук, которая целиком
восстанавливается раз в 3 секунды. Отчёты по остаткам (`get_stock`, `get_stock_by_store`)
МойСклад тарифицирует впятеро дороже, и сервер списывает за них 5 токенов, а не один. Если токены кончились, вызов ждёт до конца текущего окна
и продолжается. Ограничитель один на процесс: в режиме HTTP его делят все подключённые
клиенты.

Отдельно учтите, что счётчик у сервера свой и с фактическим счётчиком МойСклад не
синхронизирован — параллельно работающая интеграция под тем же аккаунтом лимит выберет
незаметно для сервера, и вы получите `429`.

### 6.2 Meta-ссылки — главный источник затруднений

Документы МойСклад ссылаются на объекты не идентификатором, а полным адресом объекта в API —
meta-ссылкой вида `https://api.moysklad.ru/api/remap/1.2/entity/counterparty/<uuid>`.
Именно её ждут `organization_href`, `agent_href`, `assortment_href`, `store_href` и фильтр
`filter_agent`.

Готовые meta-ссылки отдают `list_organizations`, `list_stores`, `list_employees`,
`list_currencies`, `list_product_folders`, `list_price_types`, а также `search_assortment`,
`search_variants`, `search_bundles` и `search_services` — в поле `meta_href`. Порядок
работы:

- организация, склад, тип цены — из соответствующего `list_*`, поле `meta_href`;
- товар — либо `search_assortment` (сразу `meta_href`), либо `search_products` с
  досборкой ссылки из `id` по образцу выше (`/entity/product/<id>`);
- контрагент — `get_counterparties` отдаёт `id`, ссылка собирается как
  `/entity/counterparty/<id>`;
- состояние документа — `get_metadata` для нужного типа сущности.

Тип сущности в ссылке сервер выводит из самого адреса, поэтому подставлять `meta_href`
можно как есть — переписывать его не нужно.

Ошибка в ссылке даёт отказ на стороне МойСклад, а не на стороне сервера: проверки формата
`href` в схемах нет.

### 6.3 Изменяющие операции не повторяются автоматически

Повторы выполняются только для запросов чтения (GET). Создание и изменение — все
инструменты `create_*`, `update_*` и `delete_webhook` — при таймауте, ответе `5xx` или
обрыве соединения **не повторяются**, и к тексту ошибки дописывается:

> Повтор не выполнен автоматически, потому что операция изменяет данные. Проверьте в базе,
> не создан ли объект, прежде чем повторять.

Это сделано намеренно: неоднозначный сбой не означает, что МойСклад не выполнил запрос —
повтор создал бы второй документ. Прежде чем повторять вызов, найдите объект через
`get_orders`, `get_documents` или `search_products`.

Для чтения повторов не больше трёх, с задержкой `1000 × 2^(попытка−1)` мс, но не дольше
8 секунд. Таймаут одного запроса — 15 секунд, переменной окружения не настраивается.

### 6.4 Ответ `401` не приводит к повторной аутентификации

Ни токен, ни пара логин-пароль не обновляются на лету: при `401` или `403` запрос сразу
завершается ошибкой. Просроченный токен требует замены в конфигурации клиента и
перезапуска.

### 6.5 Цена продажи при создании товара

Раньше `create_product` отправлял цену продажи с пустой ссылкой на тип цены, и создание
товара с `sale_price_rubles` отклонялось. Теперь сервер подставляет тип цены по умолчанию —
первый из `list_price_types`, — либо тот, что передан в `price_type_href`. Список типов цен
запрашивается один раз за время жизни процесса и кэшируется.

Остаточное ограничение: если в базе не заведён **ни один** тип цены, вызов завершится
ошибкой «No price type configured in MoySklad» — тип цены нужно создать в настройках
МойСклада. Товар без цены продажи при этом создаётся нормально.

### 6.6 Округление рублей в копейки

Перевод выполняется как `округление(рубли × 100)`. Значения с более чем двумя знаками после
запятой округляются до копейки — например, `10.005` превратится в `10.01` (1001 копейка).
Для цен это несущественно, но при переносе прайса с высокой точностью расхождение стоит
учитывать.

### 6.7 Пагинация и объём ответа

Списочные инструменты работают по схеме `limit` + `offset`, максимум 1000 записей на
страницу; поле `total` в ответе показывает полный размер выборки. Сортировка задаётся только
у `get_orders` (`order`), у остальных её нет.

Значения фильтров не должны содержать `;` — это разделитель условий в грамматике фильтров
МойСклада. Такой аргумент отклоняется до обращения к API, чтобы подставленное значение не
дописало в запрос чужое условие.

Любой ответ длиннее 50 000 символов обрезается с пометкой о срезке — при массовых выгрузках
уменьшайте `limit` и ходите страницами. Кроме того, тексты из базы проходят фильтр:
конструкции вида «игнорируй предыдущие инструкции» и теги `<system>` заменяются на
`[filtered]`. Отключается переменной `MCP_DISABLE_SANITIZE=true`; для учётной базы, куда
данные попадают от контрагентов, отключать не рекомендуется.

## 7. Частые ошибки

Ошибки возвращаются модели как результат с признаком `isError: true`. Сообщение состоит из
типовой фразы категории и хвоста `Детали: <текст от МойСклад>`. Тело ответа МойСклада
(`errors[]`) разбирается в читаемую строку с кодом, сообщением и именем параметра — именно
там видно, какого реквизита не хватило документу.

| Что видно | Что это значит | Что делать |
|---|---|---|
| `Auth not configured. Provide token OR login+password.` при старте | Ни `MOYSKLAD_TOKEN`, ни пара логин+пароль не дошли до процесса | Задать переменные в блоке `env` конфигурации клиента (не в окружении оболочки) и перезапустить клиент |
| `Отказ в доступе (HTTP 401)` | Токен недействителен, отозван или пароль неверен | Проверить и заменить учётные данные; автоматического обновления нет |
| `Отказ в доступе (HTTP 403)` | Учётные данные верны, но у роли пользователя нет прав на объект или операцию | Выдать права роли в МойСклад — аргументами инструментов это не обходится |
| `Ресурс не найден` (404) | Неверный UUID, неверная meta-ссылка или объект удалён | Найти действительный идентификатор через `search_products` / `get_counterparties`; сверить ссылку с разделом 6.2 |
| `Rate limit. Повторите через Nс` (429) | Лимит МойСклад выбран — обычно параллельной интеграцией под тем же аккаунтом | Пауза; уменьшить `limit` и частоту вызовов |
| `Ошибка сервера (HTTP 5xx)` | МойСклад временно недоступен | Для чтения повтор уже выполнялся трижды; повторить через 10–30 секунд |
| `Таймаут запроса (15с)` | Ответ не пришёл вовремя | Сузить период отчёта, уменьшить `limit`, повторить |
| `Повтор не выполнен автоматически, потому что операция изменяет данные…` | Сбой на создании или изменении; результат неизвестен | **Не повторять вслепую.** Сначала проверить в базе, создан ли документ (раздел 6.3) |
| `Ошибка валидации: <поле>: <причина>` | Аргументы не прошли проверку схемы **до** обращения к API | Исправить аргумент; сетевого вызова не было |
| Ошибка от МойСклад о незаполненном обязательном поле при создании документа | Не хватает реквизита, обязательного в вашей базе | Имя поля — в хвосте `Детали:`; добавить значение и повторить |
| `No price type configured in MoySklad` | В базе не заведён ни один тип цены | Создать тип цены в настройках МойСклада (раздел 6.5) |
| `Filter value for "<поле>" must not contain ';'` | В значении фильтра символ-разделитель условий | Убрать `;` из значения (раздел 6.7) |
| Ответ обрывается фразой о срезке | Ответ длиннее 50 000 символов | Уменьшить `limit`, идти страницами через `offset` |

Весь журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. В журнал пишутся
метод и путь запроса без строки параметров: в фильтрах бывают ИНН и суммы.
