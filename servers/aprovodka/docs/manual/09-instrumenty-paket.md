## 7.10 Модуль `batch` — пакетные операции (3 инструмента)

Модуль включается значением `batch` в `ONEC_SERVICES` (по умолчанию включены все модули).

**Пакетность здесь клиентская.** Встроенный OData-сервис «1С:Предприятия» не реализует точку `$batch`: запрос `multipart/mixed` к `/odata/standard.odata/$batch` возвращает «Произошла ошибка сервиса». Поэтому инструменты модуля рассылают N обычных OData-запросов с ограничением параллелизма и собирают результаты в общий конверт. Серверного объединения (join) нет.

**Поведение при частичном отказе.** Отказ одного элемента не прерывает пакет: остальные выполняются до конца. Каждый элемент получает собственный статус, порядок результатов совпадает с порядком входного массива. Транзакции на весь пакет нет: если из 100 документов создались 97, три оставшихся отправляются повторно, а 97 уже находятся в базе.

Общий формат ответа всех трёх инструментов:

| Поле | Смысл |
|---|---|
| `total` | Сколько элементов было во входном массиве |
| `succeeded` | Сколько выполнено успешно |
| `failed` | Сколько завершилось ошибкой |
| `results[]` | По элементу: `index`, `status` (`ok` / `error`), `data` либо `error` |
| `failed_indexes[]` | Индексы неудачных элементов — список для повтора |
| `note` | Напоминание об отсутствии `$batch` в «1С» |

### 7.10.1 `batch_create_documents`

**Назначение.** Создать от 1 до 100 документов одного вида параллельными запросами.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Вид документа, единый для всего пакета. Принимается и полное имя (`Document_РеализацияТоваровУслуг`), и имя без префикса — `Document_` достраивается |
| `documents` | массив объектов | да | От 1 до 100 наборов полей документа; структура элемента та же, что у аргумента `data` инструмента `create_document` |
| `concurrency` | целое 1–20 | нет | Предел одновременных HTTP-запросов к «1С», по умолчанию 5 |

**Возвращает** конверт, описанный выше; в `data` успешного элемента — ответ «1С» на создание записи с присвоенным `Ref_Key`.

**Пример запроса на естественном языке.** «Создай 20 реализаций товаров по этой таблице, по 5 запросов одновременно».

Пример ответа (иллюстративный, сокращён; получен не из рабочей базы):

```json
{
  "total": 20, "succeeded": 19, "failed": 1,
  "results": [
    { "index": 0, "status": "ok", "data": { "Ref_Key": "…", "Number": "…" } },
    { "index": 7, "status": "error", "error": "Поле объекта не обнаружено (Контрагент)" }
  ],
  "failed_indexes": [7], "note": "…"
}
```

**Примечания.** Документы создаются непроведёнными — проведение выполняется отдельно (`post_document`). Повышение `concurrency` увеличивает нагрузку на сервер «1С» и вероятность взаимных блокировок при записи в одни регистры; при таких ошибках значение следует снижать.

### 7.10.2 `batch_update_catalog_items`

**Назначение.** Изменить от 1 до 100 элементов одного справочника: по каждому выполняется `PATCH` по его `Ref_Key`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `catalog_name` | строка | да | Имя справочника. Принимается и `Catalog_Номенклатура`, и `Номенклатура` — префикс `Catalog_` достраивается |
| `updates` | массив объектов | да | От 1 до 100 пар: `ref_key` — GUID элемента, `data` — изменяемые поля (структура как у `data` в `update_document`) |
| `concurrency` | целое 1–20 | нет | Предел одновременных запросов, по умолчанию 5 |

**Возвращает** тот же конверт. `Ref_Key` проверяется на формат GUID отдельно для каждого элемента: неверный ключ приводит к ошибке только своего элемента.

**Пример запроса.** «Установи признак „Услуга“ у этих 40 позиций номенклатуры».

**Примечания.** Передаются только перечисленные поля, остальные реквизиты не затрагиваются. Несуществующий `Ref_Key` даёт ошибку «1С» в своей строке результата.

### 7.10.3 `batch_query`

**Назначение.** Выполнить от 1 до 50 независимых запросов чтения OData параллельно.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `queries` | массив объектов | да | От 1 до 50 описаний запросов; каждое — отдельный HTTP-запрос |
| `queries[].entity` | строка | да | Сущность OData, например `Catalog_Номенклатура`. Имя передаётся как есть, без достройки префикса |
| `queries[].filter`, `.select`, `.expand`, `.orderby` | строка | нет | Выражения `$filter`, `$select`, `$expand`, `$orderby` |
| `queries[].top` | целое 1–5000 | нет | Ограничение количества строк, по умолчанию 100 |
| `queries[].skip` | целое ≥ 0 | нет | Пропуск строк для постраничного обхода, по умолчанию 0 |
| `concurrency` | целое 1–20 | нет | Предел одновременных запросов, по умолчанию 5 |

**Пример запроса.** «Посчитай за один заход остатки по трём складам и заодно подтяни справочник организаций».

**Примечания.** Поскольку имя сущности не изменяется, `batch_query` служит аварийным выходом для объектов, чьё имя нельзя получить достройкой префикса. Соединение результатов выполняет вызывающая сторона.

## 7.11 Модуль `changes` — отслеживание изменений (2 инструмента)

Модуль включается значением `changes` в `ONEC_SERVICES`. Встроенный OData-сервис «1С» не предоставляет ни веб-хуков, ни подписки на события, ни ленты изменений: доступен только синхронный CRUD. Единственный штатный способ узнать об изменениях — периодический опрос.

### 7.11.1 `poll_changes_since`

**Назначение.** Получить строки сущности, изменённые с заданной отметки времени, и курсор для следующего опроса.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `entity` | строка | да | Опрашиваемая сущность OData, например `Document_РеализацияТоваровУслуг` или `Catalog_Номенклатура` |
| `since` | строка `ГГГГ-ММ-ДДTчч:мм:сс` | да | Курсор: возвращаются строки со значением поля даты больше либо равным `since`. При первом опросе задаётся вручную, далее — `next_cursor` из предыдущего ответа |
| `date_field` | строка | нет | Поле даты, по которому идёт отбор. По умолчанию `Date` — подходит большинству документов. Для справочников и регистров без `Date` указывается другое поле, например `ModificationDate`; состав реквизитов зависит от конфигурации, наличие поля проверяется через `describe_entity` |
| `top` | целое 1–1000 | нет | Максимум строк за один опрос, по умолчанию 100 |
| `select` | строка | нет | Выражение `$select` для сокращения состава возвращаемых полей |

**Возвращает:** `entity`, `since`, `date_field`, `count` — число строк, `rows` — сами строки, `next_cursor`, `has_more`, `note`.

- `next_cursor` — наибольшее значение поля даты среди возвращённых строк; `null`, если строк нет или значение не удалось прочитать.
- `has_more` — истина, когда число строк достигло `top`: изменений больше, чем поместилось в ответ, и опрос следует повторить сразу, не дожидаясь интервала.

**Пример запроса.** «Каждую минуту проверяй новые реализации и показывай только появившиеся».

**Примечания.** Отбор идёт по условию «больше либо равно», а курсор равен максимальной дате выборки, поэтому строки с граничной датой вернутся и в следующем опросе — дубли отсеиваются по `Ref_Key` на стороне вызывающего. Сортировка ответа — по возрастанию поля даты. Изменение видно только через поле `date_field`: если конфигурация не обновляет его при записи, изменение останется незамеченным.

### 7.11.2 `list_subscriptions`

**Назначение.** Явно зафиксировать отсутствие подписок на события в «1С». Аргументов не имеет.

**Возвращает:** `supported: false`, пустой список `subscriptions`, `reason` с объяснением и `workarounds` — три обходных пути: опрос через `poll_changes_since`; собственный HTTP-сервис «1С», отправляющий уведомления во внешнюю точку (доработка конфигурации, читается через `get_report`); внешний брокер сообщений через подписку «1С» — за пределами возможностей сервера.

**Примечания.** Инструмент существует, чтобы языковая модель не изобретала несуществующий вызов вида `subscribe_to_event` и не предлагала настроить отсутствующий в платформе веб-хук.

## 7.12 Инструменты гейта записи (2 инструмента)

Оба инструмента регистрируются, только если `ONEC_WRITE_MODE` равна `preview` или `approval`. При значении по умолчанию (`off`) их в списке инструментов нет, а запись выполняется сразу.

Гейт встроен в три функции клиента, через которые проходит любая запись (`POST`, `PATCH`, `DELETE`), поэтому действует и на пакетные операции: в режиме `preview` каждый элемент пакета вернёт предварительный отчёт вместо записи, в режиме `approval` — потребует отдельного подтверждения. Для пакетов из десятков элементов режим `approval` практически неприменим.

### 7.12.1 `approve_write`

**Назначение.** Подтвердить одну ожидающую операцию записи по `op_hash` из её предварительного отчёта.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `op_hash` | строка, 16 шестнадцатеричных символов | да | `op_hash` из preview-ответа пишущего инструмента |
| `reason` | строка | нет | Кто и почему подтвердил — попадает в журнал аудита |

**Возвращает:** подтверждённый `op_hash`, `expires_in_sec` — срок действия (по умолчанию 300 секунд, настраивается `ONEC_APPROVAL_TTL_SEC`), признак одноразовости и указание следующего шага.

**Порядок работы.** Вызов пишущего инструмента → сервер ничего не пишет и возвращает предварительный отчёт с `op_hash` → отчёт показывается человеку → после явного согласия вызывается `approve_write` → тот же инструмент вызывается повторно с теми же аргументами и выполняется один раз.

**Примечания.** Подтверждение одноразовое и привязано к конкретной операции: любое изменение аргументов даёт другой `op_hash` и требует нового подтверждения. Подтверждения хранятся в памяти процесса и теряются при перезапуске. Подтвердить можно только тот `op_hash`, чей предпросмотр ещё лежит в памяти сервера: предпросмотров хранится не больше сотни, старые вытесняются, а выполненная операция забирает свой. Для неизвестного хеша инструмент возвращает ошибку с объяснением — повторите вызов пишущего инструмента и подтверждайте новый `op_hash`. В режиме `preview` инструмент возвращает ошибку — там запись не выполняется вообще. `approve_write` сам является вызовом инструмента, поэтому фактическим рубежом для человека служит окно подтверждения вызовов в клиенте MCP; сервер гарантирует лишь невозможность записи без отдельного явного шага с указанием точного хеша операции.

### 7.12.2 `rollback_write`

**Назначение.** Выполнить обратную операцию для уже совершённой записи по её токену отката.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `token` | строка | да | Значение `rollback.token` из ответа выполненной операции, например `rb-1a2b3c4d5e6f7890` |

**Что обратимо:** проведение → отмена проведения; отмена проведения → проведение (неоперативное); изменение реквизитов → возврат ранее прочитанных значений; переключение пометки удаления `DeletionMark`.

**Что необратимо:** физическое удаление через `DELETE` (в «1С» нет отмены; вместо него рекомендуется `set_deletion_mark`) и создание новой записи. Токен для них не выдаётся, в ответе присутствует `irreversible_reason` с указанием ручного способа отмены.

**Примечания.** Токен одноразовый. Токены хранятся в памяти процесса, их число ограничено сотней — при переполнении вытесняется самый старый. После перезапуска сервера токены недействительны; обратную операцию тогда воспроизводят вручную по записи `inverse` в журнале аудита. Сам откат повторно через гейт не проводится — он отменяет уже подтверждённую операцию, — но фиксируется в журнале событиями `rollback_attempt` и `rollback_executed`.

**Журнал аудита.** При заданном `ONEC_AUDIT_LOG` в файл JSONL дописываются события `preview`, `approved`, `attempt`, `executed`, `failed`, `rollback_token_issued`, `rollback_attempt`, `rollback_executed` с отметкой времени и именем исполнителя (`ONEC_AUDIT_ACTOR`, по умолчанию — `ONEC_LOGIN`). Строка пишется до обращения к «1С»: если дописать её не удалось, операция отменяется. Журнал содержит тела запросов целиком и требует такой же защиты, как сами данные «1С».
