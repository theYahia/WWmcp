## 1. Введение

### 1.1. Назначение продукта и решаемая задача

aprovodka — серверная программа, которая предоставляет ИИ-агенту (языковой модели,
работающей внутри поддерживающего MCP клиентского приложения) набор инструментов для
чтения и изменения данных информационной базы «1С:Предприятие».

Решаемая задача. Данные учётной системы закрыты для внешних программ до тех пор, пока
кто-то не напишет к ним обработку, отчёт или обмен. Типовой цикл «сформулировать вопрос
→ поставить задачу программисту → получить выгрузку» занимает от часов до недель, и
каждая новая формулировка вопроса запускает его заново. При этом штатный интерфейс OData
платформы уже предоставляет доступ к справочникам, документам, регистрам и константам —
не хватает не канала, а связующего слоя, который объясняет модели, что в базе есть, как
это называется и как к этому обратиться, не нарушая правил платформы.

Этот слой и составляет содержание продукта. В версии 4.3.0 он включает:

- 34 инструмента в 11 модулях: `meta` (обнаружение структуры, включён всегда),
  `catalogs`, `documents`, `registers`, `accounting`, `constants`, `shortcuts`,
  `reports`, `odata`, `batch`, `changes`;
- 3 готовых сценария: `inventory-database` (инвентаризация незнакомой базы),
  `find-and-post-document` (поиск документа и его проведение только после явного
  подтверждения человеком), `reconcile-balances` (сверка остатков регистра накопления
  с движениями);
- курированные схемы типовых конфигураций («1С:Бухгалтерия предприятия 3.0»,
  «1С:Управление торговлей 11», «1С:Зарплата и управление персоналом 3.1»,
  «1С:ERP Управление предприятием 2»), доступные офлайн, без подключения к базе;
- необязательный контур безопасности записи (режимы `preview` и `approval`, журнал
  аудита в формате JSONL, откат обратимых операций).

Продукт не является ни аналитической системой, ни хранилищем данных, ни заменой отчётам
конфигурации. Он не хранит данные базы: каждый вызов инструмента — это обращение к
работающей информационной базе по HTTP и возврат её ответа вызывающей стороне.

### 1.2. Что такое MCP и зачем он нужен при работе с учётной базой

MCP (Model Context Protocol) — протокол взаимодействия между клиентским приложением, в
котором работает языковая модель, и внешней программой-сервером, предоставляющей доступ
к данным и действиям. Сервер при подключении сообщает клиенту своё имя и версию (в данном
случае — `aprovodka` и `4.3.0`), а затем — перечень объявленных им инструментов и
сценариев.

Инструмент (tool) — это именованная операция с описанием на естественном языке и строгой
схемой аргументов: какие параметры принимаются, какие из них обязательны, какого они типа.
Модель не «додумывает» способ обращения к базе — она выбирает инструмент из списка и
заполняет его аргументы, а фактический запрос формирует уже программа-сервер.

Практическая разница именно в этом. Без MCP модель работает с текстом *о* базе: с
выгрузкой, скриншотом, пересказом. Такой текст устаревает в момент создания, его нельзя
уточнить встречным вопросом, а любая деталь, не попавшая в выгрузку, для модели не
существует. С MCP модель работает *с самой базой*: запрашивает список сущностей,
уточняет состав полей конкретного документа, считает количество записей, читает остатки
на дату. Ответ на уточняющий вопрос приходит из базы, а не из ранее полученного текста.

Из этого следуют два практических свойства продукта.

Во-первых, инструмент задаёт границу возможного. Модель может вызвать только то, что
объявлено сервером; операции, не имеющей соответствующего инструмента, для неё не
существует. Так, в 1С отсутствует механизм подписки на события (webhook), поэтому вместо
несуществующей подписки объявлен инструмент `poll_changes_since` — опрос изменений по
временной метке; отдельный инструмент `list_subscriptions` существует специально для
того, чтобы явно сообщить об отсутствии подписок и предотвратить попытку модели
«вызвать» несуществующий механизм.

Во-вторых, реальные права всегда определяются не описанием инструмента, а ролью
пользователя «1С:Предприятие», под которым выполняется подключение. Инструменты
принимают выражения отбора OData в исходном виде — это сделано намеренно, поэтому
ограничивать область чтения и записи следует настройкой роли в информационной базе, а не
формулировкой аргументов.

### 1.3. Для кого предназначен продукт

Продукт рассчитан на четыре роли, каждая из которых пользуется своей частью
функциональности.

**Бухгалтер, экономист, руководитель.** Получает ответы на вопросы по данным своей базы
без постановки задачи программисту: остатки и обороты по счетам (регистр бухгалтерии и
его виртуальные таблицы), остатки по складам (регистр накопления), состояние конкретного
документа и его табличных частей, последние документы заданного вида. Работа ведётся
формулировками на естественном языке в привычном клиентском приложении.

**Аналитик.** Строит выборки, недоступные штатными отчётами: произвольный запрос OData с
отбором, сортировкой, ограничением выборки и подсчётом количества, параллельное
выполнение до 50 запросов одним вызовом (`batch_query`), сопоставление остатков с
движениями. Результат выдаётся в машиночитаемом виде и пригоден для дальнейшей обработки.

**Внедренец и консультант.** Быстро осваивает незнакомую базу: сценарий
`inventory-database` последовательно вызывает офлайн-пресет конфигурации, перечисление
сущностей по группам, подсчёт записей и разбор полей ключевых объектов. Пресеты типовых
конфигураций подсказывают, что именно искать, но каждая сущность в них снабжена признаком
достоверности: `verified` — имя встречено в цитируемом источнике, `common` — типовое имя
из практики, первоисточником не подтверждённое. Имена с признаком `common` следует
проверять инструментами `list_entities` и `describe_entity` на конкретной базе. Пресет —
карта, а не гарантия: любая база могла быть доработана.

**Разработчик и специалист по интеграциям.** Использует продукт как готовый транспортный
слой к OData: произвольные запросы, пакетные операции создания и изменения, опрос
изменений по курсору, транспорт Streamable HTTP для удалённого развёртывания, фильтрацию
состава инструментов переменной `ONEC_SERVICES` и контур безопасности записи с журналом
аудита.

### 1.4. Архитектура

Схема взаимодействия состоит из трёх звеньев:

```text
┌──────────────────────────────┐
│ MCP-клиент                   │   Claude Desktop, Cursor, Windsurf,
│ (приложение с ИИ-моделью)    │   VS Code (Copilot) и другие клиенты MCP
└──────────────┬───────────────┘
               │  MCP: stdio (по умолчанию)
               │  либо Streamable HTTP (POST /mcp, GET /mcp, DELETE /mcp)
┌──────────────▼───────────────┐
│ aprovodka                    │   процесс Node.js;
│ 34 инструмента, 11 модулей   │   проверка аргументов, сборка URL OData,
│ 3 сценария (промпта)         │   разбор ошибок 1С, контур безопасности записи
└──────────────┬───────────────┘
               │  HTTP(S), аутентификация HTTP Basic
               │  <ONEC_BASE_URL>/odata/standard.odata/
┌──────────────▼───────────────┐
│ «1С:Предприятие»             │   опубликованная информационная база,
│ штатный интерфейс OData 3.0  │   права определяются ролью пользователя 1С
└──────────────────────────────┘
```

Главное свойство архитектуры: **со стороны информационной базы ничего не
дорабатывается**. Конфигурация не изменяется, код на встроенном языке не пишется,
расширение конфигурации не устанавливается, внешние обработки не подключаются.
aprovodka обращается к базе снаружи, по протоколу HTTP, к тому же стандартному интерфейсу
OData, который платформа предоставляет штатно. Единственные действия на стороне 1С —
административные: публикация информационной базы на веб-сервере, включение нужных
объектов в состав стандартного интерфейса OData в Конфигураторе и создание пользователя с
подходящей ролью (порядок выполнения описан в разделе 3).

Отсюда следуют границы применимости, о которых лучше знать заранее. Продукт видит ровно
то, что опубликовано в составе интерфейса OData: если сущность не включена в этот состав,
она не появится в перечне и обратиться к ней нельзя. Продукт не выполняет
конфигурационную бизнес-логику иначе, чем это делает сама платформа при обращении по
OData: проведение и отмена проведения документа выполняются связанными действиями
`Post()` и `Unpost()` платформы, а не воспроизведением алгоритма проведения. Наконец, в
интерфейсе OData платформы отсутствуют пакетная конечная точка `$batch` и подписки на
события — пакетность в продукте реализована на стороне клиента (параллельная отправка
запросов с ограничением числа одновременных), а отслеживание изменений — опросом.

Данные не покидают контур предприятия по вине сервера: aprovodka устанавливается рядом с
базой или на рабочем месте пользователя и обращается только к тому адресу, который указан
в параметре `ONEC_BASE_URL`; обращения на другой источник по абсолютному адресу
отклоняются. При этом следует учитывать, что содержимое ответов передаётся в
MCP-клиент — выбор клиентского приложения и модели остаётся ответственностью
организации, внедряющей продукт.

## 2. Системные требования

### 2.1. Среда исполнения

| Параметр | Требование |
|---|---|
| Среда исполнения | Node.js версии 18.0.0 или выше (`engines.node: ">=18.0.0"`) |
| Операционная система | Любая, поддерживаемая указанной версией Node.js |
| Дистрибуция | Пакет npm `@theyahia/aprovodka`, исполняемый файл `aprovodka` |
| Клиентское приложение | Приложение с поддержкой протокола MCP |
| Сетевой доступ | HTTP(S) до опубликованной информационной базы «1С:Предприятие» |
| Сетевой порт (только для транспорта HTTP) | Задаётся переменной `HTTP_PORT` |

Продукт распространяется в виде пакета для среды Node.js; собственных нативных
компонентов, требующих компиляции под конкретную операционную систему, в состав поставки
не входит. Прямые зависимости версии 4.3.0: `@modelcontextprotocol/sdk`, `express`, `zod`
и собственная библиотека `@theyahia/mcp-core`; все они распространяются по лицензии MIT.

Об отечественных операционных системах. Astra Linux, РЕД ОС и другие ОС на базе Linux,
для которых доступна среда Node.js требуемой версии, технически подходят: продукт
кроссплатформенный и платформенно-зависимого кода не содержит. Однако протокол испытаний
на конкретных отечественных дистрибутивах на дату выпуска версии 4.3.0 **не оформлен**, и
подтверждать совместимость с ними как проверенную неправомерно. До оформления протокола
работоспособность в конкретном дистрибутиве следует подтвердить самостоятельно: установить
пакет, запустить сервер и проверить ответ конечной точки `GET /health`.

Требования к объёму оперативной памяти и дискового пространства в исходных материалах не
зафиксированы, поэтому в руководстве не приводятся. Сервер представляет собой один
процесс Node.js; фактическое потребление памяти в конкретной установке возвращает
конечная точка `GET /health` (поле `memory_mb`) вместе с версией, числом
зарегистрированных инструментов и временем работы процесса.

### 2.2. Требования к «1С:Предприятие»

Продукт работает со штатным интерфейсом OData 3.0 платформы «1С:Предприятие» 8.3.
Минимальный номер релиза платформы в исходных материалах не зафиксирован — при
необходимости уточните его по документации платформы.

Для работы должны быть выполнены три условия.

**1. Информационная база опубликована на веб-сервере.** Обращение выполняется по тому же
адресу, по которому доступен веб-клиент базы, без завершающей части `/odata/...`. Этот
адрес указывается в параметре `ONEC_BASE_URL`; конечная точка OData формируется
программой самостоятельно по шаблону `<ONEC_BASE_URL>/odata/standard.odata/`.

**2. Включён стандартный интерфейс OData, и в его состав входят нужные объекты.**
Публикация OData и состав публикуемых объектов настраиваются в Конфигураторе. Если
сущность отсутствует в ответе инструмента `list_entities`, наиболее вероятная причина —
она не включена в состав стандартного интерфейса OData; это настройка публикации, а не
право доступа. Проверьте это на своей базе прежде, чем искать причину в правах.

**3. Создан пользователь информационной базы с необходимой ролью.** Аутентификация —
HTTP Basic, логин и пароль передаются параметрами `ONEC_LOGIN` и `ONEC_PASSWORD`
(поддерживаются также устаревшие имена `1C_LOGIN`, `1C_PASSWORD`, `1C_BASE_URL`).
Область данных, доступных ИИ-агенту, определяется именно правами этого пользователя.
Рекомендуется заводить отдельного пользователя с минимально достаточным набором прав, а
для сценариев только чтения — пользователя без прав на изменение данных.

Дополнительно следует учитывать особенности платформы, влияющие на состав требований.
Имена сущностей и реквизитов в типовых конфигурациях записаны кириллицей — программа
кодирует их в адресе запроса самостоятельно. Используется именно OData версии 3.0, а не
4.0: поиск подстроки выполняется функцией `substringof`, даты записываются литералом вида
`datetime'2026-01-31T00:00:00'`. Время возвращается по часовому поясу сервера 1С, а не в
UTC, поэтому границы периодов следует задавать явно.

Точный порядок публикации базы, включения OData и создания пользователя приведён в
разделе 3 «Установка и первичная настройка». Настоящий раздел перечисляет только
требования, которые должны быть выполнены до установки.

## 3. Установка и первичная настройка

Установка состоит из трёх частей: подготовка базы 1С, установка пакета `@theyahia/aprovodka`, описание сервера в конфигурации MCP-клиента. Порядок именно такой: без стандартного интерфейса OData сервер запустится, но все обращения к базе завершатся ошибкой.

### 3.1 Подготовка 1С: публикация базы и стандартный интерфейс OData

Информационная база должна удовлетворять трём условиям одновременно.

1. **База опубликована на веб-сервере.** aprovodka обращается к 1С только по HTTP, штатными средствами платформы; ни внешних обработок, ни кода на встроенном языке в базу не добавляется.
2. **Включён стандартный интерфейс OData.** Включается в Конфигураторе при публикации; наименования пунктов меню зависят от версии платформы — сверяйтесь с документацией 1С.
3. **Нужные объекты метаданных входят в состав публикуемого интерфейса.** Состав задаётся отдельно от самой публикации.

Третий пункт — источник самой частой ошибки первого запуска. Если сущность не видна в выдаче `list_entities`, наиболее вероятно, что она не включена в состав стандартного интерфейса OData в Конфигураторе. Это настройка публикации, а не право доступа: выдача роли такую сущность не «проявит».

Адрес для переменной `ONEC_BASE_URL` — тот же URL, по которому открывается веб-клиент 1С, без суффикса `/odata/...`, например `http://server:8080/base`. Завершающие `/` сервер отбрасывает сам. Точка входа OData собирается так:

```
${ONEC_BASE_URL}/odata/standard.odata/
```

Проверить публикацию можно до установки пакета — запросом корня интерфейса с теми учётными данными, которые вы планируете передать серверу:

```bash
curl -u your_login:your_password 'http://server:8080/base/odata/standard.odata/?$format=json'
```

Документ сервиса со списком наборов сущностей в ответе означает, что публикация выполнена. Ответ `401` — неверные учётные данные либо нет права на вход; `404` — интерфейс OData по этому адресу не опубликован.

Дальше состав опубликованных объектов смотрят средствами сервера: `list_entities` — наборы сущностей с фильтрацией по группам, `get_metadata` — полный `$metadata` (EDMX/XML), `describe_entity` — поля одной сущности по образцовой записи. `get_config_preset` работает офлайн и `ONEC_BASE_URL` не требует.

### 3.2 Пользователь 1С и настройка роли

aprovodka авторизуется в 1С по HTTP Basic: логин и пароль задаются переменными `ONEC_LOGIN` и `ONEC_PASSWORD`. Это учётная запись обычного пользователя базы; собственного механизма авторизации у сервера нет.

**Объём доступа задаётся ролью пользователя 1С, а не аргументами инструментов.** Инструменты `get_catalogs`, `get_documents`, `odata_query` и другие принимают `$filter`, `$select`, `$orderby` строкой и передают их в OData как есть; сквозная передача сделана намеренно. Ограничить круг читаемых и изменяемых данных подбором аргументов поэтому нельзя: модель, формирующая вызов, может составить любой допустимый запрос. Надёжная граница одна — права роли учётной записи, под которой работает сервер.

Практические следствия:

- Заводите **отдельного пользователя под интеграцию**. Запись администратора и личные записи сотрудников не подходят: в журнале регистрации действия сервера станут неотличимы от действий человека.
- Выдавайте роль по минимуму прав. Для сценариев только чтения — роль без прав на добавление, изменение, удаление и проведение. Инструменты записи останутся в списке, но их вызов вернёт ошибку прав.
- Ошибки прав распознаются: «Нарушение прав доступа» / «Недостаточно прав» относятся к категории `permission_denied` с подсказкой, что учётная запись валидна, но роли не хватает.
- Какие роли нужны для входа и для доступа через интерфейс OData — вопрос настроек конкретной базы; уточняйте у администратора.

Дополнительно к роли есть гейт записи `ONEC_WRITE_MODE` (режимы `preview` и `approval`) и журнал операций `ONEC_AUDIT_LOG` — не замена роли, а второй рубеж: роль ограничивает, что физически возможно, гейт — что выполняется без явного подтверждения. Их настройка — в разделах о конфигурировании и безопасности.

### 3.3 Установка пакета

Требования к среде: **Node.js 18.0.0 или выше** (поле `engines` пакета). Пакет — `@theyahia/aprovodka`, исполняемый файл — `aprovodka`, версия — 4.3.0.

**Вариант 1 — запуск через `npx` (контур с доступом к npmjs.com).** Эта команда прописывается в конфигурациях клиентов ниже; доступ к реестру npm нужен при каждом запуске.

```bash
npx -y @theyahia/aprovodka
```

**Вариант 2 — глобальная установка.** Разовая загрузка, дальше запуск локального файла:

```bash
npm install -g @theyahia/aprovodka
```

**Вариант 3 — офлайн-установка через `npm pack` (контуры без доступа к npmjs.com).** На машине с доступом к реестру формируется архив пакета:

```bash
npm pack @theyahia/aprovodka
# получится файл вида theyahia-aprovodka-4.3.0.tgz
```

Архив переносится в закрытый контур и устанавливается локально:

```bash
npm install -g ./theyahia-aprovodka-4.3.0.tgz
```

В конфигурации MCP-клиента после этого указывается команда `aprovodka` вместо `npx` — обращений к npmjs.com при запуске не будет. Тот же архив годится для внутреннего зеркала реестра.

Проверить установленный пакет до подключения к клиенту можно запуском в режиме HTTP и обращением к `GET /health` (3.7).

### 3.4 Подключение к Claude Desktop

Конфигурация описывается в файле `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "aprovodka": {
      "command": "npx",
      "args": ["-y", "@theyahia/aprovodka"],
      "env": {
        "ONEC_BASE_URL": "http://server:8080/base",
        "ONEC_LOGIN": "your_login",
        "ONEC_PASSWORD": "your_password"
      }
    }
  }
}
```

| Поле | Назначение |
|---|---|
| `mcpServers` | Раздел конфигурации клиента со всеми подключёнными MCP-серверами. |
| `aprovodka` (ключ) | Имя, под которым сервер отображается в клиенте. Произвольное; учтите, что имя сервера в MCP-рукопожатии начиная с 4.0.0 — `aprovodka`. |
| `command` | Запускаемый файл: `npx` — при установке из реестра, `aprovodka` — при глобальной или офлайн-установке. |
| `args` | Аргументы команды. `-y` подавляет вопрос `npx` об установке пакета; для установленного `aprovodka` массив пуст. |
| `env` | Переменные окружения процесса. Обязательны `ONEC_BASE_URL`, `ONEC_LOGIN`, `ONEC_PASSWORD`; сюда же — необязательные `ONEC_SERVICES`, `ONEC_WRITE_MODE`, `ONEC_AUDIT_LOG` и прочие из раздела 4. |

Транспорт здесь — stdio: клиент сам порождает процесс и общается с ним через стандартные потоки. Переменные окружения ОС дочернему процессу могут не наследоваться, поэтому параметры задаются именно в блоке `env`. Вместо `ONEC_BASE_URL`, `ONEC_LOGIN`, `ONEC_PASSWORD` допустимы устаревшие `1C_BASE_URL`, `1C_LOGIN`, `1C_PASSWORD`. После правки файла клиент нужно перезапустить: конфигурация читается при старте.

### 3.5 Подключение к Cursor / Windsurf

Обе среды используют тот же формат: в их настройках MCP добавляется такой же блок под ключом `mcpServers` с полями `command`, `args`, `env`. Отдельной сборки не требуется — транспорт тот же stdio.

### 3.6 Подключение к VS Code (Copilot)

Конфигурация помещается в файл `.vscode/mcp.json` рабочей области. Обратите внимание на отличие: корневой ключ здесь `servers`, а не `mcpServers`.

```json
{
  "servers": {
    "aprovodka": {
      "command": "npx",
      "args": ["-y", "@theyahia/aprovodka"],
      "env": {
        "ONEC_BASE_URL": "http://server:8080/base",
        "ONEC_LOGIN": "your_login",
```

Файл лежит в рабочей области и часто попадает под контроль версий, поэтому пароль 1С в нём хранить не следует; механизм подстановки секретов берите штатный для вашей версии VS Code.

### 3.7 Режим Streamable HTTP

Для удалённых и многопользовательских установок сервер запускается самостоятельной HTTP-службой, а не дочерним процессом клиента. Режим включается переменной `HTTP_PORT` либо флагом `--http`; при одном флаге используется порт 3000.

```bash
HTTP_PORT=3000 \
ONEC_BASE_URL=http://server:8080/base \
ONEC_LOGIN=admin \
ONEC_PASSWORD=secret \
npx @theyahia/aprovodka
# либо: npx @theyahia/aprovodka --http
```

| Метод и путь | Назначение |
|---|---|
| `POST /mcp` | Приём запросов MCP; запрос инициализации создаёт сессию. |
| `GET /mcp` | Поток событий SSE существующей сессии. |
| `DELETE /mcp` | Завершение сессии. |
| `GET /health` | Состояние процесса, без авторизации. |

Сессии различаются по заголовку `mcp-session-id`; `GET /mcp` и `DELETE /mcp` без известного идентификатора отклоняются. По сигналам `SIGINT` и `SIGTERM` открытые транспорты закрываются, после чего процесс завершается.

`GET /health` возвращает JSON с полями `status` (штатно `"ok"`), `server`, `version`, `uptime` (работа процесса, секунды), `memory_mb` (занятая память, МБ), `tools` (число зарегистрированных инструментов). Иллюстративный пример ответа — не вывод реальной установки:

```json
{
  "status": "ok",
  "server": "aprovodka",
  "version": "4.3.0",
  "uptime": 137,
  "memory_mb": 62,
  "tools": 34
}
```

Значение `tools` вычисляется по набору включённых модулей (`ONEC_SERVICES`) и увеличивается на два при включённом гейте записи: в режимах `preview` и `approval` дополнительно регистрируются `approve_write` и `rollback_write`. Так проверяют, что фильтр модулей и режим записи применились как задумано.

Два обстоятельства при развёртывании HTTP-режима:

- **Учётные данные 1С берутся из окружения процесса и одни на все сессии.** Все подключившиеся работают в базе от имени учётной записи из `ONEC_LOGIN`. Разграничение между потребителями службы делается внешними средствами: отдельный процесс со своей записью на каждый контур доступа либо ограничение сетевого доступа к порту.
- **Кросс-доменные браузерные вызовы по умолчанию запрещены.** Список разрешённых источников пуст, заголовок `Access-Control-Allow-Origin` неизвестным источникам не выдаётся. На небраузерных клиентов это не влияет.

Порт HTTP-режима не следует публиковать в недоверенной сети: собственной аутентификации у эндпоинтов `/mcp` нет, доступ к ним равносилен доступу к базе в объёме прав пользователя 1С. Штатный вариант — внутренний контур либо обратный прокси со своей аутентификацией.

## 4. Конфигурирование

Собственных файлов конфигурации у продукта нет: вся настройка выполняется переменными
окружения — в блоке `env` конфигурации MCP-клиента либо в окружении процесса.

### 4.1 Переменные окружения `ONEC_*`

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `ONEC_BASE_URL` | да | — | URL опубликованной информационной базы, например `http://server:8080/base` — тот же адрес, что у веб-клиента, без суффикса `/odata/...`. Завершающие `/` отбрасываются; путь к OData (`/odata/standard.odata/`) сервер добавляет сам |
| `ONEC_LOGIN` | да | — | Имя пользователя 1С для HTTP Basic |
| `ONEC_PASSWORD` | да | — | Пароль этого пользователя |
| `ONEC_SERVICES` | нет | `all` | Список модулей через запятую (раздел 4.2) |
| `ONEC_WRITE_MODE` | нет | `off` | Режим гейта записи: `off`, `deny`, `preview`, `approval` (раздел 5.4) |
| `ONEC_APPROVAL_TTL_SEC` | нет | `300` | Время жизни одобрения записи, секунды |
| `ONEC_AUDIT_LOG` | нет | не задана — аудит выключен | Путь к файлу аудит-леджера в формате JSONL |
| `ONEC_AUDIT_ACTOR` | нет | значение `ONEC_LOGIN` | Имя субъекта, записываемое в леджер |
| `HTTP_PORT` | нет | `3000` при запуске в HTTP-режиме | Порт транспорта Streamable HTTP (раздел 4.3) |

Отсутствие адреса или пары логин/пароль не остаётся незамеченным: первый же вызов
инструмента, обращающегося к базе, завершается ошибкой, называющей недостающую переменную.
Исключение — `get_config_preset`: он работает офлайн и `ONEC_BASE_URL` не требует.

Значения разбираются терпимо к оформлению, но без предупреждений:

- `ONEC_WRITE_MODE` приводится к нижнему регистру с отбрасыванием пробелов; любое значение,
  кроме `deny`, `preview` и `approval`, трактуется как `off`. Опечатка в имени режима тихо отключает
  гейт — проверяйте состояние по наличию инструментов `approve_write` и `rollback_write`.
- `ONEC_APPROVAL_TTL_SEC`: нечисловое значение, ноль или отрицательное заменяются на 300.
- `ONEC_AUDIT_ACTOR` при отсутствии берётся из `ONEC_LOGIN`, затем из `1C_LOGIN`, и лишь
  затем в леджер попадает `unknown`.

**Обратная совместимость с `1C_*`.** Ранние версии использовали префикс `1C_`. Как
запасной вариант принимаются три переменные: `1C_BASE_URL`, `1C_LOGIN`, `1C_PASSWORD`.
Приоритет всегда у `ONEC_*`; `1C_*` читается, только если одноимённая `ONEC_*` не задана.
У остальных переменных псевдонимов нет. Смешивать префиксы в одной конфигурации не
рекомендуется — это затрудняет диагностику.

Размещение переменных в конфигурации конкретного клиента описано в разделе 3. Таймаут
запроса к 1С (15 секунд) и число попыток при сбое (3, то есть два повтора) заданы в коде и переменными
окружения не настраиваются.

### 4.2 Фильтрация модулей `ONEC_SERVICES`

Описание каждого инструмента и схема его аргументов передаются языковой модели при каждом
обращении. Все 34 инструмента одновременно нужны редко, а их описания занимают контекст,
которого потом не хватает на данные. `ONEC_SERVICES` ограничивает набор регистрируемых
модулей.

| Модуль | Инструментов | Состав |
|---|---|---|
| `meta` | 5 | Обнаружение состава базы, отключить нельзя (см. ниже) |
| `catalogs` | 3 | Справочники: чтение, создание, изменение |
| `documents` | 7 | Документы: чтение, создание, изменение, проведение и его отмена, удаление, табличные части |
| `registers` | 3 | Регистры сведений и накопления, остатки |
| `accounting` | 2 | Регистр бухгалтерии и его виртуальные таблицы |
| `constants` | 2 | Константы: чтение и запись |
| `shortcuts` | 5 | Поиск, выборка по `Ref_Key`, подсчёт, пометка удаления, последние документы |
| `reports` | 1 | Отчёт по URL HTTP-сервиса |
| `odata` | 1 | Произвольный запрос OData |
| `batch` | 3 | Параллельные пакетные операции |
| `changes` | 2 | Опрос изменений по курсору |

Правила разбора: значение делится по запятым, у имён отбрасываются пробелы и приводится
регистр; неизвестные имена игнорируются молча. Пустая строка, значение `all` или отсутствие
переменной означают «все модули».

```bash
ONEC_SERVICES=catalogs,documents npx @theyahia/aprovodka
```

Такой запуск даёт 15 инструментов: 5 из `meta`, 3 из `catalogs`, 7 из `documents`.
Фактическое число сервер сообщает в ответе `GET /health` в HTTP-режиме.

**Почему `meta` отключить нельзя.** Это единственный способ узнать, что есть в конкретной
базе: `list_entities` перечисляет сущности по группам, `describe_entity` показывает поля по
одной записи, `get_metadata` отдаёт полный `$metadata`, `get_config_preset` даёт офлайновую
подсказку по типовой конфигурации. Имена сущностей в 1С зависят от конфигурации и
доработок; без модуля `meta` модель начинает их угадывать. Поэтому `meta` регистрируется
всегда; перечислять его в списке допустимо, но не обязательно.

Фильтрация модулей — средство экономии контекста, но **не средство разграничения прав**:
она действует на стороне сервера и меняется тем, кто управляет его окружением. Ограничения
доступа задаются ролью пользователя 1С (раздел 5.2).

### 4.3 `HTTP_PORT` и `MCP_DISABLE_SANITIZE`

**`HTTP_PORT`.** По умолчанию сервер работает по транспорту stdio, как его запускают
настольные MCP-клиенты. Если задана переменная `HTTP_PORT` либо указан ключ `--http`,
вместо stdio поднимается транспорт Streamable HTTP; порт берётся из `HTTP_PORT`, при
запуске с `--http` без переменной используется 3000. Конечные точки (`POST`, `GET`,
`DELETE /mcp` и `GET /health`) описаны в разделе 3.7.

Сессии различаются заголовком `mcp-session-id`. Кросс-доменные запросы браузера по
умолчанию запрещены: список разрешённых источников CORS пуст, пока его явно не задали.
HTTP-режим предназначен для внутреннего контура; публиковать порт наружу без обратного
прокси с TLS и собственной аутентификацией не следует — авторизации клиента здесь нет.

**`MCP_DISABLE_SANITIZE`.** По умолчанию текст, возвращаемый инструментами, проходит
проверку на попытки перехвата инструкций модели (раздел 5.3) и усечение по длине.
Переменная отключает обе обработки, причём срабатывает только точное значение `true`;
любое иное оставляет защиту включённой. Отключайте, лишь если содержимое базы полностью
доверенное и фильтр мешает читать деловые данные.

## 5. Безопасность

### 5.1 HTTP Basic и хранение учётных данных

REST-интерфейс 1С:Предприятия использует аутентификацию HTTP Basic; иных способов (токены,
OAuth) продукт не поддерживает. Логин и пароль из `ONEC_LOGIN` / `ONEC_PASSWORD`
подставляются в заголовок каждого запроса к базе. Следствия:

- Basic передаёт пару «логин: пароль» в кодировке base64, то есть в открытом виде. Между
  сервером и 1С нужен либо TLS (`https://` в `ONEC_BASE_URL`), либо доверенный сегмент сети.
- Пароль хранится в конфигурации MCP-клиента или в окружении процесса: защитите файл
  правами доступа ОС и не помещайте в систему контроля версий.
- Заводите для интеграции отдельного пользователя 1С, а не учётную запись сотрудника —
  это делает осмысленными журналы 1С и поле `actor` в леджере и позволяет отозвать доступ,
  не затрагивая людей. Нескольких операторов различайте через `ONEC_AUDIT_ACTOR`.

### 5.2 Разграничение прав ролью 1С

Инструменты `get_catalogs`, `get_documents`, `odata_query` и другие принимают `$filter`,
`$select`, `$orderby` в исходном виде и передают в OData как есть. Это сделано намеренно:
без произвольного отбора работа с незнакомой базой невозможна. Отсюда следует, что
**аргументы инструментов не являются границей доступа** — имея `odata_query`, модель может
обратиться к любой сущности, опубликованной в OData и разрешённой пользователю.

Единственная надёжная граница — роль пользователя 1С, под которым работает сервер:

- Ограничивайте состав объектов правами роли, а не набором модулей `ONEC_SERVICES`. Для
  аналитических сценариев достаточно роли только на чтение — тогда пишущие инструменты
  отклонит сама платформа.
- В публикации OData перечисляйте только объекты метаданных, нужные интеграции: то, что не
  опубликовано, недоступно в принципе.
- Отказ по правам приходит модели в разобранном виде: категория `permission_denied` и
  рекомендация обратиться к администратору 1С за нужной ролью.

### 5.3 Защита обмена: инъекции, посторонние адреса, идентификаторы

**Фильтр перехвата инструкций.** Данные из базы могут содержать текст, адресованный не
человеку, а модели («игнорируй предыдущие инструкции», «теперь ты …», псевдотеги
`<system>`). В выводе инструментов он заменяется меткой `[filtered]`. Слишком длинный ответ
усекается (порог 50 000 знаков) с припиской, что показана только часть и отбор надо сузить.
Отключается лишь переменной `MCP_DISABLE_SANITIZE` (раздел 4.3).

**Проверка адреса.** Инструмент `get_report` принимает путь к HTTP-сервису (`/hs/...`), и
модель может подставить туда абсолютный URL. Источник такого URL (схема, узел, порт)
сверяется с источником `ONEC_BASE_URL`, при несовпадении следует отказ: «Заблокирован
запрос на сторонний хост …: разрешён только …». Без проверки запрос к чужому узлу ушёл бы
вместе с учётными данными 1С.

**Идентификаторы.** Аргумент `ref_key` проверяется по шаблону GUID (36 символов вида
`01234567-89ab-cdef-0123-456789abcdef`) до того, как попадёт в путь внутри `guid'…'`.
Неверный формат отклоняется с явной ошибкой, поэтому подстановка через ключ невозможна ни в
одной операции с ключом: изменение, проведение и его отмена, удаление, выборка по ключу,
установка пометки удаления.

**Экранирование строк.** Одинарная кавычка в строковых значениях удваивается, как того
требует OData, — значение не может закрыть литерал и дописать своё условие. Для аргументов
виртуальных таблиц регистров этого мало: символы `%`, `?`, `#`, `/`, `&` и пробел
дополнительно кодируются процентной нотацией, иначе `?` внутри значения превратил бы
остаток пути в строку запроса и подменил бы параметры самого инструмента. Проверка
добавлена в версии 4.1.0 вместе с исправлением такой уязвимости в
`get_accumulation_balance` и закрыта регрессионным тестом.

### 5.4 Гейт записи

Чтение из учётной базы и запись в неё — разные по последствиям операции. Гейт переводит
все изменяющие вызовы в режим предварительного просмотра либо явного подтверждения.

| `ONEC_WRITE_MODE` | Поведение |
|---|---|
| `off` (по умолчанию) | Запись выполняется сразу. Поведение совпадает с версиями до 4.1 |
| `deny` | **Режим только чтения.** 12 пишущих инструментов не регистрируются вовсе: модель их не видит в списке инструментов и вызвать не может — это не отказ при вызове, а отсутствие инструмента. В реестре остаются 22 читающих. Штатный режим работ по сверке на чужой базе: на время работ сервер запускается так, что инструменты записи физически отсутствуют |
| `preview` | Запись **не выполняется никогда**. Каждый пишущий вызов возвращает описание того, что произошло бы: метод, путь, изменения «было → станет» и `op_hash` |
| `approval` | Первый вызов возвращает то же описание и отказ. Операция выполняется только после `approve_write` с этим `op_hash` и повторного вызова того же инструмента с теми же аргументами |

Перехват выполнен в единственном месте — функциях записи HTTP-клиента, через которые
проходят все изменяющие операции, поэтому ни один инструмент, существующий или добавленный
позже, не может записать в обход гейта.

`op_hash` — 16 шестнадцатеричных знаков от хэша метода, пути и тела запроса в каноническом
виде; порядок полей в теле на результат не влияет. Любое изменение аргумента даёт другой
`op_hash`, поэтому одобрение нельзя перенести на иную операцию.

**Инструменты `approve_write` и `rollback_write`** регистрируются только в режимах
`preview` и `approval`; в `off` и `deny` их в списке нет (в `deny` одобрять нечего —
пишущих инструментов в реестре нет).

- `approve_write(op_hash, reason?)` — одобряет одну ожидающую операцию. Работает только в
  режиме `approval`; в `preview` возвращает ошибку, поскольку там запись невозможна в
  принципе. Одобрение одноразовое, живёт `ONEC_APPROVAL_TTL_SEC` секунд и хранится в
  памяти процесса — после перезапуска сервера его нет. `reason` попадает в леджер.
- `rollback_write(token)` — выполняет обратную операцию по токену из результата записи.
  Определены: проведение → отмена проведения, отмена проведения → проведение
  (неоперативное), изменение полей → возврат ранее прочитанных значений, переключение
  `DeletionMark`. Токен одноразовый, хранится в памяти, число токенов ограничено сотней
  (старые вытесняются). Сам откат повторно не подтверждается, но протоколируется.

**Что откатить нельзя.** Создание записи и физическое удаление обратной операции не имеют.
Токен для них не выдаётся; вместо него возвращается поле `irreversible_reason` с причиной
и способом действовать вручную — для созданной записи взять `Ref_Key` из результата и
установить пометку удаления, а вместо физического удаления пользоваться пометкой удаления
как обратимой.

В режиме `off` ни поля `irreversible_reason`, ни какого-либо иного служебного конверта не
возвращается: инструмент отдаёт ответ «1С:Предприятия» как есть. Прежние значения при этом
никто не считывает, поэтому автоматического отката у изменения, сделанного в режиме `off`,
не существует — это ещё один довод в пользу режима `approval` на боевой базе.

**Аудит-леджер.** Если задана `ONEC_AUDIT_LOG`, каждая операция дописывается строкой JSON
в указанный файл: отметка времени, субъект (`ONEC_AUDIT_ACTOR`) и событие — `preview`,
`approved`, `attempt`, `executed`, `failed`, `rollback_token_issued`, `rollback_attempt`,
`rollback_executed`. Запись `attempt` делается **до** обращения к 1С, и при сбое записи в
файл операция не выполняется вовсе. Отсутствие строки в леджере никогда не означает
незаметного изменения данных. Тела запросов пишутся полностью — иначе журнал бесполезен, —
поэтому файл защищайте так же, как учётные данные базы.

**Честная граница механизма.** `approve_write` — такой же вызов инструмента, как и
остальные. Гейт гарантирует, что запись невозможна без отдельного явного шага с точным
`op_hash` операции, но сам по себе не доказывает, что подтверждение дал человек. Роль
«кнопки» выполняет интерфейс подтверждения вызовов в MCP-клиенте — выбирайте клиент,
который такие подтверждения показывает.

**Состав ответа гейта.** Предпросмотр: `write_safety` (`preview`), `mode`, `op_hash`,
`operation` (метод, сущность, `ref_key`, действие, путь, тело), `changes` (вид изменения и
разбор полей «`from` → `to`», если текущее состояние удалось прочитать), `reversible`,
`rollback_plan` либо `irreversible_reason`, `next_step`. Ответ выполненной операции:
`write_safety` (`executed`), `op_hash`, `rollback` с токеном либо `irreversible_reason`,
`result` — исходный ответ 1С.

## 6. Базовые понятия

### 6.1 OData 3.0: параметры запроса

Все инструменты чтения строят один и тот же URL к штатному интерфейсу
`${ONEC_BASE_URL}/odata/standard.odata/` и различаются только тем, какие параметры
подставляют. Параметры, перечисленные ниже, доступны напрямую в `odata_query`;
у специализированных инструментов (`get_catalogs`, `get_documents`, `get_register` и др.)
набор уже́ — состав указан в разделе 7.

| Параметр | Смысл | Пример значения |
|---|---|---|
| `$filter` | Условие отбора записей на стороне 1С | `Date ge datetime'2026-04-01T00:00:00' and Posted eq true` |
| `$select` | Список возвращаемых полей — сокращает объём ответа | `Ref_Key,Number,Date` |
| `$expand` | Разворачивает связанную сущность или табличную часть внутрь ответа | `Товары` |
| `$top` | Сколько записей вернуть | `100` |
| `$skip` | Сколько записей пропустить (постраничный обход вместе с `$top`) | `200` |
| `$orderby` | Сортировка; `desc` — по убыванию | `Date desc` |
| `$inlinecount` | Добавляет в ответ общее число записей, подходящих под `$filter` | `allpages` |

Значения по умолчанию и границы задаются схемой конкретного инструмента: в `odata_query`
`top` принимает 1…5000 (по умолчанию 100), `skip` — от 0 (по умолчанию 0), `inlinecount` —
логический флаг, который разворачивается в `$inlinecount=allpages`. У `get_documents`
верхняя граница `top` — 1000. Инструмент `count_entities` использует комбинацию
`$top=0` + `$inlinecount=allpages` и возвращает только число, не выгружая записи.

Формы литералов, которые понимает 1С (`src/presets/common.ts`):

| Тип | Форма | Замечание |
|---|---|---|
| Строка | `'текст'` | Одинарная кавычка внутри удваивается: `'О''Коннор'` |
| Дата и время | `datetime'2026-01-31T00:00:00'` | Не ISO-строка без префикса |
| GUID | `guid'01234567-89ab-cdef-0123-456789abcdef'` | |
| Подстрока | `substringof('подстрока',Description)` | Это OData 3.0; функции `contains()` здесь нет |
| Ссылка составного типа | `cast(guid'…','Document_ПоступлениеТоваровУслуг')` | Для полей `Recorder`, `ExtDimension1..3` |

Что важно учитывать при составлении запросов:

- Версия протокола — 3.0, а не 4.0. Синтаксис, найденный в примерах для OData v4,
  чаще всего не сработает.
- Поля составного типа (`Recorder` — регистратор, `ExtDimension1..3` — субконто)
  фильтруются только через `cast()`. Прямое сравнение с `guid'…'` даёт пустую выборку
  или ошибку.
- `$select` не работает с виртуальными таблицами `Balance` и `BalanceAndTurnovers` —
  возвращается полный набор полей. Сведение по источнику-статье; проверьте на своей базе.
- `$expand` по ссылке возвращает вложенный объект, но `$select` по вложенным полям часто
  отдаёт HTTP 400. Проще выполнить второй запрос по `Ref_Key` (`get_by_key`).
- 1С отдаёт время сервера, а не UTC. Границы периода задавайте явно, полуинтервалом:
  `Date ge datetime'…T00:00:00' and Date lt datetime'…T00:00:00'` следующего дня.
- Имена сущностей и реквизитов кириллические, URL-кодирование обязательно. Клиент
  aprovodka кодирует их сам; при ручной сборке URL об этом надо помнить.
- 1С не поддерживает конечную точку OData `$batch`. Инструменты `batch_*` выполняют
  запросы параллельно на стороне сервера aprovodka, а не одним пакетом.

#### 6.1.1 Конверт выдачи: `returned`, `has_more`, `next_skip`

Читающие инструменты с параметром `$top` возвращают не сырой ответ 1С, а конверт:

```json
{ "value": [ … ], "returned": 100, "has_more": true, "next_skip": 100 }
```

| Поле | Смысл |
|---|---|
| `value` | Записи, не более `top` штук |
| `returned` | Сколько записей в `value` фактически |
| `has_more` | В базе есть ещё записи, подходящие под отбор: выдача обрезана по `$top` |
| `next_skip` | Значение `skip` для следующей страницы. Только при `has_more: true` и только у инструментов, у которых `skip` есть в схеме |

Зачем: `$top` по умолчанию равен 100. Без `has_more` ответ «первые 100 из 12 000»
неотличим от «все 40» — модель сложит первую сотню и назовёт это итогом. **Если
`has_more: true`, считать по такой выборке суммы, максимумы и «сколько всего» нельзя:**
дозапросите следующую страницу со `skip: next_skip`, сузьте `$filter` или возьмите
`count_entities`, который считает на стороне 1С и записи не выгружает.

Как это устроено: инструмент запрашивает у 1С `top + 1` запись. Лишняя запись — и есть
доказательство продолжения; в `value` она не попадает. Один лишний ряд дешевле
`$inlinecount`, который заставляет 1С пересчитать всю выборку.

**Отдельно — `truncated` и `note`.** У ответа есть предел размера: слишком длинный текст
режется по символам на стороне транспорта, и JSON рвётся посреди записи — модель получает
синтаксически невалидный документ. Чтобы этого не происходило, инструменты обрезают выдачу
раньше и **по целым записям**: в ответе появляются `truncated` (сколько записей отброшено)
и `note` с объяснением. Такой ответ всегда остаётся разбираемым JSON, но выборка в нём
неполная — итоги по ней считать нельзя, как и при `has_more`. Полей `truncated` и `note`
в ответе нет, пока обрезка не понадобилась.

У `get_accumulation_balance`, `get_accounting_balance`, `get_by_key`, `get_document_lines`
и `get_metadata` конверта нет: `$top` они не применяют и выдачу не обрезают.
У `poll_changes_since` свой конверт — с полями `count`, `rows`, `next_cursor` и тем же
`has_more`.

### 6.2 `Ref_Key`, `DeletionMark`, `Posted`

Почти у любого объекта 1С в OData есть набор стандартных полей. Наиболее употребимые:

| Поле | Смысл |
|---|---|
| `Ref_Key` | GUID ссылки — первичный ключ записи |
| `DataVersion` | Версия данных (оптимистичная блокировка) |
| `DeletionMark` | Пометка удаления, логический тип |
| `Description` | Наименование/представление |
| `Code` | Код (справочники) |
| `Predefined` | Признак предопределённого элемента |
| `Parent_Key` | Ссылка на родителя (иерархические справочники) |
| `IsFolder` | Признак группы |
| `Number` | Номер документа |
| `Date` | Дата документа |
| `Posted` | Признак проведения документа |

**`Ref_Key`** — единственный надёжный идентификатор записи. Номер документа и код
справочника могут повторяться между организациями или изменяться, `Ref_Key` — нет.
Все инструменты, работающие с конкретной записью (`get_by_key`, `update_document`,
`post_document`, `unpost_document`, `delete_document`, `update_catalog_item`,
`set_deletion_mark`, `get_document_lines`), принимают `ref_key` и проверяют его на
соответствие формату GUID до обращения к 1С. Значение, не являющееся GUID,
отвергается с сообщением об ошибке, а не превращается в некорректный запрос.

**`DeletionMark`** — «мягкое» удаление: запись остаётся в базе, помечается и удаляется
физически лишь при последующем групповом удалении помеченных объектов средствами 1С.
Инструмент `set_deletion_mark` ставит и снимает эту пометку (аргумент `mark`), и это
предпочтительный способ по сравнению с `delete_document`, выполняющим необратимый
HTTP DELETE. Важно: пометка **не** отфильтровывается сама собой. Если она вам не нужна
в выборке, добавляйте условие явно: `DeletionMark eq false`.

**`Posted`** — признак проведения документа. Провести документ означает, что платформа
выполнила его алгоритм проведения и записала движения в регистры — именно движения,
а не реквизиты самого документа, являются источником учётных итогов. Отсюда следствие,
о которое чаще всего спотыкаются: **непроведённый документ движений в регистрах
не имеет**, искать по нему проводки или включать его в остатки бессмысленно. Документы,
которые движений не делают по своей природе (например, счёт на оплату), — отдельный
случай того же правила.

Проведение и отмена проведения выполняются связанными действиями OData `Post()`
и `Unpost()` — инструменты `post_document` и `unpost_document`. У `post_document`
есть флаг `operational` — оперативное проведение (`PostingModeOperational`);
по умолчанию `false`, то есть неоперативное. Отбор только проведённых документов —
`Posted eq true`; у `get_recent_documents` для этого предусмотрен флаг `posted_only`.

### 6.3 Именование сущностей

Имя набора сущностей (entity set) складывается из префикса вида объекта метаданных
и имени объекта из конфигурации.

| Префикс | Вид объекта метаданных |
|---|---|
| `Catalog_` | справочники |
| `Document_` | документы |
| `DocumentJournal_` | журналы документов |
| `Constant_` | константы |
| `ExchangePlan_` | планы обмена |
| `ChartOfAccounts_` | планы счетов |
| `ChartOfCalculationTypes_` | планы видов расчёта |
| `ChartOfCharacteristicTypes_` | планы видов характеристик |
| `InformationRegister_` | регистры сведений |
| `AccumulationRegister_` | регистры накопления |
| `CalculationRegister_` | регистры расчёта |
| `AccountingRegister_` | регистры бухгалтерии |
| `BusinessProcess_` | бизнес-процессы |
| `Task_` | задачи |
| `Report_` | отчёты |

Фильтр `type` инструмента `list_entities` группирует эти префиксы: `registers` покрывает
все четыре вида регистров, `charts` — все три `ChartOf*`. Планы обмена, бизнес-процессы
и задачи фильтром не выбираются — для них вызывайте `list_entities` с `type="all"`.

Начиная с версии 4.1.0 инструменты принимают имя **и с префиксом, и без него** там,
где префикс однозначен: справочники, документы, регистры, константы, а из пакетных операций — `batch_create_documents` и `batch_update_catalog_items`. Инструменты, которые принимают сущность любого вида (`odata_query`, `batch_query`, `get_by_key`, `count_entities`, `describe_entity`), имя не достраивают: там префикс неоднозначен, и они же служат аварийным выходом, если полное имя нужно передать буквально.
`Document_РеализацияТоваровУслуг` и `РеализацияТоваровУслуг` эквивалентны. Для регистров
вид задаётся отдельным аргументом `register_type`; если префикс в имени ему противоречит,
инструмент возвращает понятную ошибку, а не склеивает
`AccumulationRegister_InformationRegister_…`.

Достраивание префикса — проверка на начало строки, без догадок по подчёркиванию: имена
вида `Document_ЗаказНаПроизводство2_2` реальны, и правило «есть подчёркивание — значит
префикс уже на месте» их бы сломало. Обратная сторона: объект, названный в конфигурации,
например, `AccumulationRegister_Old`, порождает entity set
`AccumulationRegister_AccumulationRegister_Old`, и такое имя схлопнется. Аварийный выход
для подобных случаев — инструменты, которые имя не изменяют: `odata_query`, `batch_query`,
`get_by_key`, `count_entities`, `describe_entity`.

**Табличные части.** Строки документа или справочника адресуются двумя способами:
отдельным набором сущностей `Document_<Документ>_<ИмяТЧ>` (например,
`Catalog_Организации_КонтактнаяИнформация`) либо навигацией от записи —
`Document_<Документ>(guid'…')/<ИмяТЧ>`. Инструмент `get_document_lines` использует второй
вариант через `$expand`. Имя табличной части задаётся конфигурацией и не выводится
из имени документа: уточняйте его через `get_metadata` или `describe_entity` своей базы.

Имена сущностей, которые приводит инструмент `get_config_preset` для типовых
конфигураций, снабжены пометкой достоверности: `verified` — имя встречено в цитируемом
источнике, `common` — типовое имя из практики, первоисточником не подтверждённое.
Пометка `common` не является гарантией: перед использованием такого имени сверяйтесь
с `list_entities` или `describe_entity` на конкретной базе.

### 6.4 Порядок ведения учёта и разграничение ответственности

Раздел отвечает на требование к составу документации: «описание порядка ведения учёта».
Ответ для продукта этого класса короткий и его важно понимать буквально.

**Собственной методики учёта продукт не вводит.** aprovodka — слой доступа к данным, а не
прикладное решение: он не создаёт объектов метаданных, не содержит алгоритмов расчёта, не
формирует проводок и не влияет на закрытие периода. Учёт ведётся средствами той
конфигурации «1С:Предприятия», к которой продукт подключён, по её методике и её правилам.
Проведение документа выполняет прикладной код конфигурации со всеми его проверками —
продукт лишь инициирует штатное действие через стандартный интерфейс OData.

Отсюда практическое следствие: **отказ вида «документ не может быть проведён» — это
нормальная работа конфигурации, а не сбой обмена.** Причину следует искать в учётных
данных и настройках базы, а не в продукте.

**Что продукт определяет.** Он задаёт не методику, а порядок доступа к учётным данным:

| Уровень | Чем задаётся | Кто отвечает |
|---|---|---|
| Что вообще доступно | Состав объектов, включённых в стандартный интерфейс OData | Администратор базы |
| Что может конкретное подключение | Роль пользователя «1С:Предприятия», от имени которого работает продукт | Администратор базы |
| Выполняется ли запись | `ONEC_WRITE_MODE`: `off` / `preview` / `approval` | Владелец установки |
| Кто и что записал | Аудит-леджер `ONEC_AUDIT_LOG` | Владелец установки |

**Рекомендуемый порядок работы с учётной базой.**

1. Начинать с роли **только на чтение**. Аналитика, поиск и сверки закрываются без единой
   операции записи, а риск при этом нулевой.
2. Запись включать отдельным решением и с обоснованием. На боевой базе — режим `approval`,
   при котором каждая операция изменения требует явного одноразового подтверждения.
3. Проведение, отмену проведения и удаление не выполнять без подтверждения человеком:
   первые два запускают прикладную логику и меняют движения регистров, третье необратимо.
4. Обязательно включать аудит-леджер там, где запись разрешена. Если файл леджера
   недоступен для записи, операция не выполняется — отсутствие записи в журнале никогда
   не означает молча выполненное изменение.
5. Закрытые периоды, регламентные операции и перепроведение документов оставлять
   штатным средствам конфигурации и ответственному сотруднику.

**Ответственность за корректность учёта остаётся на пользователе базы.** Продукт не
проверяет учётную обоснованность передаваемых значений: он передаёт их платформе, а
платформа применяет правила конфигурации.

## 7. Справочник инструментов

Единый шаблон: назначение, модуль, параметры, результат, пример фразы пользователя,
примечания. Правила чтения раздела:

- Имена инструментов, параметров и сущностей приводятся так, как их принимает программа,
  — переводить их нельзя. Описания параметров в большинстве разделов совпадают с текстами,
  которые сервер отдаёт MCP-клиенту. Исключение — модули `batch` и `changes`: подсказки к их
  параметрам остаются англоязычными, и здесь они даны переводом по смыслу. Краткие описания
  самих инструментов, которые видит клиент, начиная с версии 4.2.0 русские у всех без
  исключения.
- «Нет» в колонке «обязательный» означает, что параметр можно опустить; значение по
  умолчанию, если оно есть, указано в описании. Имена сущностей в примерах
  иллюстративные и требуют проверки на конкретной базе.
- Инструменты записи подчиняются режиму `ONEC_WRITE_MODE` (раздел 4.1): в `preview` и
  `approval` вместо результата записи возвращается конверт предпросмотра.

### 7.1 Модуль `meta` — обнаружение структуры базы

Пять инструментов. Регистрируется всегда, переменной `ONEC_SERVICES` не отключается: без
него агент не узнает состав незнакомой базы.

#### 7.1.1 list_entities

**Назначение** — вернуть список сущностей (entity set), опубликованных в стандартном
интерфейсе OData базы. Первое действие на незнакомой базе.

**Модуль** — `meta`, включён всегда.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `type` | перечисление (значения ниже) | нет, по умолчанию `all` | Фильтр по типу сущностей | `documents` |
| `search` | строка | нет | Подстрока для поиска в имени сущности (например, `Номенклатура`) | `Реализация` |

Допустимые значения `type`:

| Значение | Что попадает в выборку |
|---|---|
| `all` | все сущности базы |
| `catalogs` | справочники `Catalog_*` |
| `documents` | документы `Document_*` |
| `registers` | все четыре вида регистров: `AccumulationRegister_*`, `InformationRegister_*`, `AccountingRegister_*`, `CalculationRegister_*` |
| `charts` | планы счетов, видов расчёта и видов характеристик — `ChartOf*` |
| `constants` | константы `Constant_*` |
| `journals` | журналы документов `DocumentJournal_*` |
| `reports` | отчёты `Report_*` |

**Возвращает** — JSON с полями `total` (число найденных) и `entities` (массив имён);
`type` и `search` применяются последовательно.

**Пример запроса** — «Покажи все документы в базе, в названии которых есть „Реализация“».

**Примечания и ограничения**

- Планы обмена (`ExchangePlan_*`), бизнес-процессы (`BusinessProcess_*`) и задачи
  (`Task_*`) значениями фильтра не выбираются — их видно только при `type="all"`.
- Отсутствие сущности в списке обычно означает, что она не включена в состав стандартного
  интерфейса OData в Конфигураторе (настройка публикации, а не право доступа).

#### 7.1.2 get_document_by_number

**Назначение** — найти документ по номеру. Готовая обёртка над OData-отбором `$filter`.

**Модуль** — `meta`, включён всегда.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него | `Document_РеализацияТоваровУслуг` |
| `number` | строка | да | Номер документа | `ТД-00123` |
| `date` | строка `YYYY-MM-DD` | нет | Дата создания документа в формате `YYYY-MM-DD` (необязательно, сужает поиск) | `2026-03-01` |
| `select` | строка | нет | Поля для выборки через OData `$select` (например, `Ref_Key,Number,Date`) | `Ref_Key,Number,Date` |

**Возвращает** — ответ OData (JSON): объект с массивом `value`, не более десяти записей
(`$top=10` задан внутри инструмента).

**Пример запроса** — «Найди счёт ТД-00123 от 1 марта 2026 года».

**Примечания и ограничения**

- Одинарные кавычки в номере экранируются автоматически; дата разворачивается в интервал
  от `00:00:00` до `23:59:59` тех же суток по времени сервера 1С, а не по UTC.

#### 7.1.3 get_metadata

**Назначение** — получить документ `$metadata` (EDMX/XML) со всеми сущностями,
реквизитами и типами базы: точный источник схемы.

**Модуль** — `meta`, включён всегда.

**Параметры** — нет.

**Возвращает** — текст XML-документа EDMX целиком, как его отдаёт платформа.

**Пример запроса** — «Выгрузи полное описание метаданных базы».

**Примечания и ограничения**

- Ответ объёмный: на больших конфигурациях съедает заметную часть контекста модели.
  Для полей одной сущности дешевле `describe_entity`.
- Им же проверяют сведения, которых нет в документации продукта: имена табличных частей,
  точные типы реквизитов, имена виртуальных таблиц (в том числе оборотов Дт/Кт регистра
  бухгалтерии, не обёрнутых инструментами).

#### 7.1.4 describe_entity

**Назначение** — перечислить реквизиты сущности по записи-образцу. Дешевле полного
`$metadata`, когда нужны только имена полей.

**Модуль** — `meta`, включён всегда.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | Имя сущности (например, `Catalog_Номенклатура`, `Document_РеализацияТоваровУслуг`) | `Catalog_Контрагенты` |

**Возвращает** — JSON с полями `entity`, `field_count` и `fields` — массивом объектов
`{ name, type }`, где `type` определён по значению в образце.

**Пример запроса** — «Какие поля есть у справочника контрагентов?»

**Примечания и ограничения**

- Читается одна запись (`$top=1`). Пустая сущность даёт пустой список полей и указание
  перейти к `get_metadata`.
- Тип выводится по образцу, а не по схеме: пустое поле получит тип `null`.
- Имя передаётся как есть, префикс не достраивается: указывайте полное имя
  (`Catalog_…`, `Document_…`).

#### 7.1.5 get_config_preset

**Назначение** — выдать курированную схему типовой конфигурации (Бухгалтерия предприятия
3.0, Управление торговлей 11, ЗУП 3.1, ERP 2): ключевые сущности с русскими пояснениями,
готовые примеры вызовов, ловушки конфигурации.

**Модуль** — `meta`, включён всегда.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `config` | строка | нет | Конфигурация: `bp30`, `ut11`, `zup31`, `erp2` — либо синоним (`бухгалтерия`, `ут`, `зуп`, `erp`, `accounting`, `trade`). Без параметра возвращается список доступных пресетов | `bp30` |

**Возвращает** — без параметра: список пресетов (`id`, `name`, `aliases`, `summary`,
число сущностей и примеров, число подтверждённых имён `verified_entities`). С параметром:
пресет (`summary`, `entities`, `examples`, `pitfalls`, `sources`), блок `platform`
(префиксы имён, стандартные поля, литералы OData, табличные части, виртуальные таблицы
регистров, ловушки платформы) и пояснение `how_to_read`.

**Пример запроса** — «Я подключился к базе Бухгалтерии 3.0 — с каких сущностей начать?»

**Примечания и ограничения**

- Работает офлайн: данные вкомпилированы в поставку, `ONEC_BASE_URL` не требуется. Это
  один из двух инструментов, отвечающих до настройки подключения (второй — `list_subscriptions`,
  он отдаёт статическую справку о том, что подписок в интерфейсе нет).
- Каждая сущность помечена признаком достоверности `confidence`:
  - `verified` — имя встречено в источнике, перечисленном в `sources` пресета;
  - `common` — типовое имя из практики, первоисточником в этой сборке **не**
    подтверждённое.
  Имя с пометкой `common` — подсказка, что искать, а не гарантия: проверьте его через
  `list_entities` или `describe_entity`. Пометка `verified` проверку тоже не отменяет:
  она говорит, что имя встречено в документации, а не что оно есть в вашей базе.
- Пресет — карта типовой конфигурации: рабочая база могла быть доработана (объекты
  переименованы, реквизиты добавлены).

### 7.2 Модуль `catalogs` — справочники

Три инструмента: чтение, создание и изменение элементов справочников. Включён по
умолчанию, отключается исключением из списка `ONEC_SERVICES` (раздел 4.2).

#### 7.2.1 get_catalogs

**Назначение** — прочитать данные справочника через OData 3.0: отбор, выбор полей,
сортировка, постраничный обход.

**Модуль** — `catalogs`, включён по умолчанию.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `catalog_name` | строка | да | Имя справочника — с префиксом `Catalog_` или без него (`Catalog_Номенклатура` / `Номенклатура`) | `Catalog_Контрагенты` |
| `filter` | строка | нет | OData `$filter` (например, `Description eq 'Молоко'`) | `ИНН eq '7707083893' and DeletionMark eq false` |
| `select` | строка | нет | OData `$select` (например, `Ref_Key,Description`) | `Ref_Key,Code,Description` |
| `top` | целое, 1…1000 | нет, по умолчанию 100 | Количество записей (`$top`) | `50` |
| `skip` | целое, ≥0 | нет, по умолчанию 0 | Пропустить записей (`$skip`) | `100` |
| `orderby` | строка | нет | OData `$orderby` (например, `Description asc`) | `Description asc` |

**Возвращает** — ответ OData (JSON): объект с массивом `value` — записями справочника.

**Пример запроса** — «Покажи 50 контрагентов без пометки удаления, по алфавиту».

**Примечания и ограничения**

- `filter`, `select` и `orderby` передаются в 1С без разбора — сознательно: область
  видимости ограничивается ролью пользователя 1С, а не формой аргументов.
- Отбор не подставляется сам: без `DeletionMark eq false` в выборку попадут помеченные на
  удаление, а без `IsFolder eq false` — группы иерархического справочника.
- Синтаксис OData 3.0: подстрока — `substringof('текст',Description)`, функция
  `contains()` не поддерживается.

#### 7.2.2 create_catalog_item

**Назначение** — создать элемент справочника методом OData POST (например, контрагента
или позицию номенклатуры).

**Модуль** — `catalogs`, включён по умолчанию.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `catalog_name` | строка | да | Имя справочника — с префиксом `Catalog_` или без него (`Catalog_Номенклатура` / `Номенклатура`) | `Номенклатура` |
| `data` | объект JSON | да | Поля нового элемента в формате JSON (например, `{"Description":"Молоко"}`) | `{"Description":"Молоко","Code":"00-000123"}` |

**Возвращает** — созданную запись с присвоенным `Ref_Key`; при включённом режиме записи
— конверт предпросмотра с хешем `op_hash`.

**Пример запроса** — «Заведи в номенклатуре позицию „Молоко 3,2 %“».

**Примечания и ограничения**

- Создание записи необратимо: токен отката не выдаётся, в ответе указывается причина
  (`irreversible_reason`). Обратный шаг — взять `Ref_Key` из результата и пометить запись
  на удаление (`set_deletion_mark`).
- Обязательные реквизиты определяет конфигурация; состав полей уточняйте через
  `describe_entity` или `get_metadata`. При отказе из-за незаполненного поля сервер
  добавляет к сообщению 1С категорию ошибки и рекомендацию (раздел 10.1).

#### 7.2.3 update_catalog_item

**Назначение** — изменить элемент справочника методом OData PATCH по `Ref_Key`.

**Модуль** — `catalogs`, включён по умолчанию.

**Параметры**

| Имя | Тип | Обязательный | Описание | Пример |
|---|---|---|---|---|
| `catalog_name` | строка | да | Имя справочника — с префиксом `Catalog_` или без него | `Catalog_Контрагенты` |
| `ref_key` | строка, GUID | да | `Ref_Key` элемента (GUID) | `01234567-89ab-cdef-0123-456789abcdef` |
| `data` | объект JSON | да | Обновляемые поля | `{"Description":"ООО Ромашка"}` |

**Возвращает** — результат PATCH. При включённом режиме записи — конверт со сравнением
«было → станет» по каждому изменяемому полю.

**Пример запроса** — «Измени наименование контрагента с этим идентификатором на
„ООО Ромашка“».

**Примечания и ограничения**

- `ref_key` проверяется на формат GUID из 36 символов до обращения к базе.
- Передавайте только изменяемые реквизиты: не указанные в `data` поля платформа
  не трогает.
- Изменение обратимо: после выполнения в режиме `approval` возвращается токен отката,
  восстанавливающий прежние значения через `rollback_write`.
- Массовое изменение — `batch_update_catalog_items` (модуль `batch`): параллельно, с
  отчётом по каждому элементу.

### 7.3 Модуль `documents` (7 инструментов)

Модуль обслуживает документы — объекты метаданных, которые в стандартном интерфейсе OData 3.0 публикуются с префиксом `Document_`. Регистрируется по умолчанию; отключается или включается выборочно переменной `ONEC_SERVICES` (значение `documents`).

Общее для всех семи инструментов:

- **Имя типа документа** принимается в двух формах — `Document_РеализацияТоваровУслуг` и `РеализацияТоваровУслуг`. Префикс подставляется сервером, если его нет.
- **`ref_key`** проверяется как GUID (36 символов вида `01234567-89ab-cdef-0123-456789abcdef`) до обращения к базе. Некорректное значение приводит к ошибке на стороне сервера, запрос в 1С не уходит.
- **Ответ** возвращается как форматированный JSON — то, что отдала платформа, без переупаковки. Коллекции приходят в поле `value`.
- **Изменяющие вызовы** (`create_document`, `update_document`, `post_document`, `unpost_document`, `delete_document`) проходят через гейт записи `ONEC_WRITE_MODE` (см. раздел 5). В режимах `preview` и `approval` вместо результата возвращается конверт `write_safety` с описанием того, что было бы изменено, и хешем операции `op_hash`.
- **Имена документов, реквизитов и табличных частей зависят от конфигурации.** Пресеты (`get_config_preset`) дают типовые имена с пометкой достоверности: `verified` — имя встречено в цитируемом источнике, `common` — типовое имя из практики, первоисточником не подтверждённое. Перед использованием сверяйте по `list_entities`, `describe_entity` или `get_metadata` своей базы.

---

#### 7.3.1 `get_documents`

**Назначение.** Чтение документов заданного типа с произвольным отбором средствами OData 3.0.

**Модуль.** `documents`, включён по умолчанию.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него | `Document_РеализацияТоваровУслуг` |
| `filter` | строка | нет | OData `$filter` | `Date ge datetime'2024-01-01T00:00:00'` |
| `select` | строка | нет | OData `$select` | `Ref_Key,Number,Date` |
| `top` | целое 1…1000 | нет, по умолчанию `100` | Количество записей (`$top`) | `500` |
| `skip` | целое ≥ 0 | нет, по умолчанию `0` | Пропустить записей (`$skip`) | `100` |
| `orderby` | строка | нет | OData `$orderby` | `Date desc` |

**Возвращает.** Конверт выдачи (п. 6.1.1): записи в поле `value`, плюс `returned`, `has_more` и `next_skip`. Иллюстративная форма (реальный состав полей определяется конфигурацией):

```json
{ "value": [ { "Ref_Key": "…", "Number": "…", "Date": "…", "Posted": true } ],
  "returned": 100, "has_more": true, "next_skip": 100 }
```

При `has_more: true` выборка обрезана по `$top` — итоги по ней считать нельзя.

**Пример запроса.** «Покажи реализации за второй квартал 2026 года, только проведённые, по убыванию даты».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "filter": "Date ge datetime'2026-04-01T00:00:00' and Date lt datetime'2026-07-01T00:00:00' and Posted eq true",
  "orderby": "Date desc"
}
```

**Примечания.** Даты записываются литералом `datetime'…'`, а не ISO-строкой без префикса. Платформа отдаёт время сервера, а не UTC, поэтому границы периода задавайте явно — «от начала дня» и «до начала следующего дня». Пометка удаления сама собой не отсекается: почти всегда к отбору нужно добавлять `DeletionMark eq false`. Для страничного обхода больших выборок используйте пару `top` / `skip`.

#### 7.3.2 `create_document`

**Назначение.** Создание нового документа (HTTP POST на набор сущностей документа).

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него |
| `data` | объект JSON | да | Данные документа в формате JSON |

**Возвращает.** Созданную запись в том виде, в каком её вернула платформа, — включая присвоенный `Ref_Key`. При включённом гейте записи — конверт `write_safety`.

**Пример запроса.** «Создай реализацию товаров и услуг от 1 июля 2026 года по этому контрагенту».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "data": { "Date": "2026-07-01T00:00:00" }
}
```

**Примечания.** Состав обязательных реквизитов конфигурационно-зависим; узнать его можно через `describe_entity` или `get_metadata`. Если платформа отвергнет запись, встроенный разбор ошибок 1С вернёт категорию (`field_required`, `type_mismatch` и др.) и подсказку: даты передавать как `datetime'…'`, ссылочные значения — объектом `{Ref_Key, Type}`, логические — `true`/`false`, а не `0`/`1`.

Создание документа **не** является его проведением: новый документ приходит непроведённым и движений в регистрах не имеет. Провести его — отдельный вызов `post_document`.

Создание записи **необратимо автоматически**: гейт записи честно помечает такую операцию как не имеющую токена отката. Чтобы отменить создание, возьмите `Ref_Key` из результата и вызовите `set_deletion_mark` (модуль `shortcuts`) либо `delete_document`.

---

#### 7.3.3 `update_document`

**Назначение.** Изменение реквизитов существующего документа (HTTP PATCH по `Ref_Key`).

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него |
| `ref_key` | GUID | да | `Ref_Key` документа |
| `data` | объект JSON | да | Обновляемые поля |

**Возвращает.** Ответ платформы на PATCH; при включённом гейте — конверт `write_safety`.

**Пример запроса.** «Проставь в этом документе комментарий и новую дату».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "ref_key": "01234567-89ab-cdef-0123-456789abcdef",
  "data": { "Date": "2026-07-02T00:00:00" }
}
```

**Примечания.** Передаются только изменяемые поля — остальные реквизиты не затрагиваются. В режимах `preview` и `approval` сервер предварительно читает текущую запись и показывает изменение как `from` → `to`; сохранённые прежние значения затем позволяют выполнить `rollback_write`. В режиме `off` прежние значения не фиксируются, и автоматического отката у изменения нет.

Проведённый документ, изменённый через PATCH, не перепроводится сам: движения регистров останутся прежними, пока не будет выполнено `post_document` заново.

---

#### 7.3.4 `post_document`

**Назначение.** Проведение документа связанным действием OData `Post()`.

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него |
| `ref_key` | GUID | да | `Ref_Key` документа |
| `operational` | булево | нет, по умолчанию `false` | Оперативное проведение (`PostingModeOperational`). По умолчанию — неоперативное |

**Возвращает.** Ответ платформы на вызов действия; при включённом гейте — конверт `write_safety` с токеном отката (обратная операция — `Unpost`).

**Пример запроса.** «Проведи документ ТД-00123 неоперативно».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "ref_key": "01234567-89ab-cdef-0123-456789abcdef",
  "operational": false
}
```

**Примечания.** Запрос собирается как обращение к действию на конкретной записи: `…/odata/standard.odata/Document_<Тип>(guid'…')/Post` с параметрами `$format=json` и `PostingModeOperational=<true|false>`. Формы `Post()` и `Unpost()` соответствуют спецификации стандартного интерфейса OData платформы, но **точный состав действий и параметров стоит сверить по `$metadata` конкретной конфигурации** (инструмент `get_metadata`) до промышленного использования.

Проведение — это запись движений по регистрам и установка признака `Posted`. Если бизнес-правила конфигурации откажут в проведении, разбор ошибок вернёт категорию `posting_failed` с подсказкой проверить корректность и активность ссылочных объектов (организация, контрагент, склад) и открытость периода.

---

#### 7.3.5 `unpost_document`

**Назначение.** Отмена проведения документа связанным действием OData `Unpost()`.

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него |
| `ref_key` | GUID | да | `Ref_Key` документа |

**Возвращает.** Ответ платформы; при включённом гейте — конверт `write_safety` с токеном отката (обратная операция — `Post` в неоперативном режиме).

**Пример запроса.** «Отмени проведение этого документа».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "ref_key": "01234567-89ab-cdef-0123-456789abcdef"
}
```

**Примечания.** Отмена проведения снимает признак `Posted` и удаляет движения документа по регистрам. Непроведённый документ движений не имеет — искать по нему проводки бессмысленно, и в итогах учёта он не участвует.

`post_document` и `unpost_document` — взаимно обратная пара: гейт записи именно так и строит план отката (`post` → `unpost`, `unpost` → `post`). Как и для `Post()`, точную форму действия желательно сверить по `$metadata` своей конфигурации.

#### 7.3.6 `delete_document`

**Назначение.** Физическое удаление документа (HTTP DELETE по `Ref_Key`).

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него |
| `ref_key` | GUID | да | `Ref_Key` документа |

**Возвращает.** При выключенном гейте — подтверждение вида `{ "deleted": true, "document_type": …, "ref_key": … }`. При включённом гейте возвращается конверт `write_safety`, который сам сообщает исход операции и её необратимость.

**Пример запроса.** «Удали этот документ из базы окончательно».

```json
{
  "document_type": "Document_РеализацияТоваровУслуг",
  "ref_key": "01234567-89ab-cdef-0123-456789abcdef"
}
```

**Примечания.** ⚠ Это **физическое удаление**: запись исчезает из информационной базы. Отмены у операции нет — платформа не предоставляет undo, и токен отката для неё не выдаётся; гейт записи прямо помечает такую операцию как необратимую.

Пометка на удаление — **другая** операция. Это обратимое «мягкое» удаление: устанавливается признак `DeletionMark`, объект остаётся в базе и может быть восстановлен снятием пометки. Выполняется инструментом `set_deletion_mark` модуля `shortcuts`, и в подавляющем большинстве сценариев следует использовать именно его.

Если объект задействован в других документах, платформа откажет в удалении — разбор ошибок вернёт категорию `deletion_locked` с рекомендацией перейти на пометку удаления.

#### 7.3.7 `get_document_lines`

**Назначение.** Чтение табличной части документа (строк — например, товаров) по `Ref_Key`.

**Модуль.** `documents`.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него | `Document_ЗаказКлиента` |
| `ref_key` | GUID | да | `Ref_Key` документа | `01234567-89ab-cdef-0123-456789abcdef` |
| `tabular_section` | строка | да | Имя табличной части. Имя конфигурационно-зависимо — проверьте через `get_metadata` / `describe_entity`, если не уверены | `Товары` |

**Возвращает.** Запись документа, суженную до одной табличной части: запрос выполняется с `$expand` и `$select` по имени этой части, поэтому в ответе приходит массив строк указанной табличной части.

**Пример запроса.** «Покажи строки (товары) заказа клиента с этим идентификатором».

```json
{
  "document_type": "Document_ЗаказКлиента",
  "ref_key": "01234567-89ab-cdef-0123-456789abcdef",
  "tabular_section": "Товары"
}
```

**Примечания.** В стандартном интерфейсе OData табличная часть доступна двумя путями: отдельным набором сущностей `Document_<Документ>_<ИмяТЧ>` и навигацией от записи — `Document_<Документ>(guid'…')/<ИмяТЧ>`. Инструмент использует второй путь через `$expand`.

Имена табличных частей различаются между конфигурациями и даже между документами одной конфигурации. В пресетах, например, у `Document_РеализацияТоваровУслуг` (УТ 11) перечислены `Товары` и `Услуги`, у `Document_ЗаказКлиента` — `Товары`; сам документ `Document_ЗаказКлиента` помечен как `common`, то есть имя первоисточником не подтверждено. Достоверный список для вашей базы даёт `get_metadata`.

Раскрытие ссылочных полей через `$expand` возвращает вложенный объект, но `$select` по вложенным полям часто приводит к ответу HTTP 400. В таком случае проще выполнить второй запрос по `Ref_Key` (`get_by_key` модуля `shortcuts`).

### 7.4 Модуль `registers` — регистры сведений и накопления

Модуль регистрируется по умолчанию; отключается исключением имени `registers` из списка `ONEC_SERVICES`.

#### 7.4.1 `get_register`

**Назначение.** Чтение записей регистра сведений (`InformationRegister_*`) или регистра накопления (`AccumulationRegister_*`) — то есть самих движений, а не итогов.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `register_type` | `InformationRegister` \| `AccumulationRegister` | да | Тип регистра | `AccumulationRegister` |
| `register_name` | строка | да | Имя регистра — обычно без префикса; полное имя тоже принимается, но должно совпадать с `register_type` | `ТоварыНаСкладах` |
| `filter` | строка | нет | OData `$filter` | `Period ge datetime'2026-07-01T00:00:00'` |
| `select` | строка | нет | OData `$select` | `Period,Количество` |
| `orderby` | строка | нет | OData `$orderby` | `Period desc` |
| `top` | целое 1…5000 | нет, по умолчанию 100 | `$top` | `500` |
| `skip` | целое ≥ 0 | нет, по умолчанию 0 | `$skip` | `100` |

**Возвращает.** Ответ OData в формате JSON (массив записей в поле `value`), отформатированный с отступами.

**Пример запроса (естественный язык).** «Покажи движения по регистру ТоварыНаСкладах за июль, свежие сверху, не больше 500 строк.»

**Примечания и ограничения.**

- Вид регистра задаётся отдельным аргументом `register_type`, а не угадывается по имени. Если префикс в `register_name` противоречит `register_type` (например, `InformationRegister_Цены` при `register_type="AccumulationRegister"`), инструмент возвращает явную ошибку с указанием обоих значений и предложением передать «голое» имя — вместо молчаливой склейки `AccumulationRegister_InformationRegister_Цены`, которая дала бы непонятный HTTP 404.
- Регистры расчёта (`CalculationRegister_*`) и бухгалтерии (`AccountingRegister_*`) этим инструментом не читаются: в перечислении `register_type` их нет. Для регистров расчёта используйте `odata_query` с полным именем сущности, для регистров бухгалтерии — `get_accounting_register` (п. 7.5.1).
- Приход и расход в регистре накопления различает поле `RecordType`.
- Инструмент только читает; запись движений регистра накопления штатно выполняется проведением документа (`post_document`).

#### 7.4.2 `write_information_register`

**Назначение.** Запись одной записи в независимый регистр сведений — HTTP POST на `InformationRegister_*`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `register_name` | строка | да | Имя регистра сведений — с префиксом `InformationRegister_` или без него |
| `data` | объект | да | Запись регистра: измерения + ресурсы, например `{"Period":"2024-01-01T00:00:00","Номенклатура_Key":"…","Цена":100}` |

**Возвращает.** JSON-ответ 1С о созданной записи.

**Примечания и ограничения.**

- Состав измерений и ресурсов конфигурационно-зависим: перед записью посмотрите набор полей через `describe_entity` или `get_metadata` своей базы.
- Инструмент рассчитан на **независимые** регистры сведений. Регистр, подчинённый регистратору, штатно заполняется документом, а не прямой записью.
- Это операция записи: при `ONEC_WRITE_MODE=preview` она никогда не выполняется и возвращает dry-run с `op_hash`; при `approval` требует предварительного вызова `approve_write`. Создание записи помечается как необратимое (`irreversible_reason`) — токена отката для него не выдаётся.

#### 7.4.3 `get_accumulation_balance`

**Назначение.** Остатки регистра **накопления** через штатный виртуальный метод OData `Balance(Period=…,Condition=…)`. Это итоги, а не движения.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `register_name` | строка | да | Имя регистра накопления — с префиксом `AccumulationRegister_` или без него | `ТоварыНаСкладах` |
| `period` | `YYYY-MM-DDTHH:MM:SS` | нет | Дата среза остатков (`Period`). Без указания — текущие остатки | `2026-07-01T00:00:00` |
| `condition` | строка | нет | OData-условие отбора по измерениям (`Condition`) | `Склад_Key eq guid'…'` |

**Возвращает.** JSON с записями остатков.

**Пример ответа (иллюстративный, не вывод реальной базы).**

```json
{
  "value": [
    { "Склад_Key": "01234567-89ab-cdef-0123-456789abcdef",
      "Номенклатура_Key": "89abcdef-0123-4567-89ab-cdef01234567",
      "КоличествоBalance": 12 }
  ]
}
```

**Примечания и ограничения.**

- В результате к имени ресурса дописывается суффикс: `<Ресурс>Balance`; измерения возвращаются как `<Измерение>_Key`.
- Инструмент оборачивает только таблицу `Balance`. Обороты регистра накопления (`Turnovers`, `BalanceAndTurnovers`) им не запрашиваются: при необходимости читайте движения через `get_register` и агрегируйте на стороне клиента, предварительно сверив состав таблиц по `get_metadata` своей базы.
- Значение `condition` экранируется дважды — на уровне литерала OData и на уровне URL. Правка версии 4.1.0: до неё символы `?` и `#` в условии могли подменить строку запроса.
- Для регистров бухгалтерии этот инструмент не подходит — см. п. 7.5.2 и врезку ниже.

---

### 7.5 Модуль `accounting` — регистры бухгалтерии

#### 7.5.1 `get_accounting_register`

**Назначение.** Чтение записей регистра бухгалтерии (`AccountingRegister_*`, в типовых конфигурациях — `Хозрасчетный`), то есть отдельных проводок.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `register_name` | строка | нет, по умолчанию `Хозрасчетный` | Имя регистра бухгалтерии (основной план счетов); префикс необязателен | `Хозрасчетный` |
| `filter` | строка | нет | OData `$filter` | `Period ge datetime'2026-06-01T00:00:00'` |
| `select` | строка | нет | OData `$select` | `Period,LineNumber` |
| `orderby` | строка | нет | OData `$orderby` | `Period desc` |
| `top` | целое 1…5000 | нет, по умолчанию 100 | `$top` | `1000` |
| `skip` | целое ≥ 0 | нет, по умолчанию 0 | `$skip` | `0` |

**Возвращает.** JSON-массив записей регистра.

**Пример запроса.** «Все проводки документа поступления с таким-то Ref_Key, по порядку строк.»

**Примечания и ограничения.**

- Типовые поля записи: `Period`, `Recorder` (регистратор), `LineNumber`, `Active`, `AccountDr_Key` / `AccountCr_Key` (счета дебета и кредита), `ExtDimension1`…`ExtDimension3` (субконто). Имена ресурсов (`Сумма` и т. п.) конфигурационно-зависимы.
- `Recorder` и субконто — ссылки составного типа: фильтр по ним пишется только через `cast(guid'…','Document_ПоступлениеТоваровУслуг')`; прямое сравнение с `guid'…'` даёт пустую выборку или ошибку.
- Имя `Хозрасчетный` — типовое, в доработанной базе может отличаться. На незнакомой базе начинайте с `list_entities` с фильтром `registers`.
- Инструмент только читает. Прямая запись проводок через OData в общем случае недоступна; штатный путь — создать документ и провести его.

#### 7.5.2 `get_accounting_balance`

**Назначение.** Виртуальные таблицы регистра бухгалтерии — остатки, обороты и субконто, то есть итоги двойной записи в разрезе счетов.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `register_name` | строка | нет, по умолчанию `Хозрасчетный` | Имя регистра — с префиксом `AccountingRegister_` или без него |
| `table` | перечисление | нет, по умолчанию `Balance` | `Balance` — остатки на дату; `Turnovers`, `BalanceAndTurnovers` — за период; `RecordsWithExtDimensions`, `ExtDimensions` — субконто |
| `period` | `YYYY-MM-DDTHH:MM:SS` | нет | Только для `Balance`: дата среза |
| `start_period` | `YYYY-MM-DDTHH:MM:SS` | нет | Начало периода для `Turnovers` / `BalanceAndTurnovers` |
| `end_period` | `YYYY-MM-DDTHH:MM:SS` | нет | Конец периода для `Turnovers` / `BalanceAndTurnovers` |
| `condition` | строка | нет | Отбор по измерениям (`Condition`), например `Организация_Key eq guid'…'` |
| `account_condition` | строка | нет | Отбор по счетам (`AccountCondition`) — имя параметра первоисточником не подтверждено |
| `extra` | объект «строка → строка» | нет | Прочие параметры вызова как есть, например `{"Dimensions": "'Счет,Организация'"}` |

**Возвращает.** JSON с результатом виртуальной таблицы.

**Примечания и ограничения.**

- Параметры периода проверяются по смыслу таблицы: `Balance` с `start_period` / `end_period` и `Turnovers` / `BalanceAndTurnovers` с `period` отклоняются с текстом, объясняющим, какой параметр нужен.
- **Таблиц оборотов по дебету и кредиту в перечислении `table` нет намеренно.** Точное имя (`DrCrTurnover` либо `DrCrTurnovers`) ни в одном доступном нам источнике однозначно не зафиксировано, а угадывать имя, которое уйдёт в боевой запрос, недопустимо. Сверьте состав виртуальных таблиц по `get_metadata` своей базы.
- Имя параметра `account_condition` (`AccountCondition`) также относится к неподтверждённым. Если база отвечает ошибкой, передайте параметр через `extra` под тем именем, которое показал `$metadata`. Значения в `extra` уходят как готовые литералы OData — экранирование их содержимого на стороне вызывающего.
- По статье-первоисточнику `Balance` регистра бухгалтерии ожидает наличия `AccountCondition`, допуская пустое значение; проверьте поведение на своей базе.
- `$select` с виртуальными таблицами `Balance` и `BalanceAndTurnovers`, по тому же источнику, не работает — возвращается полный набор полей.
- Инструмент появился в версии 4.1.0. До неё виртуальные таблицы регистра бухгалтерии не были доступны ни одним инструментом, включая `odata_query`: тот кодирует `/`, `=`, `,` и скобки вызова, поэтому такой URL им не выражался.

### Врезка: `get_accumulation_balance` и `get_accounting_balance` — не путать

| | `get_accumulation_balance` | `get_accounting_balance` |
|---|---|---|
| Объект метаданных | Регистр **накопления**, `AccumulationRegister_*` | Регистр **бухгалтерии**, `AccountingRegister_*` |
| Модуль | `registers` | `accounting` |
| Что считает | Остатки по измерениям (склад, номенклатура, контрагент) | Итоги двойной записи: счета, корреспонденция, субконто |
| Таблицы | Только `Balance` | `Balance`, `Turnovers`, `BalanceAndTurnovers`, `RecordsWithExtDimensions`, `ExtDimensions` |
| Отбор по счетам | Не применим | `account_condition` (имя не подтверждено) либо `extra` |

Практическое следствие: вопрос «сколько товара на складе» решается через `get_accumulation_balance`, вопрос «какое сальдо по счёту 51 на дату» — через `get_accounting_balance`. Оба инструмента работают с итогами; построчные движения отдают `get_register` и `get_accounting_register` соответственно.

### 7.6 Модуль `constants` — константы

#### 7.6.1 `get_constant`

**Назначение.** Чтение значения константы 1С (`Constant_*`).

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `constant_name` | строка | да | Имя константы, например `Constant_ОсновнаяВалюта` или `ОсновнаяВалюта` |

**Возвращает.** JSON-ответ 1С; собственно значение находится в поле `Value`.

**Примечания.** Префикс `Constant_` подставляется автоматически, если он не указан. Перечень констант базы даёт `list_entities` с фильтром `constants`.

#### 7.6.2 `set_constant`

**Назначение.** Запись значения константы через OData PATCH поля `Value`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `constant_name` | строка | да | Имя константы (`Constant_*` или короткое имя) |
| `value` | любое | да | Новое значение константы (поле `Value`) |

**Возвращает.** JSON-ответ 1С о выполненном изменении.

**Примечания и ограничения.**

- Тип значения должен соответствовать типу константы в конфигурации: даты передаются литералом `datetime'…'`, ссылки — как объект со ссылкой, булевы — как `true`/`false`, а не `0`/`1`. Несоответствие типа 1С отвергает — парсер ошибок отнесёт ответ к категории `type_mismatch`.
- Константа обычно влияет на учётную политику и поведение всей базы. При включённом гейте записи (`ONEC_WRITE_MODE=preview` или `approval`) операция сначала показывается как разница «было → стало»; в режиме `approval` она выполняется только после `approve_write` с соответствующим `op_hash`. Для PATCH, у которого удалось прочитать прежнее значение, выдаётся токен отката для `rollback_write`.
- Права на запись ограничиваются ролью пользователя 1С, а не аргументами инструмента.

### 7.7 Модуль `shortcuts` — 5 инструментов

Модуль включается значением `shortcuts` в `ONEC_SERVICES` и входит в набор по умолчанию. Инструменты модуля — это готовые обёртки над частыми OData-запросами: то же самое достижимо через `odata_query`, но здесь параметры запроса собираются сервером, а не вызывающей стороной.

Имена сущностей в примерах ниже взяты из пресета «1С:Бухгалтерия предприятия 3.0» с пометкой `confidence: verified`. Имена с пометкой `common` — типовые, первоисточником не подтверждённые; перед использованием проверяйте их через `list_entities` или `describe_entity` на своей базе.

#### 7.7.1 `find_by_description`

**Назначение.** Найти элементы сущности по подстроке в поле `Description` (наименование). Нечёткий поиск «по названию», когда точный код или `Ref_Key` неизвестен.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | Сущность для поиска | `Catalog_Контрагенты` |
| `query` | строка | да | Подстрока для поиска в поле `Description` | `Ромашка` |
| `top` | целое 1–100 | нет, по умолч. 20 | Сколько записей вернуть | `20` |

**Как выполняется.** `$filter=substringof('<query>',Description)` c `$top`. Это синтаксис OData 3.0; функции `contains()` из OData 4.0 платформа не понимает. Одинарная кавычка внутри `query` удваивается автоматически, поэтому наименование вида `ООО "Ромашка'с"` не ломает запрос.

**Возвращает.** Стандартный OData-ответ сущности в JSON: объект с массивом `value`, каждый элемент — запись со всеми полями.

**Пример запроса на естественном языке.** «Найди контрагентов, в названии которых есть Ромашка».

**Примечания и ограничения.**
- Имя сущности передаётся как есть, префикс не достраивается: нужно писать `Catalog_Контрагенты`, а не `Контрагенты`.
- Поиск идёт только по `Description`. У документов наименования нет — их ищут по `get_document_by_number` (номер) либо через `odata_query` по нужному реквизиту.
- Помеченные на удаление записи в выборку попадают: фильтр `DeletionMark eq false` этот инструмент не добавляет.

#### 7.7.2 `get_by_key`

**Назначение.** Получить одну запись по её `Ref_Key` — GUID-ссылке, первичному ключу объекта 1С.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | Сущность | `Catalog_Номенклатура` |
| `ref_key` | строка (GUID) | да | `Ref_Key` записи | `01234567-89ab-cdef-0123-456789abcdef` |
| `select` | строка | нет | OData `$select` — список возвращаемых полей | `Code,Description` |

**Как выполняется.** Адресация по ключу: `<Сущность>(guid'<ref_key>')`. Значение `ref_key` проверяется на соответствие формату GUID до отправки запроса — некорректное значение даёт ошибку на стороне сервера aprovodka, а не 1С.

**Возвращает.** Одну запись в JSON.

**Пример запроса.** «Покажи карточку номенклатуры по ссылке 01234567-89ab-cdef-0123-456789abcdef».

**Примечания.** Имя сущности не достраивается. Инструмент удобен как второй шаг после `$expand`: вложенные объекты платформа отдаёт, но `$select` по их полям часто возвращает HTTP 400, и отдельный запрос по `Ref_Key` оказывается проще.

#### 7.7.3 `count_entities`

**Назначение.** Узнать количество записей сущности, не выгружая их.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | Сущность для подсчёта | `Document_РеализацияТоваровУслуг` |
| `filter` | строка | нет | OData `$filter` — условие подсчёта | `Posted eq true` |

**Как выполняется.** `$top=0` вместе с `$inlinecount=allpages`: платформа возвращает только счётчик, без строк.

**Возвращает.** Компактный объект с именем сущности и числом. Пример ответа — иллюстративный, это не вывод реальной базы:

```json
{
  "entity": "Document_РеализацияТоваровУслуг",
  "count": "1842"
}
```

**Примечания.** Если платформа счётчик не вернула, поле `count` будет `null` — тогда объём оценивают постраничной выборкой через `odata_query` с `skip`. Инструмент рассчитан на оценку объёма перед массовой выгрузкой: счёт по всей сущности без фильтра на большой базе всё равно нагружает сервер 1С.

#### 7.7.4 `set_deletion_mark`

**Назначение.** Установить или снять пометку удаления (`DeletionMark`) у элемента справочника или документа.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | Сущность, `Catalog_*` или `Document_*` | `Document_РеализацияТоваровУслуг` |
| `ref_key` | строка (GUID) | да | `Ref_Key` записи | `01234567-89ab-cdef-0123-456789abcdef` |
| `mark` | логический | нет, по умолч. `true` | `true` — пометить на удаление, `false` — снять пометку | `true` |

**Как выполняется.** OData PATCH по адресу записи с телом `{"DeletionMark": <mark>}`.

**Это пометка, а не удаление.** Запись остаётся в информационной базе со всеми реквизитами и связями; меняется только значение булева поля `DeletionMark`. Из выборок она сама собой не исчезает — чтобы её не видеть, в запросы нужно добавлять `DeletionMark eq false`. Физическое удаление помеченных объектов выполняется отдельно, штатными средствами самой «1С:Предприятия», с контролем ссылочной целостности; порядок этой операции задаётся конфигурацией и настоящим руководством не описывается.

**Отличие от `delete_document`.** `delete_document` выполняет OData DELETE — физическое удаление документа без возможности отмены средствами сервера. `set_deletion_mark` обратим: повторный вызов с `mark: false` возвращает исходное состояние. При включённом гейте записи (`ONEC_WRITE_MODE=preview` или `approval`) переключение пометки распознаётся как структурно обратимая операция и получает токен для `rollback_write`; для физического удаления токен не выдаётся, в ответе указывается причина необратимости.

**Примечания.** Если 1С отказывает в удалении из-за ссылок из других документов, парсер ошибок относит ответ к категории `deletion_locked` и предлагает пометку вместо жёсткого удаления.

#### 7.7.5 `get_recent_documents`

**Назначение.** Получить последние документы указанного типа, отсортированные по дате по убыванию.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `document_type` | строка | да | Тип документа — с префиксом `Document_` или без него | `РеализацияТоваровУслуг` |
| `top` | целое 1–100 | нет, по умолч. 10 | Сколько последних документов вернуть | `10` |
| `posted_only` | логический | нет, по умолч. `false` | Только проведённые (`Posted eq true`) | `true` |

**Как выполняется.** `$orderby=Date desc` с `$top`; при `posted_only: true` добавляется `$filter=Posted eq true`.

**Пример запроса.** «Покажи десять последних проведённых реализаций».

**Примечания.**
- Это единственный инструмент модуля, который достраивает префикс: обе формы, `РеализацияТоваровУслуг` и `Document_РеализацияТоваровУслуг`, дают один результат.
- Сортировка идёт по полю `Date`, то есть по дате документа, а не по времени его изменения. Для отслеживания правок предназначен `poll_changes_since` из модуля `changes`.
- 1С возвращает время сервера, а не UTC. При сравнении дат с внешними системами учитывайте часовой пояс базы.

### 7.8 Модуль `reports` — 1 инструмент

#### 7.8.1 `get_report`

**Назначение.** Получить отчёт по произвольному адресу HTTP-сервиса, опубликованного в вашей конфигурации 1С.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `report_url` | строка | да | Полный относительный путь к отчёту | `/hs/reports/balance?date=2024-12-31` |

**Как выполняется.** GET по указанному пути на том же хосте, что задан в `ONEC_BASE_URL`, с теми же учётными данными HTTP Basic и заголовком `Accept: application/json`. Путь передаётся без изменений — сервер aprovodka его не разбирает и не дополняет параметрами.

**Возвращает.** Тело ответа HTTP-сервиса.

**Примечания и ограничения.**
- Это не OData-инструмент. Он обращается к механизму HTTP-сервисов платформы (публикуются отдельно от стандартного интерфейса OData, обычно по префиксу `/hs/`). Если в вашей конфигурации HTTP-сервис отчётов не реализован и не опубликован, вызывать нечего.
- Состав и формат ответа целиком определяются кодом этого HTTP-сервиса. Универсальной схемы нет, поэтому пример ответа в руководстве не приводится: возьмите его из документации на свою конфигурацию.
- Инструмент рассчитан на относительные пути в пределах настроенной базы; произвольные внешние адреса он не обслуживает.

### 7.9 Модуль `odata` — 1 инструмент

#### 7.9.1 `odata_query`

**Назначение.** Выполнить произвольный запрос чтения OData 3.0 к любой сущности базы.

| Параметр | Тип | Обяз. | Описание | Пример |
|---|---|---|---|---|
| `entity` | строка | да | OData-сущность | `Catalog_Номенклатура` |
| `filter` | строка | нет | `$filter` | `DeletionMark eq false` |
| `select` | строка | нет | `$select` | `Code,Description` |
| `expand` | строка | нет | `$expand` для связанных таблиц | `Товары` |
| `top` | целое 1–5000 | нет, по умолч. 100 | `$top` | `500` |
| `skip` | целое ≥ 0 | нет, по умолч. 0 | `$skip` | `500` |
| `orderby` | строка | нет | `$orderby` | `Date desc` |
| `inlinecount` | логический | нет, по умолч. `false` | Добавить `$inlinecount=allpages` | `true` |

**Как выполняется.** Собирается один GET-запрос вида `<Сущность>?$format=json&$top=…` с переданными системными параметрами. `$format=json` добавляется всегда.

**Это аварийный выход.** Инструмент существует для запросов, которых нет среди типовых: нестандартная комбинация отборов, редкая сущность, разовая выгрузка. Если для задачи есть специализированный инструмент — пользуйтесь им: он собирает параметры сам и меньше зависит от знания синтаксиса платформы.

**Ограничения, о которых нужно знать заранее.**
- **Имя сущности не достраивается.** Что передали, то и уйдёт в запрос: `Номенклатура` вместо `Catalog_Номенклатура` даст ошибку от 1С, а не автоисправление. Обратная сторона того же свойства полезна: если автодостройка префикса в других инструментах мешает (например, у объекта, чьё имя само начинается с `AccumulationRegister_`), обходным путём служит именно `odata_query`.
- **Виртуальную таблицу регистра вызвать нельзя.** Обращения вида `<Регистр>/Balance(Period=…,Condition=…)` требуют, чтобы символы `/`, `=`, `,`, `:` в пути остались как есть, а здесь имя сущности кодируется целиком. Для остатков и оборотов предназначены отдельные инструменты: `get_accumulation_balance` для регистров накопления и `get_accounting_balance` для регистров бухгалтерии.
- **Только чтение.** Инструмент выполняет GET. Запись идёт через инструменты модулей `catalogs`, `documents`, `registers`, `constants` и `shortcuts` — только так она попадает под гейт записи и аудит.
- Значения параметров передаются в запрос как есть; отвечает за корректность синтаксиса OData вызывающая сторона. Ссылочные поля составного типа (`Recorder`, `ExtDimension*`) фильтруются только через `cast(guid'…','Тип')`.

### 7.10 Модуль `batch` — пакетные операции (3 инструмента)

Модуль включается значением `batch` в `ONEC_SERVICES` (по умолчанию включены все модули).

**Пакетность здесь клиентская.** Встроенный OData-сервис «1С:Предприятия» не реализует точку `$batch`: запрос `multipart/mixed` к `/odata/standard.odata/$batch` возвращает «Произошла ошибка сервиса». Поэтому инструменты модуля рассылают N обычных OData-запросов с ограничением параллелизма и собирают результаты в общий конверт. Серверного объединения (join) нет.

**Поведение при частичном отказе.** Отказ одного элемента не прерывает пакет: остальные выполняются до конца. Каждый элемент получает собственный статус, порядок результатов совпадает с порядком входного массива. Транзакции на весь пакет нет: если из 100 документов создались 97, три оставшихся отправляются повторно, а 97 уже находятся в базе.

Общий формат ответа всех трёх инструментов:

| Поле | Смысл |
|---|---|
| `total` | Сколько элементов было во входном массиве |
| `succeeded` | Сколько выполнено успешно |
| `failed` | Сколько завершилось ошибкой |
| `results[]` | По элементу: `index`, `status` (`ok` / `error`), `data` либо `error` |
| `failed_indexes[]` | Индексы неудачных элементов — список для повтора |
| `note` | Напоминание об отсутствии `$batch` в «1С» |

#### 7.10.1 `batch_create_documents`

**Назначение.** Создать от 1 до 100 документов одного вида параллельными запросами.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `document_type` | строка | да | Вид документа, единый для всего пакета. Принимается и полное имя (`Document_РеализацияТоваровУслуг`), и имя без префикса — `Document_` достраивается |
| `documents` | массив объектов | да | От 1 до 100 наборов полей документа; структура элемента та же, что у аргумента `data` инструмента `create_document` |
| `concurrency` | целое 1–20 | нет | Предел одновременных HTTP-запросов к «1С», по умолчанию 5 |

**Возвращает** конверт, описанный выше; в `data` успешного элемента — ответ «1С» на создание записи с присвоенным `Ref_Key`.

**Пример запроса на естественном языке.** «Создай 20 реализаций товаров по этой таблице, по 5 запросов одновременно».

Пример ответа (иллюстративный, сокращён; получен не из рабочей базы):

```json
{
  "total": 20, "succeeded": 19, "failed": 1,
  "results": [
    { "index": 0, "status": "ok", "data": { "Ref_Key": "…", "Number": "…" } },
    { "index": 7, "status": "error", "error": "Поле объекта не обнаружено (Контрагент)" }
  ],
  "failed_indexes": [7], "note": "…"
}
```

**Примечания.** Документы создаются непроведёнными — проведение выполняется отдельно (`post_document`). Повышение `concurrency` увеличивает нагрузку на сервер «1С» и вероятность взаимных блокировок при записи в одни регистры; при таких ошибках значение следует снижать.

#### 7.10.2 `batch_update_catalog_items`

**Назначение.** Изменить от 1 до 100 элементов одного справочника: по каждому выполняется `PATCH` по его `Ref_Key`.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `catalog_name` | строка | да | Имя справочника. Принимается и `Catalog_Номенклатура`, и `Номенклатура` — префикс `Catalog_` достраивается |
| `updates` | массив объектов | да | От 1 до 100 пар: `ref_key` — GUID элемента, `data` — изменяемые поля (структура как у `data` в `update_document`) |
| `concurrency` | целое 1–20 | нет | Предел одновременных запросов, по умолчанию 5 |

**Возвращает** тот же конверт. `Ref_Key` проверяется на формат GUID отдельно для каждого элемента: неверный ключ приводит к ошибке только своего элемента.

**Пример запроса.** «Установи признак „Услуга“ у этих 40 позиций номенклатуры».

**Примечания.** Передаются только перечисленные поля, остальные реквизиты не затрагиваются. Несуществующий `Ref_Key` даёт ошибку «1С» в своей строке результата.

#### 7.10.3 `batch_query`

**Назначение.** Выполнить от 1 до 50 независимых запросов чтения OData параллельно.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `queries` | массив объектов | да | От 1 до 50 описаний запросов; каждое — отдельный HTTP-запрос |
| `queries[].entity` | строка | да | Сущность OData, например `Catalog_Номенклатура`. Имя передаётся как есть, без достройки префикса |
| `queries[].filter`, `.select`, `.expand`, `.orderby` | строка | нет | Выражения `$filter`, `$select`, `$expand`, `$orderby` |
| `queries[].top` | целое 1–5000 | нет | Ограничение количества строк, по умолчанию 100 |
| `queries[].skip` | целое ≥ 0 | нет | Пропуск строк для постраничного обхода, по умолчанию 0 |
| `concurrency` | целое 1–20 | нет | Предел одновременных запросов, по умолчанию 5 |

**Пример запроса.** «Посчитай за один заход остатки по трём складам и заодно подтяни справочник организаций».

**Примечания.** Поскольку имя сущности не изменяется, `batch_query` служит аварийным выходом для объектов, чьё имя нельзя получить достройкой префикса. Соединение результатов выполняет вызывающая сторона.

### 7.11 Модуль `changes` — отслеживание изменений (2 инструмента)

Модуль включается значением `changes` в `ONEC_SERVICES`. Встроенный OData-сервис «1С» не предоставляет ни веб-хуков, ни подписки на события, ни ленты изменений: доступен только синхронный CRUD. Единственный штатный способ узнать об изменениях — периодический опрос.

#### 7.11.1 `poll_changes_since`

**Назначение.** Получить строки сущности, изменённые с заданной отметки времени, и курсор для следующего опроса.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `entity` | строка | да | Опрашиваемая сущность OData, например `Document_РеализацияТоваровУслуг` или `Catalog_Номенклатура` |
| `since` | строка `ГГГГ-ММ-ДДTчч:мм:сс` | да | Курсор: возвращаются строки со значением поля даты больше либо равным `since`. При первом опросе задаётся вручную, далее — `next_cursor` из предыдущего ответа |
| `date_field` | строка | нет | Поле даты, по которому идёт отбор. По умолчанию `Date` — подходит большинству документов. Для справочников и регистров без `Date` указывается другое поле, например `ModificationDate`; состав реквизитов зависит от конфигурации, наличие поля проверяется через `describe_entity` |
| `top` | целое 1–1000 | нет | Максимум строк за один опрос, по умолчанию 100 |
| `select` | строка | нет | Выражение `$select` для сокращения состава возвращаемых полей |

**Возвращает:** `entity`, `since`, `date_field`, `count` — число строк, `rows` — сами строки, `next_cursor`, `has_more`, `note`.

- `next_cursor` — наибольшее значение поля даты среди возвращённых строк; `null`, если строк нет или значение не удалось прочитать.
- `has_more` — истина, когда число строк достигло `top`: изменений больше, чем поместилось в ответ, и опрос следует повторить сразу, не дожидаясь интервала.

**Пример запроса.** «Каждую минуту проверяй новые реализации и показывай только появившиеся».

**Примечания.** Отбор идёт по условию «больше либо равно», а курсор равен максимальной дате выборки, поэтому строки с граничной датой вернутся и в следующем опросе — дубли отсеиваются по `Ref_Key` на стороне вызывающего. Сортировка ответа — по возрастанию поля даты. Изменение видно только через поле `date_field`: если конфигурация не обновляет его при записи, изменение останется незамеченным.

#### 7.11.2 `list_subscriptions`

**Назначение.** Явно зафиксировать отсутствие подписок на события в «1С». Аргументов не имеет.

**Возвращает:** `supported: false`, пустой список `subscriptions`, `reason` с объяснением и `workarounds` — три обходных пути: опрос через `poll_changes_since`; собственный HTTP-сервис «1С», отправляющий уведомления во внешнюю точку (доработка конфигурации, читается через `get_report`); внешний брокер сообщений через подписку «1С» — за пределами возможностей сервера.

**Примечания.** Инструмент существует, чтобы языковая модель не изобретала несуществующий вызов вида `subscribe_to_event` и не предлагала настроить отсутствующий в платформе веб-хук.

### 7.12 Инструменты гейта записи (2 инструмента)

Оба инструмента регистрируются, только если `ONEC_WRITE_MODE` равна `preview` или `approval`. При значении по умолчанию (`off`) их в списке инструментов нет, а запись выполняется сразу.

Гейт встроен в три функции клиента, через которые проходит любая запись (`POST`, `PATCH`, `DELETE`), поэтому действует и на пакетные операции: в режиме `preview` каждый элемент пакета вернёт предварительный отчёт вместо записи, в режиме `approval` — потребует отдельного подтверждения. Для пакетов из десятков элементов режим `approval` практически неприменим.

#### 7.12.1 `approve_write`

**Назначение.** Подтвердить одну ожидающую операцию записи по `op_hash` из её предварительного отчёта.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `op_hash` | строка, 16 шестнадцатеричных символов | да | `op_hash` из preview-ответа пишущего инструмента |
| `reason` | строка | нет | Кто и почему подтвердил — попадает в журнал аудита |

**Возвращает:** подтверждённый `op_hash`, `expires_in_sec` — срок действия (по умолчанию 300 секунд, настраивается `ONEC_APPROVAL_TTL_SEC`), признак одноразовости и указание следующего шага.

**Порядок работы.** Вызов пишущего инструмента → сервер ничего не пишет и возвращает предварительный отчёт с `op_hash` → отчёт показывается человеку → после явного согласия вызывается `approve_write` → тот же инструмент вызывается повторно с теми же аргументами и выполняется один раз.

**Примечания.** Подтверждение одноразовое и привязано к конкретной операции: любое изменение аргументов даёт другой `op_hash` и требует нового подтверждения. Подтверждения хранятся в памяти процесса и теряются при перезапуске. В режиме `preview` инструмент возвращает ошибку — там запись не выполняется вообще. `approve_write` сам является вызовом инструмента, поэтому фактическим рубежом для человека служит окно подтверждения вызовов в клиенте MCP; сервер гарантирует лишь невозможность записи без отдельного явного шага с указанием точного хеша операции.

#### 7.12.2 `rollback_write`

**Назначение.** Выполнить обратную операцию для уже совершённой записи по её токену отката.

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `token` | строка | да | Значение `rollback.token` из ответа выполненной операции, например `rb-1a2b3c4d5e6f7890` |

**Что обратимо:** проведение → отмена проведения; отмена проведения → проведение (неоперативное); изменение реквизитов → возврат ранее прочитанных значений; переключение пометки удаления `DeletionMark`.

**Что необратимо:** физическое удаление через `DELETE` (в «1С» нет отмены; вместо него рекомендуется `set_deletion_mark`) и создание новой записи. Токен для них не выдаётся, в ответе присутствует `irreversible_reason` с указанием ручного способа отмены.

**Примечания.** Токен одноразовый. Токены хранятся в памяти процесса, их число ограничено сотней — при переполнении вытесняется самый старый. После перезапуска сервера токены недействительны; обратную операцию тогда воспроизводят вручную по записи `inverse` в журнале аудита. Сам откат повторно через гейт не проводится — он отменяет уже подтверждённую операцию, — но фиксируется в журнале событиями `rollback_attempt` и `rollback_executed`.

**Журнал аудита.** При заданном `ONEC_AUDIT_LOG` в файл JSONL дописываются события `preview`, `approved`, `attempt`, `executed`, `failed`, `rollback_token_issued`, `rollback_attempt`, `rollback_executed` с отметкой времени и именем исполнителя (`ONEC_AUDIT_ACTOR`, по умолчанию — `ONEC_LOGIN`). Строка пишется до обращения к «1С»: если дописать её не удалось, операция отменяется. Журнал содержит тела запросов целиком и требует такой же защиты, как сами данные «1С».

## 8. Готовые сценарии (промпты)

Помимо инструментов сервер публикует три **промпта** (MCP prompts) — заготовки диалога с заранее прописанной последовательностью шагов. Клиент показывает их отдельным списком (в Claude Desktop, Cursor, Windsurf, VS Code это выбор сценария), выбранный промпт подставляется в переписку как сообщение пользователя, после чего модель выполняет шаги сама, вызывая инструменты из раздела 7.

Промпты входят в состав пакета — отдельная установка не требуется — и регистрируются всегда: переменная `ONEC_SERVICES` на них не влияет. При этом шаги промпта являются инструкцией для модели, а не техническим ограничением: если нужный модуль отключён, соответствующий вызов просто не состоится, а если включён режим `ONEC_WRITE_MODE`, запись пройдёт через гейт независимо от текста промпта.

| Промпт | Аргументы | Назначение |
|---|---|---|
| `inventory-database` | нет | Инвентаризация незнакомой базы |
| `find-and-post-document` | `query`; `document_type` (необязательный) | Найти документ и провести его после подтверждения человеком |
| `reconcile-balances` | `register_name`; `period` (необязательный) | Сверка остатков регистра накопления с его движениями |

### 8.1 `inventory-database` — инвентаризация незнакомой базы

Аргументов нет. Промпт задаёт четыре шага.

| Шаг | Вызов | Зачем |
|---|---|---|
| 1 | `get_config_preset` | Определить, на какую типовую конфигурацию (БП 3.0 / УТ 11 / ЗУП 3.1 / ERP 2) похожа база, и получить типовые имена сущностей, примеры и ловушки |
| 2 | `list_entities` по группам: `type=catalogs`, `documents`, `registers`, `charts`, `constants`, `journals`, `reports` | Получить фактический состав базы группами, а не разбирать префиксы вручную |
| 3 | `count_entities` по 5–10 наиболее релевантным сущностям | Понять, где реально лежат данные, а где пустые справочники |
| 4 | `describe_entity` по ключевым справочникам и типам документов | Узнать состав полей; `get_metadata` — только если нужны точные типы OData |

Порядок выбран от дешёвого к дорогому и от гипотез к фактам.

- `get_config_preset` не обращается к базе вообще: данные локальные, `ONEC_BASE_URL` не нужен. Это единственный шаг, который работает до того, как подключение настроено, поэтому он первый.
- Промпт прямо предписывает считать сущности с пометкой `confidence: "common"` подсказками, требующими проверки, и никогда — подтверждёнными именами. Пометка `verified` означает лишь, что имя встречено в цитируемом источнике, а не что оно есть в вашей базе: любая конфигурация могла быть доработана.
- Фильтр `type` покрывает `Catalog_`, `Document_`, все четыре вида регистров, `ChartOf*`, `Constant_`, `DocumentJournal_` и `Report_`. Планы обмена (`ExchangePlan_`), бизнес-процессы (`BusinessProcess_`) и задачи (`Task_`) ни одним фильтром не выбираются — для них промпт велит вызвать `list_entities` с `type="all"`.
- `describe_entity` читает одну запись (`$top=1`) и перечисляет её поля; полный `$metadata` — это EDMX всей базы, и запрашивать его ради списка полей одной сущности дорого. Если сущность пуста, полей по образцу не извлечь — инструмент так и сообщит и отправит к `get_metadata`.

На выходе промпт требует компактную сводку: таблицу групп сущностей с количествами и списки полей самых важных из них.

### 8.2 `find-and-post-document` — поиск и проведение с подтверждением

Аргументы: `query` — номер документа (например, `ТД-00123`) или подстрока наименования; `document_type` — тип `Document_*`, если известен (сужает поиск). Шаги:

1. **Найти.** Если `query` похож на номер — `get_document_by_number`; если это текст — `find_by_description`. Когда `document_type` не передан, промпт велит модели сначала спросить у пользователя, среди каких документов искать, а не угадывать тип.
2. **Показать.** Ключевые поля документа и его табличные части через `get_document_lines`, чтобы человек убедился: документ тот самый и заполнен полностью.
3. **Остановиться.** Промпт содержит явный запрет вызывать `post_document` без прямого «да» от пользователя и требует отдельно спросить, нужно ли оперативное проведение (`operational=true`, параметр `PostingModeOperational`).
4. **Провести и отчитаться.** После подтверждения — `post_document`; при ошибке модель обязана прочитать подсказку из разобранного ответа 1С (раздел 10) и предложить исправление.

Проведение — это запись: у документа выставляется признак проведения и формируются движения по регистрам. Обратная операция — `unpost_document`. Если требуется не рекомендация, а техническая гарантия, что модель не проведёт документ самовольно, включайте `ONEC_WRITE_MODE=approval`: тогда первый вызов вернёт описание операции и `op_hash`, а выполнение произойдёт только после `approve_write` с этим хешем и повторного вызова с теми же аргументами.

### 8.3 `reconcile-balances` — сверка остатков с движениями

Аргументы: `register_name` — имя регистра накопления (в промпте приведён пример `ОстаткиТоваровНаСкладах`); `period` — дата среза в формате `YYYY-MM-DDTHH:MM:SS`, без неё берутся текущие остатки. Шаги:

1. `get_accumulation_balance` с этим именем (и периодом, если задан) — виртуальная таблица `Balance()`.
2. `get_register` с `register_type="AccumulationRegister"` и тем же именем — записи движений (приход и расход).
3. Агрегация движений по измерениям и сравнение с остатками.
4. Отчёт: таблица расхождений, либо явное «всё сходится». Промпт предписывает считать результат `Balance()` авторитетным и помечать подозрительными строки движений.

Особенности, о которых стоит помнить при разборе результата:

- Промпт работает только с регистрами накопления. Для регистра бухгалтерии предназначен `get_accounting_balance` (таблицы `Balance`, `Turnovers`, `BalanceAndTurnovers`, `RecordsWithExtDimensions`, `ExtDimensions`).
- В ответе виртуальной таблицы к имени ресурса добавляется суффикс: `<Ресурс>Balance`, `<Ресурс>Turnover`, `<Ресурс>OpeningBalance`, `<Ресурс>ClosingBalance` и т. п. Измерения возвращаются как `<Измерение>_Key`.
- `get_register` по умолчанию возвращает 100 записей (максимум 5000). Агрегировать усечённую выборку и объявлять расхождение нельзя — сузьте период через `filter` и поднимите `top` либо считайте частями через `skip`.
- Расхождение чаще означает неполноту выборки движений или неучтённые служебные документы (корректировки, оприходования), чем ошибку учёта.

## 9. Практические примеры

Формат ниже: фраза пользователя — цепочка вызовов — что получится. **Все показанные ответы иллюстративны**: они собраны по форматам, которые возвращают инструменты, а не сняты с реальной базы. Имена реквизитов конфигурационно-зависимы — перед переносом в регламент проверяйте их `describe_entity` или `get_metadata` на своей базе.

### 9.1 Какие есть типы документов реализации

> «Покажи все типы документов, в названии которых есть „Реализация“.»

Вызов: `list_entities` с `type="documents"` и `search="Реализация"`.

Ответ — счётчик и список имён (иллюстрация):

```json
{ "total": 2, "entities": ["Document_РеализацияТоваровУслуг", "Document_РеализацияУслугПоПереработке"] }
```

Это первый шаг на любой незнакомой базе: он показывает, что действительно опубликовано в интерфейсе OData. Отсутствие сущности в списке — обычно признак того, что её не включили в состав интерфейса OData в Конфигураторе.

### 9.2 Документ по номеру вместе со строками

> «Найди счёт ТД-00123 от 2026-03-01 — покажи строки и сумму.»

Цепочка: `get_document_by_number` (`document_type`, `number="ТД-00123"`, `date="2026-03-01"`) → взять `Ref_Key` из результата → `get_document_lines` (`document_type`, `ref_key`, `tabular_section="Товары"`).

Дата в `get_document_by_number` необязательна, но сужает поиск: инструмент сам достраивает границы суток. Имя табличной части зависит от конфигурации — в типовых это `Товары` и `Услуги`, но проверять следует `describe_entity`. Сумму документа модель возьмёт из его реквизита; имя такого реквизита (в практике — `СуммаДокумента`) первоисточником не подтверждено, поэтому надёжнее суммировать строки самостоятельно.

### 9.3 Последние продажи за неделю

> «Дай последние 50 документов продаж за неделю, свежие сверху.»

Короткий путь: `get_recent_documents` (`document_type`, `top=50`, `posted_only=true`) — сортировка по `Date desc` уже внутри, максимум `top` — 100.

Точный путь с границами периода: `get_documents` с `filter="Date ge datetime'2026-07-28T00:00:00' and Date lt datetime'2026-08-04T00:00:00' and Posted eq true"` и `orderby="Date desc"`.

1С отдаёт время сервера, а не UTC, поэтому границы периода всегда задавайте явно двумя условиями. `Posted eq true` существенен: непроведённый документ движений в регистрах не имеет, и в отчётность попадать не должен.

### 9.4 Цены номенклатуры из регистра сведений

> «Прочитай регистр „Цены номенклатуры“ для товара с GUID abc-….»

Вызов: `get_register` с `register_type="InformationRegister"`, `register_name="ЦеныНоменклатуры"`, `filter="Номенклатура_Key eq guid'…'"`, `orderby="Period desc"`.

Имя регистра и его реквизиты помечены в пресете УТ 11 как `common` — проверьте `list_entities`. Виртуального «среза последних» среди обёрнутых инструментов нет: возвращаются записи как есть, поэтому актуальную цену получают сортировкой по `Period` и выбором верхней записи.

### 9.5 Создание и проведение документа продажи

> «Создай реализацию для ООО „Ромашка“ на две позиции и проведи.»

Цепочка: `find_by_description` (`entity="Catalog_Контрагенты"`, `query="Ромашка"`) → `create_document` (`document_type`, `data` со шапкой и строками) → `post_document` (`document_type`, `ref_key` из ответа).

Это самый рискованный сценарий раздела. Что учитывать:

- В УТ 11 и ERP 2 контрагент и партнёр — разные справочники: документы и взаиморасчёты идут по `Catalog_Контрагенты`, управленческая аналитика — по `Catalog_Партнеры`. Поиск не в том справочнике даёт пустой ответ.
- Состав обязательных полей `data` конфигурационно-зависим. Если поле не заполнено, 1С вернёт ошибку, которую сервер разберёт в категорию `field_required` с подсказкой (раздел 10).
- Создание записи необратимо автоматически: токена отката у него нет. Чтобы отменить, берут `Ref_Key` из результата и вызывают `set_deletion_mark` (мягкая пометка удаления) — она предпочтительнее физического `delete_document`.
- В режимах `preview` и `approval` вместо записи вернётся описание операции с `op_hash`; в режиме `preview` не запишется ничего и никогда.

### 9.6 Произвольный запрос OData

> «Выбери номенклатуру, где в наименовании есть „кофе“, разверни производителя, топ 20.»

Вызов: `odata_query` с `entity="Catalog_Номенклатура"`, `filter="substringof('кофе',Description) and IsFolder eq false and DeletionMark eq false"`, `expand="Производитель"`, `top=20`.

Это OData 3.0, а не 4.0: подстрока ищется через `substringof('текст',Поле)`, функцию `contains()` платформа не понимает. Иерархический справочник почти всегда требует `IsFolder eq false`, а пометка удаления сама собой не отфильтровывается — нужен явный `DeletionMark eq false`. `$expand` вернёт вложенный объект, но `$select` по его полям часто отдаёт HTTP 400: проще сделать второй запрос через `get_by_key`.

### 9.7 Остатки на складе на дату

> «Сколько товара было на складе на 1 июля?»

Вызов: `get_accumulation_balance` с `register_name="ТоварыНаСкладах"` (префикс `AccumulationRegister_` инструмент добавит сам), `period="2026-07-01T00:00:00"`, при необходимости `condition="Склад_Key eq guid'…'"`. Без `period` возвращаются текущие остатки.

Остатки не считают суммированием документов: часть движений делают служебные документы. Ресурс придёт с суффиксом (например, `КоличествоBalance`). Отдельно: регистр `СвободныеОстатки` удалён начиная с УТ 11.5.7 и ERP 2.5.7 — свободный остаток собирают из регистра сведений `РаспределениеЗапасов` самостоятельно.

### 9.8 Отслеживание новых заказов

> «Проверяй, не появились ли новые заказы клиентов.»

Вызов: `poll_changes_since` (`entity="Document_ЗаказКлиента"`, `since="2026-08-04T00:00:00"`, `date_field="Date"`). В ответе — строки, `count`, `has_more` и `next_cursor`, который передают в следующий вызов.

Подписок и вебхуков в штатном интерфейсе OData 1С нет — только опрос по расписанию. Инструмент `list_subscriptions` существует именно для того, чтобы это заявить явно: он всегда возвращает `supported: false`, пустой список и перечень обходных путей, чтобы модель не выдумывала несуществующую настройку подписки.

### 9.9 Отчёт из HTTP-сервиса

> «Возьми отчёт по адресу /hs/reports/balance?date=2026-04-01 и кратко изложи.»

Вызов: `get_report` с `report_url="/hs/reports/balance?date=2026-04-01"`.

Инструмент обращается к произвольному HTTP-сервису (`/hs/…`) той же информационной базы; адреса за пределами настроенного `ONEC_BASE_URL` отклоняются. Сам HTTP-сервис и формат его ответа — часть вашей конфигурации, а не сервера aprovodka: этот путь применяют, когда нужного разреза данных штатным OData не выразить.

## 10. Диагностика и устранение неполадок

Ошибка проходит два слоя обработки. Первый — разбор ответа 1С (`src/lib/errors.ts`):
из тела извлекается русское сообщение платформы и подбирается категория с подсказкой,
что делать дальше. Второй — общая обработка транспорта (`@theyahia/mcp-core`), которая
классифицирует сбой по HTTP-статусу и возвращает результат с признаком `isError: true`.
Клиент видит оба слоя в одном тексте ошибки.

### 10.1 Категории ошибок 1С и подсказки по восстановлению

Русское сообщение платформы извлекается из трёх форм ответа:

- JSON-конверт OData — поле `odata.error.message.value`;
- XML-конверт Atom — содержимое тега `<message xml:lang="ru">`;
- обычный текст — если тело короче 500 знаков, оно берётся целиком.

Дальше сообщение сопоставляется с набором шаблонов **по порядку, первое совпадение
побеждает**, и к тексту ошибки дописывается строка вида
`[1C <категория>] <краткая суть> — "<сообщение 1С, до 200 знаков>". Подсказка: <подсказка>`.
Начиная с версии 4.3.0 подсказка формулируется по-русски; таблица ниже приводит её дословно.

| Категория | По каким словам распознаётся | Что подсказывает продукт |
|---|---|---|
| `object_not_found` | «Объект не найден», «по ссылке не найден», `Object not found` | GUID в `Ref_Key` не соответствует ни одному объекту базы. Проверить имя сущности через `list_entities`, затем найти действительный `Ref_Key` через `get_documents` или `get_catalogs` |
| `field_required` | «Поле … не заполнено», «Не заполнено значение» | 1С отклонила запись из-за пустого обязательного реквизита. Имя реквизита — в тексте ошибки; добавить его в `data`. Состав полей смотреть через `list_entities` и разбор метаданных |
| `type_mismatch` | «несоответствие типов», «Несоответствие типа» | Значение отправлено не того типа. Типовые случаи: даты — `datetime'ГГГГ-ММ-ДДTчч:мм:сс'`, ссылки — объект `{Ref_Key, Type}`, булево — `true`/`false`, а не 0/1 |
| `permission_denied` | «Нарушение прав доступа», «Недостаточно прав» | У пользователя 1С нет права на объект или операцию. Учётные данные при этом верны — нужна выдача роли администратором 1С |
| `posting_failed` | «Документ не может быть проведен», «Не удалось провести» | Проведение отклонено бизнес-логикой конфигурации. Проверить, что контрагент, организация, склад действительны и не помечены на удаление, а период не закрыт |
| `deletion_locked` | «пометка удаления», «удаление запрещено» | Объект используется другими документами. Вместо физического удаления выставить `DeletionMark: true` (инструмент `set_deletion_mark`) |
| `invalid_guid` | «Неверный … GUID», «неправильный формат идентификатора» | `Ref_Key` должен быть 36-символьным UUID. Проверить значение аргумента `ref_key` |
| `session_locked` | «сеанс … заблокирован», «Блокировка» | База или сеанс временно заблокированы: регламентное задание, обновление конфигурации, восстановление. Подождать 10–60 секунд и повторить; если не проходит — к администратору 1С |
| `validation_failed` | «Ошибка валидации», «неверный запрос», `Bad Request` | 1С не приняла синтаксис OData-запроса. Обычные причины: незакрытая кавычка в `$filter`, опечатка в имени реквизита, несовпадение регистра |
| `unknown` | сообщение извлечено, но ни один шаблон не подошёл | Прочитать исходный русский текст 1С и решить: повторить, изменить параметры или передать оператору |

Если тело ответа пустое или сообщение извлечь не удалось, подсказка не добавляется —
остаётся только категория транспортного слоя: `validation` (аргументы не прошли проверку
схемы), `auth` (HTTP 401 или 403), `rate_limit` (429), `not_found` (404), `server_error`
(500 и выше), `timeout` (запрос прерван по времени), `unknown`.

### 10.2 Типовые проблемы

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| HTTP 401, текст «Ошибка авторизации» | Неверные `ONEC_LOGIN` / `ONEC_PASSWORD`; пользователь 1С заблокирован или у него нет права входа | Проверить учётные данные и что `ONEC_BASE_URL` указан без хвоста `/odata/...` — продукт достраивает `/odata/standard.odata/` сам |
| Любой инструмент падает; корень `/odata/standard.odata/` недоступен | Не включена публикация OData / HTTP-сервисов для информационной базы | Администратору 1С: включить HTTP-сервисы и публикацию OData (раздел 3.1 руководства), затем повторить `list_entities` |
| Читается одна сущность, соседняя даёт ошибку прав | У роли пользователя 1С нет прав на этот объект метаданных | Категория `permission_denied`: ключ верен, требуется выдать роль. Область доступа продукта задаётся именно ролью 1С, а не аргументами инструментов |
| Сущность отсутствует в выдаче `list_entities` | Скорее всего, объект не включён в состав стандартного интерфейса OData в Конфигураторе. Это настройка публикации, а не право доступа (подтверждать на своей базе) | Добавить объект в состав интерфейса OData. Отдельно проверить фильтр: планы обмена, бизнес-процессы и задачи не выбираются фильтром `type` — вызывать `list_entities` с `type="all"` |
| HTTP 404 на имя сущности, взятое из `get_config_preset` | Имя помечено `confidence: common` — типовое, первоисточником не подтверждённое; в вашей конфигурации или её редакции оно может отличаться | Найти фактическое имя: `list_entities` с аргументом `search` по фрагменту, при необходимости `get_metadata`. Именам с `confidence: verified` доверять тоже только после сверки с базой |
| Таймаут запроса | Запрос выполняется дольше 15 секунд (клиентское ограничение, всего 3 попытки — два повтора). Обычно — тяжёлый `$filter` или виртуальная таблица за длинный период | Сузить период, добавить `$top`, отсечь лишнее: `DeletionMark eq false`, `Posted eq true`. Повторить; при устойчивом повторении — к администратору 1С за нагрузкой базы |
| `describe_entity` вернул `fields: []` и примечание «Сущность пуста» | Инструмент определяет поля по образцу одной записи (`$top=1`), а в сущности нет ни одной записи | Взять состав полей из `get_metadata` (EDMX всей базы) либо из `get_config_preset` для типовой конфигурации |
| Пустая выборка при фильтре по регистратору или субконто | Ссылочные поля составного типа (`Recorder`, `ExtDimension1`…`3`) не сравниваются напрямую с `guid'…'` | Использовать `cast(guid'…','Document_ИмяДокумента')` |
| Ошибка синтаксиса на `contains(...)` или на дате без префикса | Платформа реализует OData **3.0**, а не 4.0 | Подстрока — `substringof('текст',Description)`; дата — `datetime'2026-01-31T00:00:00'` |
| В выборку попали объекты, помеченные на удаление | Пометка удаления сама собой не отсекается | Добавлять `DeletionMark eq false` в `$filter` |
| По документу не находится ни одного движения в регистрах | Документ не проведён | Проверить `Posted eq true`; у непроведённого документа движений нет |
| HTTP 400 после `$expand` с `$select` по вложенным полям | Платформа часто не принимает такую комбинацию | Сделать второй запрос по `Ref_Key` инструментом `get_by_key` |

### 10.3 Проверка работоспособности: `GET /health`

Служебный эндпоинт доступен, когда сервер запущен в режиме Streamable HTTP —
с переменной `HTTP_PORT` или с ключом `--http`. В режиме stdio эндпоинта нет:
работоспособность там проверяется вызовом `list_entities`.

```bash
curl http://localhost:3000/health
```

Иллюстративный ответ (не вывод реальной базы):

```json
{
  "status": "ok",
  "server": "aprovodka",
  "version": "4.3.0",
  "uptime": 137,
  "memory_mb": 62,
  "tools": 34
}
```

| Поле | Значение |
|---|---|
| `status` | Признак того, что процесс сервера отвечает. Всегда `ok`, если ответ вообще получен |
| `server` | Имя сервера в MCP-рукопожатии — `aprovodka` |
| `version` | Версия продукта; должна совпадать с версией установленного пакета |
| `uptime` | Время работы процесса в секундах (округлено). Неожиданно малое значение указывает на недавний перезапуск или падение |
| `memory_mb` | Резидентная память процесса в мегабайтах (округлено) |
| `tools` | Число фактически зарегистрированных инструментов. Зависит от `ONEC_SERVICES` (модуль `meta` включён всегда) и от режима записи: при `ONEC_WRITE_MODE=preview` или `approval` добавляются `approve_write` и `rollback_write`, при `deny` — вычитаются 12 пишущих инструментов (полная конфигурация: 22 вместо 34) |

Эндпоинт проверяет только сам процесс и не обращается к 1С. Ответ `status: "ok"`
не означает, что база доступна и учётные данные верны — связь с 1С подтверждается
успешным вызовом `list_entities`.

### 10.4 Что сервер пишет в журнал (stderr)

Весь журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. Записи
структурированные, по одной JSON-строке на событие. Клиент MCP обычно складывает
stderr в собственный файл журнала, который живёт неопределённо долго, поэтому состав
записей важен при работах на чужой базе.

**Что попадает в stderr:**

| Событие | Поля |
|---|---|
| Повтор запроса после 429 или 5xx | `status`, `delay`, `attempt`, `path` |
| Повтор после таймаута | `attempt`, `path` |
| Повтор после сетевого сбоя | `attempt`, `code`, `path` |
| Обновление истёкшей авторизации | `attempt`, `status` |
| Старт сервера, прослушивание порта, сигналы завершения | имя сервера, версия, число инструментов, порт |
| Необработанная ошибка | текст сообщения об ошибке |

**Чего в stderr нет:**

- **Строки запроса.** `path` пишется без части после `?`: в журнал попадает
  `/odata/standard.odata/Catalog_Контрагенты`, но не `$filter`, `$select` и `$orderby`.
  Значения отбора — ИНН, наименования, суммы, даты — в журнал не попадают.
- **Тел запросов и ответов.** Ни отправленные поля записи, ни полученные строки данных
  в журнал не пишутся.
- **Пароля и заголовка авторизации.** Поля с именами `password`, `token`, `secret`,
  `authorization` и подобными маскируются значением `***` на уровне логгера.

Исключение — **аудит-леджер** `ONEC_AUDIT_LOG` (раздел 5.4): это отдельный файл, и в него
тела операций записи пишутся дословно, иначе аудит бессмысленен. По чувствительности он
приравнивается к самим данным 1С: хранить с теми же ограничениями доступа.

## 11. Приложения

### 11.1 Глоссарий

| Термин | Значение |
|---|---|
| **MCP** (Model Context Protocol) | Протокол, по которому приложение с языковой моделью получает доступ к внешним данным и операциям. Продукт реализует серверную сторону протокола. |
| **MCP-клиент** | Программа пользователя: Claude Desktop, Cursor, Windsurf, VS Code с Copilot и другие. Запускает сервер как процесс (stdio) либо подключается к нему по HTTP. |
| **MCP-сервер** | Процесс, публикующий для клиента набор инструментов и промптов. Представляется именем `aprovodka`. |
| **Инструмент** (tool) | Именованная операция сервера с описанной схемой аргументов; модель вызывает её по имени, результат возвращается текстом. В версии 4.3.0 инструментов 34 (см. 11.2). |
| **Промпт** (prompt) | Готовый многошаговый сценарий, поставляемый с сервером и задающий модели последовательность вызовов инструментов. Их три: `inventory-database`, `find-and-post-document`, `reconcile-balances`. |
| **OData** | Протокол доступа к данным поверх HTTP. «1С:Предприятие» публикует стандартный интерфейс OData версии **3.0**, адрес — `${ONEC_BASE_URL}/odata/standard.odata/`. Версия существенна: подстрока задаётся как `substringof('текст',Description)`, а не `contains()`, даты — литералом `datetime'2026-01-31T00:00:00'`. |
| **EDMX** | XML-документ описания модели данных, который OData отдаёт по запросу `$metadata`: все сущности, их поля и типы. Возвращается инструментом `get_metadata`. |
| **Entity set** (набор сущностей) | Адресуемая коллекция записей одного объекта метаданных. Имя строится из префикса вида объекта и его имени в конфигурации: `Catalog_` — справочники, `Document_` — документы, `InformationRegister_`, `AccumulationRegister_`, `CalculationRegister_`, `AccountingRegister_` — четыре вида регистров. Полный перечень префиксов — в разделе 6.3. |
| **Ref_Key** | GUID ссылки на объект — первичный ключ записи. Аргументы `ref_key` проверяются на формат GUID до отправки запроса в базу. |
| **Проведение** | Операция, формирующая движения документа в регистрах. Выполняется действием OData `Post()` (`post_document`, параметр `operational` — оперативное проведение), отменяется `Unpost()` (`unpost_document`). Признак — поле `Posted`. Непроведённый документ движений не имеет. |
| **Регистр накопления** | Механизм учёта остатков и оборотов, `AccumulationRegister_*`. Итоги дают виртуальные методы `Balance(...)` — остатки на дату, `Turnovers(...)` — обороты за период, `BalanceAndTurnovers(...)`. Инструмент — `get_accumulation_balance`. |
| **Регистр бухгалтерии** | Механизм учёта по плану счетов методом двойной записи, `AccountingRegister_*`. Поля записи: `Period`, `Recorder` (регистратор), `AccountDr_Key` и `AccountCr_Key` (счета дебета и кредита), `Active`, `LineNumber`. Виртуальные таблицы — инструмент `get_accounting_balance`. |
| **Субконто** | Аналитический разрез записи регистра бухгалтерии; в OData — поля `ExtDimension1`…`ExtDimension3`. Тип составной, фильтрация только через `cast(guid'…','Тип')`; прямое сравнение с `guid'…'` даёт пустую выборку либо ошибку. |
| **Табличная часть** | Строки документа или элемента справочника.
