Пакет `@theyahia/retailcrm-mcp`, версия 3.0.0, 39 инструментов и 2 сценария-промпта.
Node.js 18 и выше. API RetailCRM версии 5.

## 1. Что это и кому нужно

Сервер открывает ИИ-агенту рабочий контур RetailCRM (и её редакции Simla): заказы,
покупатели, каталог, остатки по складам, платежи, задачи менеджеров, заметки, файлы,
расходы, сегменты и справочники. Всё, ради чего оператор обычно открывает вкладку CRM и
ставит фильтры руками, выполняется репликой в чате: «сколько заказов в статусе „новый“ за
вчера», «найди клиента по телефону», «поставь задачу менеджеру перезвонить», «создай
заказ на две позиции с доставкой курьером».

Кому это нужно: менеджеру интернет-магазина, который целый день сидит между чатом с
клиентом и карточкой заказа; руководителю, которому нужна сводка за период без выгрузки в
таблицу; интегратору, который сверяет данные CRM со складом или бухгалтерией.

Чтения возвращают не сырой ответ RetailCRM, а сокращённую выжимку — только поля, нужные
для ответа. Это управляемо: `detail: "full"` добавляет строки заказа, доставку и платежи,
`raw: true` возвращает ответ CRM без изменений.

## 2. Установка и подключение

### Claude Desktop

Файл `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "retailcrm": {
      "command": "npx",
      "args": ["-y", "@theyahia/retailcrm-mcp"],
      "env": {
        "RETAILCRM_DOMAIN": "yourstore.retailcrm.ru",
        "RETAILCRM_API_KEY": "ваш_api_ключ"
      }
    }
  }
}
```

Клиент читает конфигурацию при старте — после правки его нужно перезапустить. Переменные
окружения операционной системы дочернему процессу могут не наследоваться, поэтому ключ
задают именно в блоке `env`.

### Claude Code

```
claude mcp add retailcrm -e RETAILCRM_DOMAIN=yourstore.retailcrm.ru -e RETAILCRM_API_KEY=ваш_ключ -- npx -y @theyahia/retailcrm-mcp
```

### Cursor / Windsurf / VS Code (Copilot)

Cursor и Windsurf принимают тот же блок `mcpServers` в `.cursor/mcp.json` или
`.windsurf/mcp.json`. У VS Code файл `.vscode/mcp.json`, и корневой ключ там — `servers`,
а не `mcpServers`; поля `command`, `args`, `env` те же. Файл рабочей области обычно
попадает в систему контроля версий — `RETAILCRM_API_KEY` в нём хранить не следует.

### Режим Streamable HTTP

```bash
PORT=3000 npx @theyahia/retailcrm-mcp --http
```

Режим включается **только флагом `--http`**; переменная `PORT` (по умолчанию 3000) и `HOST`
(по умолчанию `127.0.0.1`) задают адрес. Транспорт stateless: на каждый `POST /mcp`
создаётся отдельный экземпляр сервера, который закрывается вместе с ответом.

| Метод и путь | Поведение |
|---|---|
| `POST /mcp` | Приём запросов MCP |
| `GET /health` | `{status, version, tools, prompts}` |
| `GET` или `DELETE /mcp` | `405 Method not allowed` — сессий в этом режиме нет |
| прочее | `404` |

Защита от DNS-rebinding включена по умолчанию: принимаются только заголовки `Host` из
`RETAILCRM_HTTP_ALLOWED_HOSTS`, по умолчанию `localhost:<порт>,127.0.0.1:<порт>`.
Отключается `RETAILCRM_DNS_PROTECTION=off`. Собственной аутентификации у `/mcp` нет, а
доступ к порту равносилен доступу к CRM с правами ключа — публиковать порт в недоверенной
сети нельзя.

### Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `RETAILCRM_DOMAIN` | да | Домен вида `yourstore.retailcrm.ru`; схема `https://` подставляется сама, лишний слеш срезается |
| `RETAILCRM_API_KEY` | да | Ключ API, уходит в заголовке `X-API-KEY` |
| `RETAILCRM_URL` | нет | Запасное имя для `RETAILCRM_DOMAIN` |
| `RETAILCRM_READONLY` | нет | `1`, `true` или `yes` — регистрируются только 25 читающих инструментов |
| `RETAILCRM_RATE_LIMIT` | нет | Запросов в секунду, ограничение на стороне клиента; по умолчанию выключено |
| `PORT`, `HOST` | нет | Адрес HTTP-режима |
| `RETAILCRM_HTTP_ALLOWED_HOSTS` | нет | Допустимые значения `Host` через запятую |
| `RETAILCRM_DNS_PROTECTION` | нет | `off` отключает проверку `Host` |

Отсутствие переменных обнаруживается **при первом вызове инструмента**, а не при старте:
адрес и ключ читаются лениво. Сообщение прямо называет недостающую переменную и путь к
ней в кабинете.

## 3. Где взять ключ доступа

Ключ выдаётся в кабинете RetailCRM: **Настройки → Интеграция → Ключи API** (этот путь
сервер называет сам в сообщении об отсутствующем ключе). Создайте ключ и выдайте ему права
на те разделы, с которыми будете работать: заказы, клиенты, магазин (каталог и остатки),
справочники, задачи, файлы, расходы.

Домен — это адрес вашего кабинета целиком, вместе с зоной: `yourstore.retailcrm.ru`. Схему
`https://` писать необязательно — сервер её подставит, а лишнюю уберёт; конечный адрес
запросов складывается как `https://<домен>/api/v5`.

**Права ключа определяют реальную границу возможного.** Инструмент, для которого у ключа
нет права, вернёт ошибку доступа от RetailCRM, а не будет скрыт из списка. Обратное тоже
верно: `RETAILCRM_READONLY=1` прячет пишущие инструменты от модели, но не ограничивает сам
ключ — это защита от неудачной формулировки, а не замена правам.

**Многомагазинный ключ.** Если ключ обслуживает несколько сайтов, при создании и изменении
объектов нужен параметр `site` с символьным кодом магазина. Список кодов — `list_sites`.

## 4. Инструменты по задачам

Списочные инструменты работают по схеме `page` (с 1) и `limit` (1–100, по умолчанию 20) и
возвращают блок `pagination` с полями `page`, `totalPages`, `totalCount`, `returned`,
`hasMore`. Читающие инструменты заказов и клиентов принимают `detail` (`summary` по
умолчанию либо `full`) и `raw` (вернуть нетронутый ответ CRM).

### 4.1 Начать с справочников

Восемь инструментов без обязательных параметров, каждый принимает только `raw`. Ответ
RetailCRM приходит объектом, ключами которого служат коды; сервер разворачивает его в
массив значений.

| Инструмент | Что отдаёт | Когда нужен |
|---|---|---|
| `list_statuses` | Коды, названия, группы и порядок статусов заказа | Перед любым фильтром или сменой статуса |
| `list_order_types` | Типы заказов | Значение `order_type` в `create_order` |
| `list_order_methods` | Способы оформления (каналы привлечения) | Аналитика источников |
| `list_delivery_types` | Типы доставки с кодами и базовой стоимостью | `delivery_code` |
| `list_payment_types` | Типы оплаты | `type` в `order_payment_create` |
| `list_stores` | Склады и магазины | Разбор остатков |
| `list_sites` | Сайты, доступные ключу | Значение `site` на создании и изменении |
| `list_countries` | Коды стран ISO | Адреса и доставка |

Коды статусов, типов доставки и оплаты **настраиваются в каждом кабинете отдельно**.
Угаданный код приведёт к отказу CRM, поэтому справочник вызывают до записи, а не после
ошибки.

### 4.2 Заказы

**`list_orders`** — выборка заказов. Все параметры необязательны: `filter_status` (код
статуса), `filter_customer` (имя покупателя, частичное совпадение), `filter_number` (номер
заказа), `filter_date_from` и `filter_date_to` (даты создания в формате `YYYY-MM-DD`,
формат проверяется до запроса). В кратком виде на каждый заказ приходят `id`, `number`,
`status`, `total`, `customer`, `phone`, `itemCount`, `createdAt`.

**`get_order`** — один заказ. Обязателен `id`; `by` выбирает, чем считать это значение —
`id` (внутренний идентификатор RetailCRM, по умолчанию) или `externalId` (идентификатор
внешней системы). При `detail: "full"` добавляются позиции, доставка, платежи и оба
комментария.

**`create_order`** — создание заказа. Обязателен непустой массив `items`, у каждой позиции
`product_name`, `quantity` и `initial_price`. Покупателя задают одним из трёх способов:
`customer_id`, `customer_external_id` или встроенное создание через `first_name`
(плюс `last_name`, `phone`, `email`). Если не задано ни одно из трёх — сервер откажет до
обращения к CRM. Необязательны `order_type` (по умолчанию `eshop-individual`), `status`,
`delivery_code`, `delivery_cost`, `delivery_address`, `site`.

**`update_order`** — изменение. Обязателен `id` (плюс `by`). Отправляются **только
переданные поля**: `status`, контакты покупателя, перепривязка к другому покупателю через
`customer_id` / `customer_external_id`, доставка, `manager_comment` (внутренний) и
`customer_comment` (видимый покупателю).

**`orders_history`** — журнал изменений заказов, включая переходы между статусами.
`filter_since_id` возвращает записи после указанного номера записи журнала — это штатный
способ инкрементальной синхронизации; `filter_date_from`, `filter_date_to`,
`filter_order_id` сужают выборку. Ответ отдаётся как есть, без переработки.

### 4.3 Покупатели

**`list_customers`** — поиск по `filter_name`, `filter_email`, `filter_phone` и датам
создания. Кратко: `id`, `name`, `email`, `phone`, `ordersCount`, `totalSpent`. При
`detail: "full"` добавляются все телефоны, адрес, город, регион, `externalId`.

**`get_customer`** — один покупатель по `id` или `externalId` (параметр `by`).

**`create_customer`** — обязателен `first_name`. Необязательны `last_name`, `patronymic`,
`email`, `phones` (массив строк), `address_text`, `address_city`, `address_region`,
`external_id`, `site`.

**`update_customer`** — те же поля плюс `id` и `by`. Массив `phones` **заменяет** список
телефонов целиком, а не дополняет его.

**`merge_customers`** — склейка дублей. `result_customer_id` — тот, кого оставляем,
`merged_customer_ids` — массив тех, кого вливаем. Влитые записи **удаляются**; операция
помечена как разрушающая и скрывается в режиме `RETAILCRM_READONLY`.

**`customers_history`** — журнал изменений покупателей, `filter_since_id` для
инкрементальной выгрузки.

### 4.4 Каталог и остатки

**`list_products`** — товары каталога. Фильтры: `filter_name`, `filter_active`,
`filter_groups` (идентификатор группы), `filter_min_price`, `filter_max_price`. На каждый
товар приходят `id`, `name`, `article`, `active`, `url`, названия групп и массив
торговых предложений с ценой и количеством.

**`list_product_groups`** — дерево категорий; `filter_active`, `filter_parent_group`.

**`store_inventories`** — остатки и себестоимость по торговым предложениям. Фильтры:
`filter_offer_external_id`, `filter_product_active`, `site`. Параметр `details: true`
разворачивает остаток по складам — без него приходит суммарное количество.

### 4.5 Платежи по заказу

**`order_payment_create`** — регистрация оплаты. Обязательны `amount` и `type` (код из
`list_payment_types`), а также один из `order_id` / `order_external_id` — иначе сервер
откажет до обращения к CRM. Необязательны `status` и `paid_at` в формате
`YYYY-MM-DD HH:MM:SS`.

**`order_payment_edit`** — правка суммы, статуса, даты оплаты по `id` платежа (`by`
переключает на `externalId`).

**`order_payment_delete`** — удаление платежа по `id`. Разрушающая операция.

### 4.6 Работа менеджера: задачи, заметки, файлы

**`tasks_list`** — задачи и напоминания. `filter_status` принимает `completed`,
`performing` или `not_completed`; `filter_performer_id` — идентификатор менеджера;
`filter_customer` — **текстовое** совпадение по покупателю (числового фильтра по
идентификатору клиента в API v5 нет).

**`tasks_create`** — обязателен `text`. Необязательны `commentary`, `datetime` (срок в
формате `YYYY-MM-DD HH:MM:SS`), `performer_id`, `order_id`, `customer_id`, `site`.

**`tasks_edit`** — по `id`: правка текста, срока, исполнителя; `complete: true` закрывает
задачу.

**`customer_notes_list`** — заметки, фильтры `filter_customer_id` и
`filter_customer_external_id`. **`customer_notes_create`** — обязателен `text` и один из
идентификаторов покупателя, необязателен `manager_id`. **`customer_notes_delete`** —
удаление по числовому `id`, разрушающая операция.

**`files_list`** — вложения, фильтры `filter_order_id`, `filter_customer_id`,
`filter_filename`. **`files_get`** — метаданные по числовому `id`. **`files_upload`** —
загрузка: `filename`, `content` и, для двоичных файлов, `base64: true` плюс
`content_type`. Файл уходит **сырым телом запроса**, а не формой multipart.

### 4.7 Деньги и маркетинг

**`list_costs`** — записи расходов: `filter_date_from`, `filter_date_to`,
`filter_cost_groups`. **`create_cost`** — обязательны `summ`, `cost_item` (код статьи
расхода) и `date_from`; если `date_to` не задан, он приравнивается к `date_from`.
Необязательные `order_id` и `comment` привязывают расход к заказу.

**`list_segments`** — сегменты покупателей (RFM и маркетинговые когорты);
`filter_active`, `filter_type` (`dynamic` или `custom`).

### 4.8 Сводки за период

**`get_orders_summary`** — обязательны `date_from` и `date_to`, необязательны
`filter_status` и `max_pages` (1–20, по умолчанию 5). Возвращает `totalCount` (точное
число заказов периода — берётся из пагинации), а также `revenue`, `averageOrderValue` и
распределение `byStatus`, посчитанные по фактически загруженным заказам. Ограничение
описано в разделе 6.2.

**`get_customers_summary`** — число новых покупателей за период; обязательны `date_from` и
`date_to`. Делает один запрос с `limit=1` и берёт только счётчик — дёшево и точно.

### 4.9 Сценарии-промпты

Кроме инструментов сервер регистрирует два промпта: `new-orders` (заказы за сегодня
таблицей) и `customer-search` с параметром `query` (поиск покупателя по имени, почте или
телефону). В счёт 39 инструментов они не входят.

## 5. Готовые сценарии

**1. «Сколько заказов пришло сегодня и на какую сумму?»**
`get_orders_summary` (`date_from` и `date_to` — сегодняшняя дата). Один вызов даёт точное
число, выручку, средний чек и разбивку по статусам. Списком то же самое — `list_orders` с
`filter_date_from` и `filter_date_to`.

**2. «Найди клиента по телефону +7 916 … и покажи его заказы.»**
`list_customers` (`filter_phone`) → взять `id` → `list_orders` (`filter_customer` с именем
из карточки). Прямого фильтра заказов по идентификатору клиента в наборе нет — связка идёт
через имя либо через `get_customer` с `detail: "full"` для полного контекста.

**3. «Создай заказ: две пачки кофе по 450 рублей, доставка курьером, клиент новый.»**
`list_order_types` и `list_delivery_types` (взять коды) → `create_order` (`first_name`,
`phone`, `items` с `product_name` / `quantity` / `initial_price`, `delivery_code`,
`delivery_cost`) → `get_order` по полученному `id` для проверки.

**4. «Переведи заказ 12345 в статус „комплектация“ и оставь комментарий менеджера.»**
`list_statuses` (найти точный код нужного статуса) → `update_order` (`id: "12345"`,
`status`, `manager_comment`). Коды статусов у каждого кабинета свои — угадывать нельзя.

**5. «Отметь, что заказ оплачен наличными 5000 рублей.»**
`list_payment_types` (код нужного типа) → `order_payment_create` (`order_id`, `amount`,
`type`, `status: "paid"`, `paid_at`).

**6. «Есть ли на складе товар с артикулом ABC-1 и сколько?»**
`list_products` (`filter_name`) для поиска товара и его предложений →
`store_inventories` (`filter_offer_external_id`, `details: true`) — разбивка по складам.

**7. «Поставь менеджеру задачу перезвонить клиенту завтра в 11.»**
`list_customers` (найти `id`) → `tasks_create` (`text`, `datetime: "2026-09-04 11:00:00"`,
`performer_id`, `customer_id`).

**8. «Слей два дубля клиента в одну карточку.»**
`list_customers` (`filter_phone` или `filter_email` — найти обе записи) → сверить, какая
полнее → `merge_customers` (`result_customer_id`, `merged_customer_ids`). Операция
необратима: вливаемые карточки удаляются вместе со своей историей.

**9. «Выгрузи всё, что изменилось в заказах с прошлой синхронизации.»**
`orders_history` (`filter_since_id` — номер последней обработанной записи, `limit: 100`),
дальше листать `page` до `hasMore: false`, запомнив наибольший номер записи.

## 6. Ограничения и подводные камни

### 6.1 Изменяющие операции не повторяются автоматически

Повтор выполняется только для запросов чтения (GET). Все создания, изменения и удаления
уходят методом POST и при таймауте, `5xx` или обрыве связи **не повторяются** — ответ CRM
неизвестен, и слепой повтор создал бы второй заказ, второй платёж или второй расход.

Исключение — код `429`: он означает, что запрос отвергнут **до** обработки, поэтому
повторяется даже для записи.

Повторов не больше трёх, задержка `1000 × 2^(попытка−1)` мс, но не дольше 8 секунд, плюс
случайная добавка до 250 мс, чтобы параллельные клиенты не били в один и тот же момент.
Таймаут одного запроса — 15 секунд, переменной окружения не настраивается.

Практический вывод: получив ошибку на `create_order` или `order_payment_create`, сначала
проверьте `list_orders` по номеру или периоду, и только потом повторяйте.

### 6.2 Сводка по заказам считается по окну, а не по всему периоду

`get_orders_summary` возвращает **точный** `totalCount` — он берётся из счётчика
пагинации. А вот `revenue`, `averageOrderValue` и `byStatus` считаются по фактически
загруженным заказам: до `max_pages` страниц по 100 штук, то есть по умолчанию до 500
заказов. Если заказов за период больше, в ответе появляется `partial: true` и поле
`aggregatedOver` с реальным числом обработанных записей.

Считать выручку по ответу с `partial: true` нельзя. Варианты: поднять `max_pages` (до 20,
то есть до 2000 заказов) или разбить период на части.

### 6.3 Пагинация и объём выдачи

`limit` жёстко ограничен сотней записей. Полная выгрузка — это цикл по `page` до тех пор,
пока `hasMore` не станет `false`; ориентироваться на `totalPages` из блока `pagination`.

Краткий вид (`detail: "summary"`) — не украшение, а способ уложить выдачу в контекст
модели: `detail: "full"` на сотне заказов со строками даёт ответ на порядок больше, а
`raw: true` — ещё больше. Оставляйте `raw` для разбора нештатных ситуаций.

### 6.4 Ограничение частоты запросов

RetailCRM режет всплески запросов, отвечая `503`. Собственного ограничителя сервер по
умолчанию не включает: переменная `RETAILCRM_RATE_LIMIT` задаёт потолок в запросах в
секунду и по умолчанию равна нулю (выключено). Комментарий в коде указывает, что API v5
допускает порядка 10 запросов в секунду с одного адреса; при массовых выгрузках имеет
смысл выставить `RETAILCRM_RATE_LIMIT=8` и не полагаться на повторы.

### 6.5 Права ключа, режим только чтения и разрушающие операции

Три инструмента помечены как разрушающие: `merge_customers`, `order_payment_delete`,
`customer_notes_delete`. Ещё одиннадцать пишут данные. Инструменты сообщают клиенту свой
характер (`readOnlyHint`, `destructiveHint`), но подтверждения перед действием у сервера
нет — модель вызовет их так же, как чтение.

`RETAILCRM_READONLY=1` (либо `true` / `yes`) — единственный встроенный барьер: при нём
регистрируются только 25 читающих инструментов, остальных 14 модель просто не видит.
Значение читается **при создании сервера**, то есть при запуске процесса; на лету не
меняется. Для аналитических подключений это режим по умолчанию.

### 6.6 Позиции заказа задаются наименованием

`create_order` кладёт в позицию только `offer.displayName`, `quantity` и `initialPrice`.
Привязать позицию к торговому предложению каталога по идентификатору или артикулу этим
инструментом нельзя — заказ создаётся со свободным наименованием. Для заказов, которые
должны списывать остатки конкретного предложения, набор позиций правят в кабинете либо
другим интеграционным каналом.

### 6.7 Форматы и единицы

| Что | Формат |
|---|---|
| Даты фильтров (`filter_date_*`, `date_from`, `date_to`) | `YYYY-MM-DD`, проверяется регулярным выражением до запроса |
| Момент оплаты (`paid_at`) и срок задачи (`datetime`) | `YYYY-MM-DD HH:MM:SS` |
| Суммы (`amount`, `initial_price`, `summ`, `delivery_cost`) | Число в валюте кабинета |
| `page` | Целое, с 1 |
| `limit` | Целое 1–100 |

Даты фильтров сравниваются по дате создания объекта. Часовой пояс задаётся настройками
кабинета — период «за сегодня» у кабинета и у вызывающей стороны может разойтись на
несколько часов.

### 6.8 Идентификаторы: `id` против `externalId`

Заказы, покупатели и платежи адресуются двумя разными идентификаторами: внутренним
`id` RetailCRM и `externalId` внешней системы. Инструменты чтения и правки принимают оба —
через параметр `by`. Ошибка в выборе `by` даёт не пустой ответ, а `404`: значение
ищется не в том поле.

## 7. Частые ошибки

Ошибка приходит модели результатом с признаком `isError: true`; текст собирается из ответа
RetailCRM: `RetailCRM HTTP <код> — <errorMsg> — <поле>: <сообщение>`. Если тело ответа не
разбирается как JSON, в текст попадают первые 500 символов ответа как есть.

| Что видно | Что это значит | Что делать |
|---|---|---|
| `RETAILCRM_DOMAIN is not set…` | Домен не дошёл до процесса; проявляется при первом вызове инструмента, а не при старте | Задать `RETAILCRM_DOMAIN` в блоке `env` и перезапустить клиент |
| `RETAILCRM_API_KEY is not set. Create one in RetailCRM > Settings > Integration > API keys` | Нет ключа | Создать ключ в кабинете и положить в `env` |
| `RetailCRM HTTP 403` | Ключ действителен, но у него нет права на этот раздел | Добавить право ключу в разделе «Ключи API»; для чтения аналитики достаточно прав на заказы и клиентов |
| `RetailCRM HTTP 401` | Ключ не принят: опечатка, ключ отозван или домен чужой | Сверить ключ и домен; ключ одного кабинета в другом не работает |
| `RetailCRM HTTP 404` | Объект не найден по этому идентификатору | Проверить `by`: значение `externalId` при `by: "id"` не найдётся никогда |
| `RetailCRM HTTP 400 — errors — status: …` | CRM отвергла значение справочника: несуществующий код статуса, типа доставки или оплаты | Взять код из соответствующего `list_*` — коды настраиваются в каждом кабинете |
| `RetailCRM HTTP 400 — … site` | Ключ обслуживает несколько сайтов, а параметр `site` не передан | `list_sites`, затем повторить с нужным кодом |
| `RetailCRM HTTP 503` | Сработала защита от всплеска запросов | Выставить `RETAILCRM_RATE_LIMIT`, уменьшить `limit`, разнести выгрузку по времени |
| `Rate limit` / HTTP 429 | Лимит выбран; повтор выполняется автоматически, до трёх раз | Если ошибка дошла до вас — все три попытки исчерпаны, нужна пауза |
| `RetailCRM request timed out after 15000ms` | Ответ не пришёл за 15 секунд | Для чтения — повторить с меньшим `limit`; для записи — сначала проверить, не создан ли объект |
| `RetailCRM: all retries exhausted` | Три попытки подряд закончились повторяемой ошибкой | Проверить доступность кабинета; продолжать повторы бессмысленно |
| `Provide first_name for a new customer, or customer_id/customer_external_id to link an existing one` | Проверка сервера до обращения к CRM: покупатель заказа не задан ни одним способом | Добавить `first_name` либо идентификатор существующего покупателя |
| `Provide order_id or order_external_id` | Платёж не привязан к заказу | Указать один из двух идентификаторов |
| `Provide customer_id or customer_external_id` | Заметка не привязана к покупателю | То же для заметки |
| `Date must be in YYYY-MM-DD format` | Ошибка проверки параметров: дата передана в другом виде (`01.09.2026`, ISO с временем) | Привести к `YYYY-MM-DD` |
| Ответ пришёл, но список пуст | Фильтр отработал, совпадений нет | Проверить регистр и код фильтра; частичное совпадение работает у `filter_name` и `filter_customer`, но не у кодов справочников |
| `partial: true` в сводке | Период шире загруженного окна | Раздел 6.2: поднять `max_pages` или разбить период |

Журнал сервера идёт в **stderr** — stdout занят протоколом JSON-RPC. Туда же пишутся
предупреждения о повторах (`Retryable error, backing off`) и строка запуска с числом
активных инструментов и признаком `readonly`. Если инструментов оказалось 25 вместо 39,
причина — включённый `RETAILCRM_READONLY`.
