# Security & Correctness Review — WWmcp
Date: 2026-05-21
Reviewer: Claude (Sonnet 4.6)
Scope: full repo read-only pass; focused on MCP isolation, supply-chain, prompt injection, SSRF, trust boundaries.

## BLOCKERS

### 1. SSRF via `get_report` tool — `servers/1c-rest/src/tools/reports.ts:9`

`report_url` is a free-form `z.string()` with no validation. It feeds directly to `oneCGet(params.report_url)`.

In `packages/core/src/client.ts:85`:
```ts
const url = opts.path.startsWith("http")
  ? `${opts.path}${query}`        // ← absolute URL bypass
  : `${this.baseUrl}${opts.path}`;
```

If an LLM (or a malicious tool call) passes `https://169.254.169.254/latest/meta-data/` as `report_url`, the 1C client fetches it directly with the 1C Basic auth credentials attached as headers — those credentials are sent to the attacker's endpoint too. Any URL starting with `http` escapes the configured `ONEC_BASE_URL` boundary entirely.

**Fix:** validate `report_url` starts with `/` (or better: only allow whitelisted prefixes like `/hs/`). Remove the `startsWith("http")` bypass in `BaseHttpClient.request()` or at minimum never expose it to tool-level user input.

---

### 2. `sanitizeApiResponse` is dead code — all servers return raw API data to LLM

`packages/core/src/sanitize.ts` exports `sanitizeApiResponse()` which strips prompt injection patterns. It is imported by zero server files (confirmed by grep across `servers/`). Every server passes raw third-party API responses directly to the MCP content array.

This means content from Avito listings, Bitrix24 CRM notes, Wildberries product descriptions, etc. reaches the LLM without any filtering. A malicious seller could embed `"ignore all previous instructions"` in a product description and it flows into the model context verbatim.

**Fix:** call `sanitizeApiResponse()` + `truncateResponse()` on every string returned in `content[].text` before returning from tool handlers. The simplest place is inside `withErrorHandling()` in `packages/core/src/errors.ts`.

## WARNINGS

### 3. CORS wildcard is always active in HTTP/Docker mode — `packages/core/src/server.ts:82`

`startHttp()` has `corsOrigins?: string[]` defaulting to `["*"]` with a comment "development only." But `runServer()` (line 232) calls `startHttp(createServer, { ...config, port })` — `corsOrigins` is never passed from any server's `index.ts`, so production Docker containers always run with `Access-Control-Allow-Origin: *`.

The Dockerfile sets `ENV HTTP_PORT=3000` and `CMD ["node", "dist/index.js", "--http"]`, making this the default container posture. Any web page can issue cross-origin MCP requests to a deployed container.

**Fix:** either change the default to `[]` (deny all) or require `corsOrigins` to be an explicit required field in `HttpServerConfig`.

### 4. CI security audit is non-blocking — `.github/workflows/ci.yml:47`

```yaml
- name: Security audit
  run: pnpm audit --audit-level=high
  continue-on-error: true
```

High-severity npm vulnerabilities log a warning but never block the pipeline. For a public npm org (`@theyahia`) with payment-API servers, this is a supply-chain exposure window.

**Fix:** remove `continue-on-error: true`. If there are existing known vulns that need deferral, use `pnpm audit --audit-level=critical` or an allowlist instead of silencing the check entirely.

## NITS

### 5. Dependabot auto-merge on `pull_request_target` with write permissions

`.github/workflows/dependabot-automerge.yml` uses the `pull_request_target` trigger (runs in the context of the base branch) with `contents: write` and `pull-requests: write`. This is the documented dangerous pattern for auto-merge workflows — a compromised Dependabot PR could be crafted to run arbitrary code with write access. The check `github.actor == 'dependabot[bot]'` is bypassable via actor spoofing in some GitHub configurations.

Minor given it only auto-merges semver-patch, but worth an audit if the project grows contributors.

## Verdict: fix-and-ship

Finding 1 (SSRF) and Finding 2 (dead sanitizer) must be addressed before public promotion of the catalog. Finding 3 (CORS) must be fixed before any server is deployed as an HTTP endpoint accessible outside localhost. Finding 4 should be fixed in the same PR as any security-related change.
